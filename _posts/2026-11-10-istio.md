## 서비스 간 호출 문제

### 연쇄 장애

주문 API가 평소처럼 돌다가, 재고 서비스 하나가 느려진 뒤 주문 화면 전체가 멈춘다. 서비스가 서비스를 부르는 구조에서는 맨 끝의 지연이 앞쪽으로 번진다.

- 주문(A)이 결제(B)를 부르고, 결제가 재고(C)를 부른다.
- C가 응답하지 않으면 B의 스레드가 응답을 기다리며 하나씩 묶인다.
- B의 스레드가 다 묶이면 B도 응답하지 못하고, 이번에는 A의 스레드가 B를 기다리며 묶인다.

세 장면에서 C가 느려진 뒤 대기 칸이 어느 쪽으로 번지는지 본다.

<figure class="fig" data-figure="istio-cascade">
  <figcaption>재고 서비스 하나가 느려질 때 앞단 서비스의 스레드가 차는 순서</figcaption>
</figure>

C 하나가 느려졌을 뿐인데 A와 B는 CPU와 메모리가 남은 채로 멈춘다. 도미노처럼 원인과 증상이 멀리 떨어져 있어서, 증상이 보이는 A부터 뒤지면 원인을 찾기 어렵다.

이 번짐을 끊는 장치는 세 가지다.

- 타임아웃: 기다림에 상한을 둔다.
- 재시도: 실패한 요청을 다른 곳에 다시 보낸다.
- 서킷 브레이커(circuit breaker): 고장 난 상대로 가는 요청을 끊는다.

### 공통 기능의 위치

서비스가 서른 개인 팀에서 타임아웃 값을 바꾸려면 서른 개 저장소를 고쳐 배포해야 한다. 위의 세 장치에 암호화와 지표 수집까지 더하면, 서비스마다 같은 기능을 따로 넣고 있는 셈이다.

예전에는 이를 라이브러리로 넣었다. Netflix의 Hystrix가 대표적이고, 지금은 유지보수 모드라 Resilience4j 같은 후속 라이브러리를 쓴다.

- 언어마다 라이브러리가 다르다. 설정 이름과 기본값도 제각각이다.
- 정책을 바꾸려면 서비스마다 코드를 고치고 다시 배포한다.
- 어느 서비스가 어떤 값을 쓰는지 한눈에 볼 곳이 없다.

서비스 메시(service mesh)는 이 기능을 코드에서 빼서 네트워크 경로에 둔다. 파드마다 프록시를 붙이고 모든 요청이 프록시를 지나게 하면, 앱은 평범한 HTTP 호출만 하고 정책은 프록시가 지킨다. 두 장면에서 정책이 놓인 자리가 어디로 옮겨 가는지 본다.

<figure class="fig" data-figure="istio-where">
  <figcaption>공통 기능을 코드에 넣을 때와 프록시로 뺄 때</figcaption>
</figure>

프록시는 서비스 수만큼 늘어나서, 그 설정을 한곳에서 관리하는 부분이 따로 있다.

- 데이터 플레인(data plane): 요청이 실제로 지나가는 프록시들. Istio에서는 Envoy다.
- 컨트롤 플레인(control plane): 프록시에 설정과 인증서를 내려 주는 곳. Istio에서는 istiod다.

정책을 바꿀 때는 **코드가 아니라 설정**을 바꾸고, 서비스는 다시 배포하지 않는다.

## 요청 경로

### 사이드카 주입

Istio는 istioctl이나 Helm으로 설치한다. 클러스터 안에서 돌던 IstioOperator 컨트롤러는 1.24에서 없어졌다.

```bash
# istioctl
curl -L https://istio.io/downloadIstio | sh -
istioctl install --set profile=default -y

# Helm
helm repo add istio https://istio-release.storage.googleapis.com/charts
helm install istio-base istio/base -n istio-system --create-namespace
helm install istiod istio/istiod -n istio-system --wait
```

설치 뒤 네임스페이스에 라벨을 붙이고 파드를 다시 띄우면, 배포 YAML에 없던 컨테이너가 파드에 생긴다.

```bash
kubectl label namespace default istio-injection=enabled
kubectl rollout restart deployment -n default
```

파드가 만들어질 때 API 서버는 istiod의 주입 웹훅(mutating webhook)에 파드 스펙을 보내고, istiod가 컨테이너 두 개를 끼워 넣는다.

- istio-init: 파드의 네트워크 네임스페이스에 iptables 규칙을 쓰고 끝나는 init 컨테이너
- istio-proxy: Envoy와 istio-agent가 도는 사이드카(sidecar). 파드가 사는 동안 같이 돈다.

아래 그림에서 파드 스펙이 웹훅을 지나며 무엇이 붙는지 본다.

<figure class="fig" data-figure="istio-inject">
  <figcaption>파드 스펙이 API 서버와 istiod 웹훅을 지나며 사이드카가 붙는 과정</figcaption>
</figure>

Envoy는 init 컨테이너가 아니라 앱 옆에서 계속 도는 컨테이너다. Istio 1.27부터는 쿠버네티스 네이티브 사이드카(`restartPolicy: Always`인 init 컨테이너)로 넣는 것이 기본이라, 앱보다 먼저 뜨고 나중에 내려간다. istio-cni 플러그인을 쓰면 iptables 규칙을 노드의 CNI 단계에서 써서 istio-init은 빠진다.

주입은 파드가 만들어질 때 한 번만 일어난다. 라벨만 붙이고 재시작하지 않으면 기존 파드에는 사이드카가 없고, Istio를 올린 뒤에도 파드를 다시 띄워야 새 버전 프록시가 들어간다. 주입이 안 된 것 같으면 `kubectl get pod -o jsonpath='{.spec.containers[*].name}'`부터 본다.

### iptables 가로채기

앱 코드는 `http://payments:8080`을 부를 뿐인데, 요청은 Envoy를 지나서 나간다. istio-init이 써 둔 iptables 규칙이 파드에서 나가는 TCP를 Envoy의 15001 포트로, 들어오는 TCP를 15006 포트로 돌리기 때문이다.

1. 앱이 payments로 요청을 보낸다.
2. 파드 A의 iptables가 이를 Envoy 15001로 돌린다.
3. Envoy가 목적지 파드를 직접 고르고, mTLS로 감싸 보낸다.
4. 파드 B의 iptables가 들어온 연결을 Envoy 15006으로 돌린다.
5. B의 Envoy가 TLS를 풀고 정책을 확인한 뒤, 같은 파드의 앱 8080으로 넘긴다.

두 장면에서 요청이 파드 A에서 나가는 길과 파드 B로 들어가는 길을 따라가 보자.

<figure class="fig" data-figure="istio-path">
  <figcaption>요청 하나가 파드 A의 앱에서 파드 B의 앱까지 가는 경로</figcaption>
</figure>

요청 하나가 프록시를 두 번 지난다. 앱끼리는 평문 HTTP로 말한 줄 알지만 노드 사이 구간은 암호화돼 있고, 재시도와 타임아웃도 보내는 쪽 Envoy가 처리한다.

Envoy는 Service의 가상 IP 대신 파드 IP를 직접 골라 보낸다. 그래서 부하 분산 방식도 kube-proxy가 아니라 Envoy 설정을 따른다. 응답이 이상하면 앱 로그만 보지 말고 양쪽 istio-proxy 로그를 같이 본다.

### istiod와 xDS

VirtualService 하나를 적용하면 몇 초 안에 수백 개 Envoy의 라우팅이 바뀐다. istiod가 쿠버네티스 API를 지켜보다가, 바뀐 설정을 xDS라는 gRPC 스트림(15012 포트)으로 각 Envoy에 밀어 넣는다.

istiod는 예전의 Pilot, Citadel, Galley를 하나로 합친 프로세스다(1.5부터). 하는 일은 셋이다.

- 설정 배포: Service, 엔드포인트, VirtualService 같은 리소스를 Envoy 설정으로 바꿔 내려보낸다.
- 인증서 발급: 파드의 istio-agent가 보낸 서명 요청(CSR)을 확인하고 서명하는 CA다.
- 사이드카 주입: 앞에서 본 웹훅이다.

세 장면에서 istiod가 무엇을 내려보내는지, istiod가 멈추면 요청은 어떻게 되는지 본다.

<figure class="fig" data-figure="istio-xds">
  <figcaption>istiod가 설정과 인증서를 내려보내는 길과 요청이 다니는 길</figcaption>
</figure>

istiod는 요청 경로에 없다. 멈춰도 Envoy들은 마지막으로 받은 설정으로 요청을 계속 나르고, 새 설정과 새 파드 반영, 인증서 갱신만 멈춘다.

그래서 istiod 장애는 전면 장애가 아니라 **변경이 반영되지 않는 장애**로 나타난다. 오래 가면 인증서를 갱신하지 못해 만료되므로, istiod는 레플리카를 둘 이상 둔다.

## 트래픽 관리

### VirtualService와 DestinationRule

reviews 서비스에 v1과 v2 파드가 같이 떠 있다. 쿠버네티스 Service만 있으면 요청은 두 버전에 섞여 간다. 특정 사용자만 v2로 보내려면 Istio 리소스 두 개를 쓴다.

- VirtualService: 요청을 **어디로** 보낼지 정한다. 경로, 헤더 같은 조건으로 목적지와 subset을 고른다.
- DestinationRule: 목적지에 **어떻게** 보낼지 정한다. subset을 파드 라벨로 정의하고, 부하 분산 방식과 연결 풀, 서킷 브레이커를 붙인다. 서비스 하나에 하나를 둔다.

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts: [reviews]
  http:
  - match:
    - headers:
        end-user:
          exact: jason
    route:
    - destination: { host: reviews, subset: v2 }
  - route:
    - destination: { host: reviews, subset: v1 }
---
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  subsets:
  - name: v1
    labels: { version: v1 }
  - name: v2
    labels: { version: v2 }
```

Envoy는 규칙을 위에서부터 맞춰 보고 처음 맞는 규칙을 쓴다. 조건은 헤더 말고 경로로도 걸고, 맞추는 방식은 셋이다.

- `exact`: 값이 정확히 같을 때
- `prefix`: 앞부분이 같을 때(`/api`는 `/api/orders`도 잡는다)
- `regex`: 정규식에 맞을 때

아래 그림에서 jason의 요청과 다른 사용자의 요청이 어디서 갈리는지 본다.

<figure class="fig" data-figure="istio-routing">
  <figcaption>헤더 조건으로 v1과 v2가 갈리는 자리</figcaption>
</figure>

갈림은 받는 쪽이 아니라 **보내는 쪽 Envoy**에서 일어난다. productpage의 사이드카가 규칙을 보고 v2 파드 IP를 골라 보낸다. 그래서 헤더로 나누려면 앞단 서비스가 받은 `end-user` 헤더를 다음 요청에 그대로 실어야 한다.

같은 일을 쿠버네티스 Gateway API의 HTTPRoute로도 적는다. Istio는 Gateway API를 앞으로 트래픽 관리의 기본 API로 삼겠다고 밝혔고, 시작하기 문서도 Gateway API로 바뀌어 VirtualService 쪽을 "legacy Istio APIs"로 부른다.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: reviews
spec:
  parentRefs:
  - { group: "", kind: Service, name: reviews, port: 9080 }
  rules:
  - matches:
    - headers:
      - { name: end-user, value: jason }
    backendRefs:
    - { name: reviews-v2, port: 9080 }
  - backendRefs:
    - { name: reviews-v1, port: 9080 }
```

HTTPRoute는 subset 대신 버전별 Service(reviews-v1, reviews-v2)를 가리킨다. 클러스터 밖에서 들어오는 입구도 Istio Gateway 대신 Gateway API의 Gateway(`gatewayClassName: istio`)로 만들면, Istio가 입구 프록시를 알아서 띄운다.

- 새로 시작하면 HTTPRoute로 적는다. ambient 모드의 waypoint는 Gateway API로 설정하고, 거기서 VirtualService는 아직 Alpha다.
- Gateway API가 Istio 기능을 아직 전부 담지는 못한다. 빠진 기능이 필요할 때만 VirtualService를 쓰고, 같은 서비스에 두 방식을 섞지 않는다.

### 카나리 배포

v2를 배포했는데 500을 내는 버그가 있다. 한 번에 전부 바꿨다면 모든 사용자가 겪고, 10%만 보냈다면 10%만 겪는다. VirtualService의 `weight`로 비율을 정한다.

```yaml
  http:
  - route:
    - destination: { host: reviews, subset: v1 }
      weight: 90
    - destination: { host: reviews, subset: v2 }
      weight: 10
```

쿠버네티스 Deployment만으로 9대 1을 맞추려면 파드 수로 나눠야 한다(v1 9개, v2 1개). weight는 파드 수와 상관없이 요청 비율로 나눈다.

데모에서 배포 방식을 바꿔 가며 v2를 배포해 본다. 같은 요청 40건 중 몇 건이 실패하는지 아래 칸을 지켜본다.

<figure class="fig" data-figure="istio-canary">
  <figcaption>버그 있는 v2를 한 번에 바꿀 때와 10%만 보낼 때</figcaption>
</figure>

전부 교체하면 40건이 모두 실패하고, 카나리 10%는 4건만 실패한다. 버그도 요청 수도 같고, 바뀐 것은 weight 하나다.

카나리 중에는 v2의 오류율과 지연을 v1과 나란히 보고, 괜찮으면 10, 25, 50, 100으로 올린다. Argo Rollouts나 Flagger는 이 weight를 지표에 따라 자동으로 바꾼다.

## 장애 대응

### 타임아웃과 재시도

결제 파드 하나가 가끔 응답을 수십 초씩 끌고, 그동안 주문 요청도 같이 기다린다. Istio는 HTTP 타임아웃이 기본으로 꺼져 있어서, 앱이나 프록시 어디에도 상한을 두지 않으면 끝까지 기다린다.

재시도는 기본으로 켜져 있다. 실패하면 두 번 더 보내고, 간격은 25ms 이상에서 Istio가 정한다. 둘 다 VirtualService에서 바꾼다.

```yaml
  http:
  - route:
    - destination: { host: payments }
    timeout: 2s
    retries:
      attempts: 2
      perTryTimeout: 500ms
      retryOn: 5xx,connect-failure,reset
```

- `timeout`: 재시도까지 합친 전체 상한
- `perTryTimeout`: 시도 한 번의 상한. 넘으면 그 시도를 끊고 다음 시도로 간다.

두 장면에서 느린 파드에 걸린 요청이 언제 끝나는지 견줘 본다.

<figure class="fig" data-figure="istio-retry">
  <figcaption>느린 파드에 걸린 요청 하나, 타임아웃이 없을 때와 시도마다 끊을 때</figcaption>
</figure>

상한이 없으면 3초를 다 기다리고, 500ms에 끊고 다시 보내면 다른 파드가 받아 650ms에 끝난다. 앞의 연쇄 장애에서 스레드가 묶이는 시간도 그만큼 줄어든다.

재시도에는 대가가 있다. 층마다 재시도를 걸면 맨 끝 서비스가 받는 요청이 곱해진다.

```text
A → B → C, 층마다 attempts 2 (시도 3번)
C가 받는 요청 = 3 × 3 = 9배
```

이미 힘든 C에 9배가 몰려 회복을 막는다. 재시도는 같은 요청을 다시 보내도 결과가 같은 요청(GET, 멱등한 PUT)에만 두고, 호출 사슬에서 한 층에만 건다. 기본값으로 켜진 재시도도 층이 깊으면 어느 층에서 끌지 먼저 정한다.

### 서킷 브레이커

결제 파드 둘 중 하나가 고장 나서 3초를 끌다가 503을 낸다. 그 파드로 간 요청이 3초씩 주문 서비스의 스레드를 붙잡는 동안, 멀쩡한 파드로 갈 요청까지 줄을 선다.

DestinationRule에 고장 난 파드를 빼는 규칙(outlier detection)을 둔다.

```yaml
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: payments
spec:
  host: payments
  trafficPolicy:
    connectionPool:
      http:
        http1MaxPendingRequests: 10
    outlierDetection:
      consecutive5xxErrors: 3
      baseEjectionTime: 30s
      maxEjectionPercent: 50
```

- `outlierDetection`: 5xx를 연달아 낸 파드를 부하 분산 대상에서 잠시 뺀다. 이 블록을 두면 필드 기본값은 5번 연속, 30초 제외, 한 번에 전체 파드의 10%까지다. 파드가 적은 서비스는 `maxEjectionPercent`를 같이 정해 둔다.
- `connectionPool`: 대기 요청의 상한. 넘치면 줄 서지 않고 바로 503을 돌려준다. 기본값은 사실상 무제한이다.

데모에서 파드 2를 고장 내고, 모드를 바꿔 가며 주문 서비스의 스레드 칸과 대기 줄을 지켜본다.

<figure class="fig" data-figure="istio-breaker">
  <figcaption>고장 난 결제 파드 하나가 주문 서비스의 스레드를 붙잡는 모습</figcaption>
</figure>

서킷 브레이커가 없으면 파드 2에 간 요청이 주황 칸으로 스레드를 붙잡고, 대기 줄이 계속 늘어난다. 있으면 파드 2가 503을 세 번 연달아 낸 순간 빠지고, 줄이 금방 빠진다. 요청량도 고장도 같고, **고장 난 파드에 계속 보내는지**만 다르다.

빠진 파드는 30초 뒤 다시 대상에 들어가고, 또 실패하면 더 오래 빠진다. 파드가 503을 내는지, 연결 풀이 넘쳐 Envoy가 503을 내는지는 Envoy 접근 로그의 응답 플래그(`UO`는 연결 풀 넘침, `URX`는 재시도 소진)로 가린다.

## 보안

메시 안의 서비스끼리는 앱을 고치지 않아도 암호화해 말한다. 양쪽 Envoy가 상호 TLS(mutual TLS)로 연결해 서로의 인증서를 확인한다.

- 인증서는 istiod가 서명한다. 파드의 istio-agent가 키를 만들고 서명 요청을 보내면, istiod가 확인한 뒤 서명해 돌려준다. agent는 만료 전에 알아서 갱신하고, Envoy에는 SDS로 넘긴다.
- 인증서에는 파드의 서비스 어카운트가 신원으로 들어간다(`cluster.local/ns/default/sa/orders`). IP가 아니라 이 신원으로 상대를 가린다.

받는 쪽이 평문도 받을지는 PeerAuthentication으로 정한다.

- `PERMISSIVE`: mTLS와 평문을 둘 다 받는다. 따로 정하지 않으면 이 모드다.
- `STRICT`: mTLS만 받는다. 사이드카가 없는 파드나 클러스터 밖에서 온 평문 요청은 끊는다.

세 장면에서 사이드카 없는 파드의 평문 요청이 모드마다 어떻게 되는지 본다.

<figure class="fig" data-figure="istio-mtls">
  <figcaption>PeerAuthentication 모드에 따라 평문 요청이 지나가거나 끊기는 자리</figcaption>
</figure>

PERMISSIVE는 사이드카를 차례로 붙이는 동안 통신이 끊기지 않게 하려는 모드다. 이 상태에서는 사이드카 없는 파드의 평문도 그대로 들어오므로, "메시에 넣으면 전부 암호화된다"는 반만 맞다. 이전이 끝나면 STRICT로 바꾼다.

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
```

루트 네임스페이스(istio-system)에 두면 메시 전체에 걸린다. 신원이 확인되면 누가 누구를 부를 수 있는지는 AuthorizationPolicy로 정한다.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: payments
  namespace: default
spec:
  selector:
    matchLabels: { app: payments }
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/orders"]
```

`principals` 조건은 STRICT와 같이 쓴다. 평문으로 온 요청에는 신원이 없어서, PERMISSIVE에서는 정책이 의도와 다르게 거절하거나 지나칠 수 있다.

## 관측

Istio를 붙이자마자 Kiali에 서비스 지도가 그려지고, Grafana에 서비스별 요청 수와 지연이 나온다. 앱은 아무것도 하지 않았다. 모든 요청이 Envoy를 지나니 Envoy가 요청마다 지표를 남긴다.

- `istio_requests_total`: 요청 수. 출발지, 목적지, 응답 코드 라벨이 붙는다.
- `istio_request_duration_milliseconds`: 지연 분포

예전에는 Mixer라는 별도 구성 요소가 이 일을 했지만 1.8에서 없어졌고, 지금은 Envoy가 직접 만든다. Prometheus는 각 파드의 15020 포트에서 지표를 긁어 간다.

분산 추적(distributed tracing)은 다르다. Envoy는 들어온 요청과 나간 요청이 같은 요청인지 모른다. 앱이 받은 요청의 추적 헤더(`traceparent`, `x-request-id`, `x-b3-*`)를 다음 요청에 옮겨 실어야 구간들이 한 줄로 이어진다.

두 장면에서 헤더를 옮겨 실을 때와 빠뜨릴 때 추적 화면이 어떻게 달라지는지 본다.

<figure class="fig" data-figure="istio-observe">
  <figcaption>추적 헤더 전달에 따라 이어지거나 끊기는 추적</figcaption>
</figure>

지표는 헤더와 상관없이 쌓이지만, 추적은 앱 하나만 헤더를 빠뜨려도 거기서 끊긴다. OpenTelemetry SDK를 쓰면 이 전달을 대신해 주므로, 추적이 끊긴 자리가 보이면 그 서비스의 계측부터 본다.

`samples/addons`의 Prometheus, Grafana, Jaeger, Kiali는 보여 주기용 설정이다. 운영에서는 따로 설치한 모니터링이 Envoy 지표를 가져가게 한다.

## 비용

### 프록시 자원

파드 30개에 사이드카를 붙이면 프록시도 30개다. 프록시마다 CPU와 메모리 request를 잡아야 하고, 각 파드가 가장 바쁠 때를 기준으로 잡아서 대부분은 놀고 있다.

공식 문서가 밝힌 프록시 하나의 사용량은 이렇다.

| 프록시 | vCPU | 메모리 | 몇 개 |
|---|---|---|---|
| 사이드카 Envoy | 0.20 | 60MB | 파드마다 |
| ztunnel | 0.06 | 12MB | 노드마다 |
| waypoint | 0.25 | 60MB | 필요한 네임스페이스나 서비스마다 |

Istio 1.24, 초당 1000요청(요청당 1KB), 워커 스레드 2개에서 잰 공식 측정값이다.

데모에서 모드를 바꿔 가며 파드를 30개로 늘려 보자. 노드 3대 위에 프록시가 몇 개 생기고 메모리가 얼마나 쌓이는지 본다.

<figure class="fig" data-figure="istio-cost">
  <figcaption>파드가 늘 때 프록시 수와 메모리 (공식 측정값으로 계산한 대략값)</figcaption>
</figure>

사이드카는 파드 30개에 프록시 30개, 메모리 1.8GB다. ambient는 ztunnel 3개(36MB)에 waypoint 하나(60MB)를 더해 96MB다. 처리하는 요청은 같고, 프록시를 파드마다 두는지 노드마다 두는지만 다르다.

사이드카를 쓴다면 istio-proxy의 request를 실제 사용량에 맞추고, Sidecar 리소스로 프록시가 받을 설정 범위를 필요한 서비스로 좁힌다.

### 프록시 홉과 지연

메시를 붙인 뒤 p99 지연이 늘었다. 요청 하나가 지나는 프록시가 늘었기 때문이다.

- 메시 없음: 앱에서 앱으로 바로 간다.
- 사이드카: Envoy를 두 번 지난다. 둘 다 HTTP를 해석하는 L7 처리다.
- ambient L4: ztunnel을 두 번 지난다. 둘 다 TCP 연결만 다루는 L4 처리다.
- ambient L7: ztunnel 사이에 waypoint가 끼어 L7 처리를 한 번 한다.

네 레인에서 요청 하나가 지나는 프록시의 종류와 수를 견줘 보자.

<figure class="fig" data-figure="istio-latency">
  <figcaption>데이터 플레인 모드별 요청 하나가 지나는 프록시 (길이는 모양을 보여 주는 대략값)</figcaption>
</figure>

공식 문서도 L7 처리가 L4 처리보다 훨씬 무겁다고 적는다. 지연이 민감하면 L7 기능이 정말 필요한 서비스만 L7 프록시를 지나게 한다.

실제 값은 하드웨어와 설정에 따라 달라서, 공식 성능 문서의 P90, P99 그래프를 기준으로 삼고 자기 환경에서 부하 테스트로 잰다.

## ambient 모드

### ztunnel과 waypoint

사이드카는 붙일 때 파드를 다시 띄우고, Istio를 올릴 때도 모든 파드를 다시 띄운다. ambient 모드는 프록시를 파드 밖으로 뺀다. Istio 1.24(2024년 11월)에 GA가 됐다.

- ztunnel: 노드마다 하나씩 도는 L4 프록시. mTLS, L4 인가, TCP 지표를 맡는다. 노드 사이는 HBONE(HTTP CONNECT 기반 터널, 15008 포트)으로 보낸다.
- waypoint: L7 기능이 필요할 때만 두는 Envoy. 네임스페이스나 서비스 단위의 Deployment로 뜨고, HTTP 라우팅과 L7 인가를 맡는다.

파드 안에서 가로채는 일은 istio-cni 노드 에이전트가 한다. 파드의 네트워크 네임스페이스에 들어가 리다이렉트 규칙을 쓰고, ztunnel이 그 네임스페이스 안에 15001, 15006, 15008 리스너를 연다.

```bash
kubectl label namespace default istio.io/dataplane-mode=ambient
istioctl waypoint apply -n default
kubectl label namespace default istio.io/use-waypoint=waypoint
```

라벨만 붙이면 되고 파드를 다시 띄우지 않는다. 두 장면에서 ztunnel만 있을 때와 waypoint를 붙였을 때 요청이 지나는 길을 비교한다.

<figure class="fig" data-figure="istio-ambient">
  <figcaption>ambient 모드에서 요청이 ztunnel과 waypoint를 지나는 길</figcaption>
</figure>

ztunnel만으로 mTLS와 L4 인가, 기본 지표가 된다. 헤더로 트래픽을 나누거나 L7 인가가 필요한 곳에만 waypoint를 붙인다.

한 메시 안에서 두 모드를 섞을 수 있어서, 네임스페이스마다 고른다.

- ambient가 맞는 경우: 목적이 mTLS와 기본 지표부터일 때, 파드가 많아 사이드카 비용이 클 때, 파드 재시작 없이 메시를 붙이고 올리고 싶을 때
- 사이드카가 맞는 경우: VirtualService로 짠 설정이 많을 때(ambient에서는 Alpha), 파드마다 다른 프록시 설정이 필요할 때

새로 메시를 들인다면 ambient로 mTLS부터 켜고, L7이 필요한 서비스를 찾아 waypoint를 하나씩 붙이는 순서로 간다.

## 정리

| | 하는 일 | 기억할 점 |
|---|---|---|
| 사이드카 | 파드마다 Envoy를 붙여 요청을 가로챈다 | 주입과 업그레이드에 파드 재시작. 파드 수만큼 자원 |
| istiod | 설정(xDS)과 인증서를 내려 준다 | 요청 경로에 없다. 멈추면 변경만 멈춘다 |
| VirtualService, DestinationRule | 어디로, 어떻게 보낼지 | 새로 쓴다면 Gateway API HTTPRoute |
| 카나리 | weight로 요청 비율을 나눈다 | 파드 수와 상관없이 나뉜다 |
| 타임아웃, 재시도 | 기다림 상한과 다시 보내기 | 타임아웃은 기본으로 꺼짐. 재시도는 층마다 곱해진다 |
| 서킷 브레이커 | 5xx를 연달아 낸 파드를 뺀다 | 뺄 수 있는 비율 상한(기본 10%)을 같이 정한다 |
| mTLS | 서비스 어카운트 신원으로 서로 확인 | 기본 PERMISSIVE는 평문도 받는다. STRICT로 |
| 관측 | Envoy가 지표를 남긴다 | 추적은 앱이 헤더를 옮겨 실어야 이어진다 |
| ambient | 노드의 ztunnel, 필요할 때 waypoint | 1.24에서 GA. 라벨만 붙이고 재시작 없음 |
