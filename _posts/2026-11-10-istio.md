서비스끼리 부르는 호출에는 타임아웃, 재시도, 고장 난 파드 제외, 암호화가 필요하다. 이를 앱 코드에 넣으면 언어마다 라이브러리가 다르고, 값 하나를 바꿀 때도 모든 서비스를 고쳐 다시 배포한다. 서비스 메시(service mesh)는 이 기능을 앱 밖, 요청 경로 위의 프록시(요청을 대신 받아 전달하는 중계 프로그램)에 둔다.

## 요청 가로채기

앱은 `http://payments:8080`을 부를 뿐이고 프록시 설정도 없다. 그런데 요청은 같은 파드의 Envoy를 지나서 나간다. Envoy는 Istio가 앱 컨테이너 옆에 사이드카(sidecar)로 넣는 프록시다.

파드 안의 컨테이너들은 네트워크 네임스페이스(network namespace) 하나를 같이 쓰는데, 네트워크 네임스페이스는 IP, 라우팅 표, 방화벽 규칙을 따로 갖는 리눅스의 격리 단위다. 그래서 이 네임스페이스에 iptables 규칙을 쓰면 앱의 소켓도 그 규칙을 따른다.

규칙은 파드가 뜰 때 istio-init 컨테이너(또는 노드의 istio-cni 플러그인)가 주소를 바꾸는 nat 표에 쓴다. Istio 소스의 테스트 기대 출력(`iptables-save`)에서 사이드카 기본값의 주요 줄만 추렸다.

```text
-A PREROUTING -p tcp -j ISTIO_INBOUND
-A ISTIO_INBOUND -p tcp --dport 15008 -j RETURN
-A ISTIO_INBOUND -p tcp --dport 15090 -j RETURN
-A ISTIO_INBOUND -p tcp --dport 15021 -j RETURN
-A ISTIO_INBOUND -p tcp --dport 15020 -j RETURN
-A ISTIO_INBOUND -p tcp -j ISTIO_IN_REDIRECT
-A ISTIO_IN_REDIRECT -p tcp -j REDIRECT --to-ports 15006
-A OUTPUT -j ISTIO_OUTPUT
-A ISTIO_OUTPUT -m owner --uid-owner 1337 -j RETURN
-A ISTIO_OUTPUT -d 127.0.0.1/32 -j RETURN
-A ISTIO_OUTPUT -j ISTIO_REDIRECT
-A ISTIO_REDIRECT -p tcp -j REDIRECT --to-ports 15001
```

- 나가는 TCP: `OUTPUT`에서 `ISTIO_OUTPUT`으로 가고, 마지막 줄에서 Envoy의 15001 포트로 돌려진다.
- 들어오는 TCP: `PREROUTING`에서 `ISTIO_INBOUND`로 가고, Envoy의 15006 포트로 돌려진다. 15008(ambient 절에서 볼 HBONE 터널), 15090(Envoy 지표), 15021(헬스 체크), 15020(병합 지표) 같은 Istio 자신의 포트는 그대로 둔다.
- Envoy가 내보내는 연결: Envoy는 UID 1337로 돌고, `--uid-owner 1337` 줄이 이 연결을 그냥 내보낸다. 이 줄이 없으면 Envoy가 보낸 요청이 다시 Envoy로 돌아와 끝없이 돈다.

`REDIRECT`는 목적지를 자기 포트로 바꿔 쓰므로, Envoy가 받은 연결의 목적지는 `127.0.0.1:15001`로 보인다. 커널의 연결 추적(conntrack)은 바꾸기 전 주소를 기억하고 있어서, Envoy는 소켓 옵션 `SO_ORIGINAL_DST`로 원래 목적지(`payments`의 IP와 8080)를 읽어 온다.

아래 그림처럼 요청 하나는 보내는 파드와 받는 파드에서 Envoy를 한 번씩, 모두 두 번 지난다.

</figure>

리스너는 포트 하나에서 연결을 받는 Envoy 설정 단위다. 15001 리스너(virtualOutbound)는 직접 처리하지 않고, 원래 목적지 포트에 맞는 리스너로 연결을 넘긴다. 예제 앱 Bookinfo의 파드에서 `istioctl proxy-config listeners`로 보면 이렇다.

```text
ADDRESS   PORT   MATCH             DESTINATION
0.0.0.0   15001  ALL               PassthroughCluster
0.0.0.0   15006  Addr: 0.0.0.0/0   InboundPassthroughClusterIpv4
0.0.0.0   9080   App: HTTP         Route: 9080
```

가로채기는 TCP에만 걸린다. 또 Envoy가 뜨기 전에 앱이 요청을 보내면 15001에서 연결이 거부된다. 1.27부터는 Envoy를 쿠버네티스 네이티브 사이드카(앱보다 먼저 떠서 끝까지 같이 도는 init 컨테이너)로 넣는 것이 기본이라 이 틈이 없다.

## 설정 배포 (xDS)

Envoy는 쿠버네티스를 모른다. 15001로 들어온 요청이 `payments`로 가야 한다는 것, `payments` 뒤에 어떤 파드 IP가 있는지는 istiod가 알려 준다. istiod는 API 서버에서 Service, EndpointSlice, VirtualService(라우팅, 타임아웃, 재시도 규칙), DestinationRule(목적지별 부하 분산, 장애 파드 제외 규칙)을 지켜보다가 Envoy 설정으로 바꿔 내려보낸다. 이 설정 API를 묶어 xDS라고 부른다.

- LDS(Listener): 어느 포트에서 무엇을 받을지. 앞의 15001, 15006, 9080 리스너다.
- RDS(Route): 호스트와 경로로 어느 클러스터에 보낼지. 타임아웃과 재시도가 여기 붙는다.
- CDS(Cluster): 목적지 묶음 하나. `outbound|9080||reviews.default.svc.cluster.local` 같은 이름이다.
- EDS(Endpoint): 클러스터 뒤의 실제 파드 IP 목록
- SDS(Secret): mTLS에 쓸 인증서와 키

istiod는 이 다섯 가지를 연결 하나로 계속 주고받는 gRPC 스트림 하나(ADS, 15012 포트)로 보낸다. 스트림 하나로 묶는 이유는 순서다. 라우트가 아직 모르는 클러스터를 가리키면 Envoy는 그 요청을 503으로 돌려보내므로, Envoy의 xDS 규약은 새 설정을 놓을 때 CDS, EDS, LDS, RDS 순서로 보내고 쓰지 않게 된 클러스터는 맨 나중에 지우라고 정한다(make before break).

설정이 바뀔 때마다 바로 보내지도 않는다. istiod는 변경을 받은 뒤 100ms를 기다리고, 그사이 또 바뀌면 다시 기다린다(`PILOT_DEBOUNCE_AFTER`). 배포 중처럼 변경이 계속 들어와도 10초(`PILOT_DEBOUNCE_MAX`)가 차면 그때까지 쌓인 것을 한 번에 보낸다. 각 Envoy가 받은 상태는 `istioctl proxy-status`로 확인한다.

```text
NAME                                     CDS     LDS     EDS     RDS     ISTIOD
productpage-v1-6987489c74-nc7tj.default  SYNCED  SYNCED  SYNCED  SYNCED  istiod-6cf8d4f9cb-wm7x6
```

</figure>

istiod는 요청 경로에 없다. 연결이 끊겨도 Envoy는 마지막으로 받은 설정을 다시 연결될 때까지 그대로 쓴다. istiod 장애는 요청이 끊기는 장애가 아니라 **새 파드와 새 설정이 반영되지 않는 장애**로 나타난다.

대가는 Envoy의 메모리다. 기본으로 istiod는 메시 안 모든 서비스의 리스너, 라우트, 클러스터를 모든 Envoy에 보낸다. 공식 성능 문서도 프록시 메모리는 들고 있는 설정의 양에 따라 늘어난다고 적는다. 서비스가 많으면 Sidecar 리소스의 `egress.hosts`로 실제로 부르는 서비스만 받게 좁힌다.

## 엔드포인트 선택과 장애 대응

EDS로 파드 IP 목록을 받았으므로, Envoy는 Service의 가상 IP와 kube-proxy를 거치지 않고 파드를 직접 고른다. Istio의 기본 부하 분산은 `LEAST_REQUEST`다. 가중치가 같으면 Envoy는 파드 둘을 무작위로 뽑아 처리 중인 요청이 적은 쪽에 보낸다(power of two choices). 전체를 훑지 않고도 전체를 훑은 것에 가깝게 고르고, 여러 프록시가 같은 파드로 한꺼번에 몰리지 않는다.

### 타임아웃과 재시도

Envoy 라우트의 타임아웃은 따로 정하지 않으면 15초지만, Istio는 HTTP 타임아웃을 꺼 둔 채로 내려보낸다. 앱이나 VirtualService 어디에도 상한이 없으면 느린 파드의 응답을 끝까지 기다린다.

재시도는 기본으로 켜져 있다. Istio 소스(`retry.go`)에 적힌 기본값은 이렇다.

```text
num_retries: 2
retry_on: connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes
retry_host_predicate: previous_hosts
```

- 다시 보내는 경우: 연결 실패, HTTP/2 스트림 거부, gRPC unavailable처럼 요청이 앱에 닿기 전에 실패한 경우다. 앱이 돌려준 503은 기본으로 다시 보내지 않는다.
- 다시 보낼 곳: `previous_hosts` 때문에 이미 실패한 파드를 빼고 고른다.
- 간격: 25ms를 기준으로 한 무작위 지수 백오프다. 첫 재시도는 0~24ms, 두 번째는 0~74ms 사이에서 기다린다.

느린 파드를 끊으려면 VirtualService에 상한을 둔다.

```yaml
  http:
  - route:
    - destination: { host: payments }
    timeout: 2s
    retries:
      attempts: 2
      perTryTimeout: 500ms
      retryOn: 5xx,connect-failure,reset
```

- `timeout`: 재시도까지 합친 전체 상한. 넘으면 Envoy가 504를 돌려준다.
- `perTryTimeout`: 시도 한 번의 상한. 넘으면 그 시도를 끊고 다른 파드로 다시 보낸다.

  <figcaption>느린 파드에 걸린 요청 하나, 타임아웃이 없을 때와 시도마다 끊을 때</figcaption>
</figure>

재시도는 층마다 곱해진다. A가 B를, B가 C를 부르고 층마다 재시도 2번(시도 3번)을 두면 C가 받는 요청은 최대 9배가 된다.

```text
A → B → C, 층마다 attempts 2
C가 받는 요청 = 3 × 3 = 9배
```

이미 힘든 C에 9배가 몰리면 회복이 늦어진다. `5xx` 재시도는 같은 요청을 다시 보내도 결과가 같은 요청(GET, 멱등한 PUT)에만 두고, 호출 사슬에서 한 층에만 건다.

### 이상 엔드포인트 제외

재시도는 요청 하나를 구할 뿐, 고장 난 파드로 가는 다음 요청은 막지 않는다. 파드 둘 중 하나가 3초를 끌다가 503을 내면 요청의 절반이 계속 3초씩 기다린다. DestinationRule의 이상 감지(outlier detection)는 Envoy가 파드마다 연속 실패를 세다가 기준을 넘으면 그 파드를 부하 분산 대상에서 잠시 뺀다.

```yaml
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 3
      baseEjectionTime: 30s
      maxEjectionPercent: 50
```

적지 않은 필드의 기본값은 이렇다.

- `consecutive5xxErrors: 5`: 5xx를 5번 연달아 내면 뺀다. 세는 일은 응답이 올 때마다 바로 한다.
- `interval: 10s`: 빠진 파드를 되돌릴지 살피는 주기
- `baseEjectionTime: 30s`: 빠지는 시간은 30초에 지금까지 빠진 횟수를 곱한다. 두 번째는 60초, 세 번째는 90초다.
- `maxEjectionPercent: 10`: 한 번에 뺄 수 있는 파드 비율. 파드가 적은 서비스는 직접 정한다.

아래 데모는 결제 파드 2가 3초를 끌다 503을 낼 때 주문 서비스의 스레드 6개와 대기 줄을 보여 준다. 두 모드에서 각각 파드 2 고장 내기를 눌러 대기 건수를 비교한다.

<figure class="fig" data-figure="istio-breaker">
  <figcaption>고장 난 결제 파드 하나가 주문 서비스의 스레드를 붙잡는 모습</figcaption>
</figure>

이상 감지가 없으면 파드 2로 간 요청이 3초씩 스레드를 붙잡아 대기 줄이 계속 는다. 있으면 503이 세 번 연달아 나온 순간 파드 2가 빠지고 줄이 금방 빠진다. 데모에서 정상 파드는 0.3초, 파드 2는 3초 동안 스레드를 쥔다. 반씩 나눠 보내면 스레드 6개가 초당 3.6건만 끝내 초당 5건씩 오는 요청이 쌓이고, 파드 2를 빼면 같은 스레드로 초당 20건을 끝낸다.

지금 빠져 있는 파드는 `istioctl proxy-config endpoints`의 `OUTLIER CHECK` 열에 나온다.

연속 실패만 센다는 한계가 있다. Istio API 문서의 예처럼 요청을 하나 걸러 실패하는 파드는 5번 연속을 영영 채우지 못한다. 이런 파드는 `failurePercentageThreshold`(기본 85%)로 실패 비율을 보고 뺀다.

## 상호 TLS

여기까지 Envoy끼리 주고받은 요청이 진짜 상대 Envoy에서 왔는지는 아직 확인하지 않았다. 상호 TLS(mutual TLS)는 양쪽이 서로 인증서를 보이고 확인하는 TLS다. 인증서가 파드에 들어오는 순서는 이렇다.

1. 파드 안 istio-agent가 개인 키를 만들고, 서명 요청(CSR)을 파드의 신원 증명인 서비스 어카운트 토큰과 함께 istiod(15012)에 보낸다.
2. istiod는 토큰이 진짜인지 API 서버에 묻고, 맞으면 CSR에 서명해 돌려준다.
3. Envoy는 같은 컨테이너의 istio-agent에게 SDS로 인증서와 키를 받는다.

개인 키는 파드 밖으로 나가지 않는다. 인증서에는 IP 대신 `spiffe://cluster.local/ns/default/sa/orders` 같은 서비스 어카운트 신원이 들어가고, 받는 쪽은 이 신원으로 상대를 가린다.

수명과 갱신 기본값은 이렇다.

- 워크로드 인증서: 24시간(`SECRET_TTL`)
- 갱신 시점: 수명의 50%(`SECRET_GRACE_PERIOD_RATIO=0.5`), 약 12시간 뒤. 프록시 수천 개가 한꺼번에 갱신하지 않게 ±1%(24시간 기준 약 15분)를 흔든다.
- istiod가 직접 만든 루트 인증서: 10년

istiod가 12시간 넘게 멈추면 갱신 요청이 실패하기 시작하고, 24시간이 지나면 인증서가 만료돼 mTLS 연결이 끊긴다. 하루를 넘기는 istiod 장애는 요청 경로까지 번진다. istiod를 레플리카 둘 이상으로 두는 이유다.

받는 쪽 15006 리스너는 연결 조건마다 처리 단계 묶음(필터 체인)을 따로 두고, 연결의 첫 바이트를 보는 TLS 검사기(tls_inspector)로 어느 체인에 보낼지 가른다. 평문 연결은 평문용 체인으로 간다.

메시 안의 Envoy는 TLS 핸드셰이크에 `istio-peer-exchange`, `istio` 같은 ALPN(TLS 핸드셰이크에서 쓸 프로토콜 이름을 알리는 확장) 값을 실어 보내고, 이 값이 맞으면 mTLS 체인이 연결을 받는다.

PeerAuthentication 모드마다 두는 체인이 다르다.

- `PERMISSIVE`: mTLS 체인과 평문 체인을 둘 다 둔다. 따로 정하지 않으면 이 모드다.
- `STRICT`: 평문 체인이 없다. 사이드카 없는 파드가 보낸 평문 연결은 맞는 체인이 없어 끊긴다.

  <figcaption>PeerAuthentication 모드에 따라 평문 요청이 지나가거나 끊기는 자리</figcaption>
</figure>

PERMISSIVE는 사이드카를 차례로 붙이는 동안 통신을 끊지 않으려는 모드다. 이 상태에서는 평문도 그대로 들어오고, 평문 요청에는 신원이 없어서 AuthorizationPolicy의 `principals`(보낸 쪽 인증서의 서비스 어카운트 신원) 조건도 기대대로 걸리지 않는다. 이전이 끝나면 루트 네임스페이스(istio-system)에 STRICT를 둔다.

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: istio-system }
spec:
  mtls: { mode: STRICT }
```

## 프록시 비용과 ambient

공식 성능 문서가 밝힌 프록시 하나의 사용량은 이렇다.

| 프록시 | vCPU | 메모리 | 개수 |
|---|---|---|---|
| 사이드카 Envoy | 0.20 | 60MB | 파드마다 |
| ztunnel | 0.06 | 12MB | 노드마다 |
| waypoint | 0.25 | 60MB | 필요한 곳마다 |

Istio 1.24, 초당 1000요청(요청당 1KB), 워커 스레드 2개에서 잰 공식 측정값이다.

요청이 적은 파드도 프록시를 띄워 두므로 이 비용은 요청량이 아니라 파드 수를 따라 는다. 지연도 늘어난다. 요청 하나가 L7 프록시(HTTP 요청을 열어 경로와 헤더까지 보는 프록시)를 두 번 지난다.

ambient 모드는 프록시를 파드 밖으로 빼서 일을 둘로 나눈다.

- ztunnel: 노드마다 하나 도는 L4 프록시. HTTP를 열지 않고 TCP 연결 단위로만 다루며, mTLS, L4 인가, TCP 지표를 맡는다.
- waypoint: HTTP 기능이 필요한 곳에만 두는 Envoy. 네임스페이스나 서비스 단위로 뜬다.

아래 데모에서 사이드카와 ambient를 골라 파드 30개 띄우기를 누르면 노드 3대 위의 프록시 수와 메모리가 비교된다.

<figure class="fig" data-figure="istio-cost">
  <figcaption>파드가 늘 때 프록시 수와 메모리 (공식 측정값으로 계산한 대략값)</figcaption>
</figure>

사이드카는 파드 30개에 프록시 30개, 메모리 약 1.8GB다. ambient는 ztunnel 3개(36MB)와 waypoint 하나(60MB)로 96MB다. 사이드카 메모리는 파드 수를, ambient 메모리는 노드 수를 따라가므로 노드당 파드가 많을수록 격차가 벌어진다.

파드는 그대로 둔 채 가로채기 자리만 바꾼다. 노드의 istio-cni 에이전트가 파드의 네트워크 네임스페이스에 들어가 리다이렉트 규칙을 쓰고, 그 네임스페이스의 파일 디스크립터를 유닉스 소켓으로 ztunnel에 넘긴다. ztunnel은 그 네임스페이스 안에 리스너를 연다.

- 15001: 파드에서 나가는 TCP
- 15006: 파드로 들어오는 평문
- 15008: 파드로 들어오는 HBONE

이미 떠 있는 파드도 이렇게 메시에 들어가므로 사이드카 주입처럼 파드를 다시 띄우지 않는다. 노드 사이는 HBONE으로 보낸다. HBONE은 mTLS 위의 HTTP/2 연결에서 HTTP CONNECT로 터널을 여는 방식이라, 연결 하나에 여러 요청 스트림을 싣고 앱 요청에 헤더를 덧붙이지 않는다.

<figure class="fig" data-figure="istio-ambient">
  <figcaption>ambient 모드에서 요청이 ztunnel과 waypoint를 지나는 길</figcaption>
</figure>

ztunnel은 HTTP를 해석하지 않는다. 앞에서 다룬 HTTP 타임아웃, 재시도, 헤더 라우팅은 waypoint를 붙인 서비스에서만 동작한다. 대신 waypoint를 붙여도 요청 하나가 지나는 L7 프록시는 사이드카의 두 번에서 한 번으로 준다. mTLS만 필요하면 ztunnel로 충분하고, HTTP 정책이 필요한 서비스에만 waypoint를 붙인다.

## 정리

- 가로채기: iptables가 나가는 TCP를 15001, 들어오는 TCP를 15006으로 돌린다. Envoy(UID 1337)는 뺀다.
- 설정 배포: istiod가 LDS, RDS, CDS, EDS, SDS를 ADS 하나로 보낸다. 끊겨도 Envoy는 마지막 설정을 쓴다.
- 타임아웃과 재시도: 타임아웃은 꺼져 있고, 재시도 2번은 앱의 503을 다시 보내지 않으며 층마다 곱해진다.
- 이상 감지: 5xx 5번 연속이면 30초 곱하기 횟수만큼 빼고, 최대 10%까지다. 번갈아 실패하는 파드는 못 잡는다.
- mTLS: 24시간 인증서를 12시간에 갱신한다. 기본 PERMISSIVE는 평문도 받는다.
- 비용과 ambient: 사이드카는 파드마다 60MB다. ambient는 노드의 ztunnel로 재시작 없이 붙고, HTTP 정책은 waypoint에서만 걸린다.
