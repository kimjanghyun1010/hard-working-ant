## 요청 경로

브라우저에서 `https://shop.example.com/api/orders`를 부르면 응답은 파드 하나가 만든다. 그 파드의 IP는 배포할 때마다 바뀌고, 파드는 노드 여러 대에 흩어져 있다. 그래도 요청은 매번 살아 있는 파드를 찾아간다.

요청은 다섯 구간을 지나며 목적지 주소를 몇 번 바꾼다.

1. DNS가 도메인을 LB IP로 바꾼다.
2. 라우터가 LB IP를 맡은 노드로 보낸다.
3. 노드 커널의 Service 규칙이 LB IP를 Ingress 컨트롤러 파드 IP로 바꾼다.
4. Ingress 컨트롤러가 호스트와 경로를 보고 보낼 파드를 고른다.
5. 파드 네트워크가 노드를 건너 그 파드에 넘긴다.

아래 그림에서 장면마다 맨 아래 목적지 주소가 어떻게 바뀌는지 본다.

<figure class="fig" data-figure="k8s-network-path">
  <figcaption>외부 요청 하나가 파드까지 가는 다섯 구간</figcaption>
</figure>

목적지는 도메인, LB IP, Ingress 파드 IP, 앱 파드 IP 순으로 바뀐다. 어느 구간이 고장 나도 겉으로는 똑같이 "연결이 안 된다"로 보여서, 장애가 나면 이 순서대로 한 구간씩 짚는다.

## 파드 네트워크

### 파드 안 통신

로그 수집 사이드카가 같은 파드의 앱을 `localhost:8080`으로 부른다. 컨테이너는 둘인데 IP는 하나다.

파드는 네트워크 네임스페이스(network namespace) 하나를 가지고, 그 안의 컨테이너들이 이를 같이 쓴다. 그래서 IP, 포트, `lo` 장치가 전부 한 벌이다. 두 장면에서 같은 포트를 두 번째로 열려는 순간을 지켜보자.

<figure class="fig" data-figure="k8s-network-pod-local">
  <figcaption>한 파드의 컨테이너가 나눠 쓰는 네트워크</figcaption>
</figure>

같은 파드끼리는 localhost로 바로 부르니 빠르고 설정도 필요 없다. 대신 포트까지 나눠 쓰므로 8080을 여는 컨테이너 둘을 한 파드에 넣을 수 없다. 사이드카를 붙일 때는 앱과 포트가 겹치지 않는지부터 본다.

### 파드 간 통신

노드 1의 파드가 노드 2의 파드를 `10.244.2.7`로 부르면, 받는 쪽에도 출발 주소 `10.244.1.5`가 그대로 찍힌다. 중간에 주소를 바꾸는 장비가 없다.

쿠버네티스 네트워크 모델은 두 가지를 약속한다.

- 파드마다 클러스터 전체에서 겹치지 않는 IP를 하나씩 받는다.
- 파드는 같은 노드든 다른 노드든 NAT 없이 서로 직접 통신한다.

쿠버네티스는 약속만 정하고, 지키는 일은 CNI(Container Network Interface) 플러그인이 맡는다. 플러그인은 파드마다 veth 쌍을 만들어 노드 커널에 잇고, 다른 노드의 파드 대역으로 가는 길을 깐다. 두 장면에서 패킷이 지나는 장치를 따라가 보자.

<figure class="fig" data-figure="k8s-network-pod-to-pod">
  <figcaption>같은 노드와 다른 노드의 파드 간 통신</figcaption>
</figure>

같은 노드면 노드 커널에서 바로 옆 파드로 넘어가고, 다른 노드면 노드 네트워크를 한 번 건넌다. 건너는 방법은 플러그인과 설정마다 다르다. 파드 패킷을 노드 주소로 한 번 더 감싸는 터널 방식이 있고, 라우팅 테이블에 경로를 넣어 그대로 보내는 방식이 있다.

파드 사이 통신이 안 되면 Service보다 먼저 CNI 에이전트가 노드마다 떠 있는지 본다.

## Service

### 가상 IP

파드를 재배포했더니, 예전 파드 IP를 설정 파일에 적어 둔 서비스의 호출이 전부 실패한다. 파드는 다시 뜰 때마다 새 IP를 받는다.

Service는 파드 앞에 바뀌지 않는 이름과 IP를 하나 세운다. 뒤의 파드는 이름이 아니라 레이블(label)로 고르고, 파드가 바뀌면 엔드포인트 목록(EndpointSlice)만 고친다. 부르는 쪽은 평범한 호스트 이름과 포트만 알면 된다.

DNS가 파드 IP를 바로 돌려주면 되지 않나 싶지만, TTL을 지키지 않고 조회 결과를 오래 붙잡는 DNS 구현이 많다. 그래서 쿠버네티스는 바뀌지 않는 가상 IP를 하나 두고, 그 IP로 온 패킷의 목적지를 커널에서 바꾼다.

모드를 바꿔 가며 파드 재시작 버튼을 누르고, 오른쪽 위 실패 건수를 지켜본다.

<figure class="fig" data-figure="k8s-network-vip">
  <figcaption>파드가 다시 뜰 때 파드 IP와 Service로 부른 요청</figcaption>
</figure>

파드 IP로 부르면 새 파드가 뜬 뒤에도 옛 IP로 보내 실패가 계속 쌓인다. Service로 부르면 엔드포인트가 잠시 둘로 줄었다가 새 파드가 붙고, 요청은 남은 파드로 이어진다. 두 모드에서 바뀐 것은 부르는 주소 하나다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api-svc
spec:
  selector:
    app: api            # 이 레이블이 붙은 파드로 보낸다
  ports:
    - name: http        # 포트가 둘 이상이면 이름이 필요하다
      port: 80
      targetPort: 8080
```

- `port`: Service IP에서 받는 포트
- `targetPort`: 파드에서 실제로 열려 있는 포트

둘이 같아도 되지만 하나로 합쳐지지는 않는다. 다른 서비스를 부르는 주소는 파드 IP가 아니라 Service 이름으로 적는다.

### kube-proxy와 iptables

Service IP `10.96.0.20`에 `ping`을 보내면 응답이 없는데, `curl 10.96.0.20`은 된다. 그 IP를 가진 장치는 어디에도 없고 포트별 규칙만 있기 때문이다.

kube-proxy는 노드마다 하나씩 돌며 API 서버의 Service와 EndpointSlice를 지켜보고, 커널 netfilter의 nat 테이블에 규칙을 깐다. 패킷을 나르는 건 kube-proxy가 아니라 커널이다. 규칙은 세 단으로 이어진다.

- `KUBE-SERVICES`: Service IP와 포트마다 한 줄. 맞는 줄에서 그 Service의 체인으로 넘긴다.
- `KUBE-SVC-*`: 엔드포인트 수만큼 갈래가 있고, 확률로 하나를 고른다.
- `KUBE-SEP-*`: 목적지를 파드 IP로 바꾼다(DNAT).

세 장면에서 연결이 바뀔 때 고르는 갈래가 어떻게 달라지는지 본다.

<figure class="fig" data-figure="k8s-network-iptables">
  <figcaption>kube-proxy가 깐 규칙을 새 연결이 지나는 순서</figcaption>
</figure>

엔드포인트가 셋이면 첫 갈래가 1/3, 둘째가 남은 것의 1/2, 마지막이 나머지를 받아 셋이 고르게 나뉜다. 고르는 단위는 패킷이 아니라 연결이다. 첫 패킷이 고른 파드를 conntrack이 기억해 두고, 같은 연결의 뒤 패킷은 규칙을 다시 타지 않는다.

그래서 HTTP keep-alive나 gRPC처럼 연결 하나를 오래 쓰는 클라이언트는 파드를 늘려도 부하가 고르게 퍼지지 않는다. 이럴 때는 클라이언트 쪽에서 연결을 여러 개로 나누거나 주기적으로 다시 맺는다.

노드에서 규칙을 직접 따라가 볼 수 있다.

```bash
iptables -t nat -L KUBE-SERVICES -n | grep 10.96.0.20
iptables -t nat -L KUBE-SVC-XXXXXXXXXXXXXXXX -n
iptables -t nat -L KUBE-SEP-XXXXXXXXXXXXXXXX -n
```

kube-proxy의 모드는 셋이다(쿠버네티스 1.37 기준).

- `iptables`: 지금의 기본값. Service와 엔드포인트마다 규칙이 몇 줄씩 붙어서, 수만 개 규모가 되면 규칙 갱신이 오래 걸린다.
- `nftables`: 커널 5.13 이상에서 쓴다. iptables와 ipvs를 대신하도록 만든 모드로 둘보다 빠르고, 앞으로 기본값이 될 예정이다.
- `ipvs`: 1.35부터 폐기 예정(deprecated)이다. 1.40부터 기본으로 꺼지고 1.43에서 빠진다.

기본값이 바뀔 예정이라, 업그레이드 때 모드가 저절로 바뀌지 않게 kube-proxy 설정에 `mode`를 직접 적어 둔다.

### Service 타입

클러스터 밖의 모니터링 서버가 Service를 불러야 하는데 `10.96.0.20`으로는 닿지 않는다. ClusterIP는 클러스터 안에서만 통하는 주소라서, 밖에서 부르려면 타입을 바꾼다.

- `ClusterIP`: 기본값. 클러스터 안에서만 부른다.
- `NodePort`: 모든 노드의 같은 포트(기본 30000에서 32767 사이)로 연다. 노드 IP를 알면 밖에서도 부른다.
- `LoadBalancer`: 클라우드나 LB 구현체가 외부 IP를 붙여 준다.

세 타입은 겹쳐 쌓인다. 장면마다 아래 막대가 하나씩 늘어나는 것을 보자.

<figure class="fig" data-figure="k8s-network-svc-types">
  <figcaption>ClusterIP, NodePort, LoadBalancer가 겹쳐 쌓이는 모습</figcaption>
</figure>

기본 설정에서 NodePort를 만들면 ClusterIP가 같이 생기고, LoadBalancer를 만들면 그 밑에 NodePort와 ClusterIP가 깔린다. 밖에서 온 요청이 노드 포트를 거쳐 ClusterIP 규칙을 타고 파드로 가기 때문이다.

타입과 따로, 가상 IP를 두지 않거나 방향이 반대인 Service도 있다.

- 헤드리스(headless) Service: `clusterIP: None`으로 만든다. 이름을 물으면 가상 IP 하나 대신 파드 IP 목록이 나온다. DB 복제본처럼 어느 파드에 붙는지가 중요한 StatefulSet에 쓴다.
- `ExternalName`: 클러스터 안에서 밖의 도메인을 내부 이름으로 부르게 한다(CNAME).

클러스터 안에서만 쓰는 Service는 ClusterIP로 두고, HTTP 서비스라면 LoadBalancer를 여러 개 여는 대신 Ingress 하나로 모은다.

## 클러스터 DNS

### Service 이름 조회

같은 네임스페이스에서는 `http://orders`로 잘 되던 호출이, 다른 네임스페이스로 옮긴 파드에서는 이름을 못 찾는다. 짧은 이름을 완성해 주는 건 파드의 `/etc/resolv.conf`다.

kubelet은 파드마다 아래 같은 resolv.conf를 넣는다. `nameserver`는 CoreDNS 앞에 있는 Service의 IP다.

```text
search shop.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```

- `search`: 이름 뒤에 붙여 볼 꼬리 목록. 첫 항목이 자기 네임스페이스다.
- `ndots`: 이름의 점이 이 수보다 적으면 search부터 붙여 본다.

네 장면에서 `orders`가 Service IP가 되는 과정을 따라가 보자.

<figure class="fig" data-figure="k8s-network-dns">
  <figcaption>짧은 이름 orders가 Service IP가 되기까지</figcaption>
</figure>

`orders`는 search 첫 항목이 붙어 `orders.shop.svc.cluster.local`이 되고, CoreDNS가 Service의 ClusterIP를 돌려준다. 다른 네임스페이스의 파드에서는 첫 항목이 그 파드의 네임스페이스라 찾지 못한다. 네임스페이스를 넘는 호출은 `orders.shop`처럼 네임스페이스까지 적는다.

### ndots와 search

외부 결제 API를 자주 부르는 파드의 CoreDNS 로그를 열어 보면, `api.example.com` 한 번 조회에 질의가 여덟 줄씩 찍혀 있다. 대부분이 "이름 없음(NXDOMAIN)"이다.

`api.example.com`은 점이 2개라 ndots 5보다 적다. 그래서 리졸버는 search 세 개를 차례로 붙여 묻고, 다 실패한 뒤에야 원래 이름을 묻는다. IPv4와 IPv6 주소를 함께 찾으면 이름마다 A와 AAAA 질의가 하나씩 나간다.

```text
이름 4개 × (A, AAAA) = 질의 8번, 그중 답을 받는 건 2번
```

모드를 바꿔 가며 조회 버튼을 누르고, 질의 로그가 몇 줄 쌓이는지 지켜본다.

<figure class="fig" data-figure="k8s-network-ndots">
  <figcaption>ndots 값에 따라 외부 이름 하나에 나가는 질의</figcaption>
</figure>

ndots:5에서는 8번 중 6번이 헛걸음이다. ndots:2로 낮추면 점이 2개인 이름을 그대로 먼저 묻고 2번에 끝난다. 돌아오는 IP는 같고, 질의 수만 4배 차이 난다.

외부 호출이 많은 파드는 파드 단위로 값을 낮춘다.

```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
```

낮춰도 클러스터 안 이름이 안 풀리지는 않는다. 점이 ndots 이상인 이름은 그대로 먼저 묻고, 실패하면 search를 붙여 다시 묻는다. 대신 `orders.shop.svc`처럼 점이 많은 내부 이름은 바깥 DNS까지 나갔다 오는 헛질의가 하나 붙는다.

- 바깥 호출이 많은 파드: ndots를 2 정도로 낮춘다.
- 짧은 내부 이름에 기대는 파드: 기본값 5를 그대로 둔다.

클러스터 전체를 한 번에 바꾸지 않고, CoreDNS 지표에서 NXDOMAIN 비율이 높은 파드부터 고친다.

### 네임서버 순서

사내 DB 주소 `db.corp.example`이 몇 번에 한 번꼴로 풀리지 않는다. 노드의 `/etc/resolv.conf`에 사내 DNS와 공용 DNS를 같이 적어 둔 클러스터에서 자주 생긴다.

CoreDNS는 `cluster.local`이 아닌 이름을 노드 resolv.conf의 네임서버로 넘긴다(`forward . /etc/resolv.conf`). 이때 네임서버를 고르는 기본 방식이 무작위(`policy random`)다. 공용 DNS가 사내 이름에 "이름 없음"으로 답하면, 그것도 정상 응답이라 다른 서버에 다시 묻지 않는다.

두 장면에서 공용 DNS로 간 질의가 어떤 색으로 돌아오는지 본다.

<figure class="fig" data-figure="k8s-network-nameserver">
  <figcaption>사내 이름 질의가 무작위로 공용 DNS에 갔을 때</figcaption>
</figure>

섞어 두면 질의 절반쯤이 공용 DNS로 가서 실패하고, 어느 쪽이 걸리느냐에 따라 되다 말다 한다. 사내 영역만 사내 DNS로 보내도록 나누면 매번 같은 곳에서 답을 받는다.

리눅스 glibc 리졸버도 비슷한 함정이 있다. resolv.conf의 네임서버를 적힌 순서대로 묻고, 다음 서버로 넘어가는 건 시간 초과일 때뿐이다. 1차와 2차는 액티브와 스탠바이가 아니라서, 첫 서버가 "이름 없음"이라고 답하면 둘째 서버는 묻지도 않는다.

CoreDNS 설정(Corefile)에서 사내 영역을 따로 떼어 낸다.

```text
corp.example:53 {
    forward . 10.0.0.53
}
.:53 {
    ...
    forward . /etc/resolv.conf
}
```

노드 resolv.conf에는 성격이 같은 네임서버만 둔다. 이름 조회가 간헐적으로 실패하면 사내와 공용 DNS가 섞여 있는지부터 본다.

## Ingress

웹, API, 관리자 화면을 각각 LoadBalancer Service로 열면 외부 IP도 셋이고, 인증서도 세 군데서 관리한다. Ingress는 입구를 하나로 두고, 호스트 이름과 경로를 보고 안쪽 Service로 나눠 보낸다.

Ingress 리소스는 "이렇게 보내 달라"는 규칙일 뿐이다. 규칙을 읽어 실제 프록시를 설정하는 건 Ingress 컨트롤러(controller)라서, 컨트롤러 없이 리소스만 만들면 아무 일도 일어나지 않는다. 컨트롤러가 둘 이상이면 `ingressClassName`으로 맡을 쪽을 정한다.

요청 세 개가 차례로 들어올 때, 입구에서 점 색이 바뀌는 순간과 켜지는 규칙 줄을 본다.

<figure class="fig" data-figure="k8s-network-ingress">
  <figcaption>외부 IP 하나로 들어온 요청이 Service로 갈리는 모습</figcaption>
</figure>

입구에서 TLS를 끊어(TLS 종료) 안쪽은 HTTP로 흐르고, 규칙 줄 하나가 Service 하나를 고른다. `shop.io/api`는 `/`와 `/api` 규칙에 모두 맞지만, 여러 경로가 맞으면 가장 긴 경로가 먼저다.

경로를 맞추는 방식은 `pathType`으로 정한다.

- `Exact`: 경로가 대소문자까지 정확히 같아야 한다.
- `Prefix`: `/`로 자른 조각 단위로 앞부분이 같아야 한다. `/foo/bar`는 `/foo/bar/baz`에 맞고 `/foo/barbaz`에는 맞지 않는다.
- `ImplementationSpecific`: 해석을 컨트롤러에 맡긴다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx    # 이 규칙을 맡을 컨트롤러
  tls:
    - hosts: [shop.io]
      secretName: shop-tls   # 인증서는 Secret으로 둔다
  rules:
    - host: shop.io
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-svc
                port:
                  number: 80
```

인증서 Secret은 이렇게 만든다.

```bash
kubectl create secret tls shop-tls --cert server.crt --key server.key
```

Ingress는 HTTP와 HTTPS만 다룬다. DB 포트나 임의의 TCP를 열어야 하면 NodePort나 LoadBalancer Service를 쓴다.

큰 파일을 올리다 413(Request Entity Too Large)이 뜨면 Ingress가 아니라 컨트롤러의 요청 본문 크기 제한에 걸린 것이다. ingress-nginx는 `nginx.ingress.kubernetes.io/proxy-body-size` 어노테이션으로 Ingress마다 올린다.

> **Ingress의 현재 상태.** Ingress API는 기능이 동결됐고, 쿠버네티스 프로젝트는 후속인 Gateway API를 권한다. Gateway API는 입구(Gateway)와 경로 규칙(HTTPRoute)을 다른 리소스로 나눈다. 가장 많이 쓰던 ingress-nginx 컨트롤러는 2026년 3월에 은퇴해 더는 릴리스와 보안 패치가 나오지 않는다. 새 클러스터는 Gateway API를 지원하는 컨트롤러로 시작한다.
{: .warn}

## Cilium

### eBPF Service 처리

Service가 수천 개인 클러스터에서 노드마다 iptables 규칙이 수만 줄로 늘고, Service가 바뀔 때마다 kube-proxy가 규칙을 다시 쓰느라 오래 걸린다. Cilium은 kube-proxy를 빼고 같은 일을 eBPF로 한다.

eBPF는 커널 안에서 돌리는 작은 프로그램이다. Cilium은 네트워크 장치에 eBPF 프로그램을 붙이고, Service IP와 엔드포인트를 eBPF 맵(해시 테이블)에 넣어 둔다. 패킷이 오면 맵을 한 번 찾아 바로 파드를 고른다.

Service 수가 늘 때 새 연결 하나가 비교하는 규칙 수를 견줘 보자.

<figure class="fig" data-figure="k8s-network-ebpf">
  <figcaption>Service 수에 따른 비교 횟수 (KUBE-SERVICES를 위에서부터 훑는다고 보고 센 대략값)</figcaption>
</figure>

iptables는 `KUBE-SERVICES`를 위에서부터 훑어서, Service가 1만 개면 평균 5천 줄을 본다. eBPF 맵은 Service가 몇 개든 한 번 찾는다. 규칙을 고칠 때도 전체를 다시 쓰지 않고 바뀐 항목만 고친다.

Cilium Helm 값에서 kube-proxy를 대신하게 하는 값이다. 기본값은 `false`다.

```yaml
kubeProxyReplacement: true
k8sServiceHost: 192.168.0.10   # kube-proxy가 없으니 API 서버 주소를 직접 적는다
k8sServicePort: 6443
```

백엔드를 고르는 방식은 기본이 무작위(`random`)이고, 일관 해싱인 `maglev`로 바꿀 수 있다. kube-proxy를 빼면 iptables에서는 Service 규칙이 안 보이므로 Cilium 에이전트 안에서 본다.

```bash
kubectl -n kube-system exec ds/cilium -c cilium-agent -- cilium-dbg service list
```

### 네이티브 라우팅

온프레미스 노드들이 같은 스위치(L2)에 붙어 있는데, 파드 패킷이 VXLAN으로 감싸진 채 오간다. Cilium은 따로 설정하지 않으면 터널 모드로 돈다. 바닥 네트워크에 요구하는 것이 가장 적기 때문이다.

- 터널(encapsulation): 파드 패킷을 노드 주소로 한 번 더 감싸 UDP(VXLAN 8472, Geneve 6081)로 보낸다. 노드끼리 통하기만 하면 된다.
- 네이티브 라우팅: 감싸지 않고 노드 라우팅 테이블로 보낸다. 노드 사이 네트워크가 파드 대역(PodCIDR)을 라우팅할 수 있어야 한다.

두 장면에서 노드 사이를 건너는 패킷에 껍데기가 붙는지 본다.

<figure class="fig" data-figure="k8s-network-routing">
  <figcaption>터널과 네이티브 라우팅의 노드 간 패킷</figcaption>
</figure>

VXLAN은 패킷마다 50바이트를 더 붙여, MTU 1500이면 파드가 쓸 수 있는 크기가 1450으로 준다. 네이티브 라우팅은 껍데기가 없어 파드 패킷이 노드 패킷처럼 그대로 오간다.

```yaml
routingMode: native
autoDirectNodeRoutes: true            # 같은 L2의 노드끼리 서로의 PodCIDR 경로를 깐다
ipv4NativeRoutingCIDR: 10.244.0.0/16  # 네이티브로 라우팅할 대역
ipam:
  operator:
    clusterPoolIPv4PodCIDRList: ["10.244.0.0/16"]
    clusterPoolIPv4MaskSize: 24
```

`autoDirectNodeRoutes`는 노드가 모두 한 L2에 있을 때만 쓴다. 노드가 라우터 너머로 흩어져 있으면 BGP 같은 라우팅 데몬이 경로를 나눠야 한다. 노드마다 받은 대역은 CiliumNode에서 본다.

```bash
kubectl get ciliumnode worker3 -o jsonpath='{.spec.ipam.podCIDRs}'
```

/16을 /24로 나누면 노드는 256대까지, 노드당 파드 주소는 254개 남짓이다. 클러스터가 커질 여지가 있으면 처음부터 대역을 넉넉히 잡는다.

### DSR

LoadBalancer로 연 서비스의 접근 로그에 클라이언트 IP 대신 노드 IP만 찍힌다. `externalTrafficPolicy: Cluster`(기본값)에서는 요청을 받은 노드가 다른 노드의 파드로 넘길 때 출발 주소를 자기 IP로 바꾸기(SNAT) 때문이다.

- `Cluster`: 모든 노드가 받아 어느 파드로든 넘긴다. 클라이언트 IP가 사라진다.
- `Local`: 그 노드의 파드로만 넘겨 클라이언트 IP가 남는다. 파드가 없는 노드로 온 패킷은 버려지고, 노드마다 부하가 기운다.

Cilium의 DSR(Direct Server Return)을 쓰면 둘 중 하나를 고르지 않아도 된다. 받은 노드는 출발 주소를 그대로 두고 Service IP를 IP 옵션에 실어 넘기고, 파드가 있는 노드는 응답을 클라이언트로 바로 보낸다. 모드를 바꿔 요청을 보내고, 파드가 본 IP와 응답이 돌아가는 길을 견준다.

<figure class="fig" data-figure="k8s-network-dsr">
  <figcaption>SNAT과 DSR에서 파드가 보는 출발 IP와 응답 경로</figcaption>
</figure>

SNAT에서는 파드가 노드 1의 IP만 보고, 응답도 노드 1을 거쳐 돌아간다. DSR에서는 파드가 클라이언트 IP를 보고, 응답은 노드 2에서 바로 나간다. 요청이 가는 길은 같고 출발 주소와 응답 길만 달라진다.

```yaml
loadBalancer:
  mode: dsr              # TCP만 DSR, UDP는 SNAT으로 섞으려면 hybrid
  dsrDispatch: opt       # Service IP를 IP 옵션에 싣는다
  acceleration: disabled
```

- `opt`: 껍데기 없이 옵션만 붙여 가볍다. 다만 일부 퍼블릭 클라우드 네트워크는 Cilium의 IP 옵션을 버릴 수 있다.
- `ipip`, `geneve`: 패킷을 한 번 더 감싸 옵션이 버려지는 환경에서도 통하지만, 헤더만큼 무거워진다.
- `acceleration: native`: XDP로 랜카드 드라이버 단계에서 처리해 더 빠르다. 드라이버가 XDP를 지원해야 하고, 기본값은 `disabled`다.

externalTrafficPolicy를 Cluster로 두고도 클라이언트 IP가 필요하면 DSR부터 검토한다.

### BGP LB 대역 광고

온프레미스에서 LoadBalancer Service를 만들면 `EXTERNAL-IP`가 계속 `<pending>`이다. 외부 IP를 나눠 줄 클라우드도, 그 IP로 가는 길을 라우터에 알려 줄 주체도 없기 때문이다.

Cilium은 두 가지를 다 한다.

- LB IPAM: `CiliumLoadBalancerIPPool`의 대역에서 LoadBalancer Service에 IP를 나눠 준다.
- BGP 컨트롤 플레인: 노드가 라우터와 BGP 세션을 맺고, 그 대역으로 가는 길을 광고한다.

BGP는 네트워크끼리 "이 대역은 나한테 보내라"를 주고받는 프로토콜이다. AS 번호(ASN)는 네트워크마다 붙는 번호로, 우편번호처럼 어느 네트워크인지 가른다. 세 장면에서 세션, 광고, 트래픽이 차례로 생기는 것을 지켜보자.

<figure class="fig" data-figure="k8s-network-bgp">
  <figcaption>노드가 라우터에 LB 대역을 광고하고 트래픽을 받는 과정</figcaption>
</figure>

라우터는 광고를 받은 뒤에야 `203.0.113.0/27`로 가는 길을 노드 둘로 안다. 노드 하나가 죽으면 그 노드의 세션이 끊겨 경로가 빠지고, 남은 노드로만 보낸다. hold time이 9초면 장애를 알아채는 데 최대 9초가 걸린다.

설정은 CRD 네 개로 한다.

```yaml
apiVersion: cilium.io/v2
kind: CiliumLoadBalancerIPPool
metadata:
  name: lb-pool
spec:
  allowFirstLastIPs: "No"
  blocks:
    - cidr: 203.0.113.0/27
---
apiVersion: cilium.io/v2
kind: CiliumBGPClusterConfig
metadata:
  name: bgp
spec:
  nodeSelector:
    matchLabels:
      enable-bgp: "true"
  bgpInstances:
    - name: as65130
      localASN: 65130
      peers:
        - name: router-1
          peerASN: 65133
          peerAddress: 192.168.0.1
          peerConfigRef:
            name: peer
---
apiVersion: cilium.io/v2
kind: CiliumBGPPeerConfig
metadata:
  name: peer
spec:
  timers:
    holdTimeSeconds: 9
    keepAliveTimeSeconds: 3
  gracefulRestart:
    enabled: true
  families:
    - afi: ipv4
      safi: unicast
      advertisements:
        matchLabels:
          advertise: bgp
---
apiVersion: cilium.io/v2
kind: CiliumBGPAdvertisement
metadata:
  name: lb
  labels:
    advertise: bgp
spec:
  advertisements:
    - advertisementType: Service
      service:
        addresses: [LoadBalancerIP]
        aggregationLengthIPv4: 27
      selector:            # 모든 Service를 고르는 관용 표현
        matchExpressions:
          - { key: somekey, operator: NotIn, values: ['never-used-value'] }
```

- `CiliumLoadBalancerIPPool`: LB IP를 나눠 줄 대역. `allowFirstLastIPs: "No"`면 첫 주소와 끝 주소를 뺀다.
- `CiliumBGPClusterConfig`: 어느 노드가 어느 라우터와 피어를 맺을지
- `CiliumBGPPeerConfig`: 타이머, graceful restart, 주소 체계
- `CiliumBGPAdvertisement`: 무엇을 광고할지. LoadBalancerIP 말고도 ClusterIP, ExternalIP, PodCIDR을 고를 수 있다. `aggregationLengthIPv4: 27`은 Service마다 /32를 따로 광고하지 않고 /27 하나로 묶는다.

세션 상태는 `cilium bgp peers`로 본다. `established`가 아니면 양쪽 ASN과 피어 주소, TCP 179를 막는 방화벽부터 확인한다.

## 정리

| 구간 | 하는 일 | 기억할 점 |
|---|---|---|
| 파드 안 | 네트워크 네임스페이스 하나를 나눠 쓴다 | localhost로 부르고, 포트가 겹치면 안 된다 |
| 파드 간 | 파드마다 고유 IP, NAT 없이 직접 통신 | 약속을 지키는 건 CNI 플러그인 |
| Service | 바뀌지 않는 가상 IP와 이름 | 연결 단위로 파드를 고른다. 긴 연결은 고르게 안 퍼진다 |
| kube-proxy | 커널 nat 규칙을 깐다 | 기본 iptables, 앞으로 nftables. ipvs는 폐기 예정 |
| Service 타입 | ClusterIP, NodePort, LoadBalancer가 겹쳐 쌓인다 | 헤드리스는 파드 IP 목록을 준다 |
| 클러스터 DNS | search와 ndots로 짧은 이름을 푼다 | ndots:5는 외부 이름 질의를 4배로 늘린다 |
| 업스트림 DNS | CoreDNS는 네임서버를 무작위로 고른다 | 사내와 공용 DNS를 섞지 않는다 |
| Ingress | 호스트와 경로로 Service를 고른다 | 컨트롤러가 있어야 동작. API는 동결, Gateway API로 |
| Cilium eBPF | 맵 조회로 Service를 처리 | kube-proxy를 뺄 수 있다 |
| 네이티브 라우팅 | 감싸지 않고 라우팅 테이블로 보낸다 | 노드 사이 네트워크가 PodCIDR을 라우팅해야 한다 |
| DSR | 출발 IP를 두고 응답을 바로 보낸다 | Cluster 정책에서도 클라이언트 IP가 남는다 |
| BGP | LB 대역을 라우터에 광고 | LB IPAM 풀과 CRD 네 개 |
