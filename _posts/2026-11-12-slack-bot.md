## 봇 구성

배포가 실패하면 #ops 채널에 알림이 오고, 운영자가 채널에서 `@봇 status api`를 치면 봇이 서버 상태를 답한다. 운영 봇이 하는 일은 이 두 방향으로 나뉜다.

- 보내기: 봇 서버가 슬랙 Web API의 `chat.postMessage`를 불러 채널에 글을 쓴다.
- 받기: 채널에서 생긴 일(멘션, 슬래시 명령, 버튼 클릭)을 슬랙이 봇 서버로 전달한다.

두 장면에서 메시지가 어느 쪽에서 출발해 어디를 거치는지 살펴보자.

<figure class="fig" data-figure="slack-bot-overview">
  <figcaption>알림을 보낼 때와 명령을 받을 때 메시지가 지나는 길</figcaption>
</figure>

보내기는 HTTP 호출 한 번이다. 봇 토큰을 실어 `chat.postMessage`를 부르면 끝난다.

```python
from slack_sdk import WebClient

client = WebClient(token=os.environ["SLACK_BOT_TOKEN"])
client.chat_postMessage(channel="C0123456789", text="배포 실패: api v1.42")
```

알림만 보낸다면 수신 웹훅(incoming webhook)도 된다. 앱 설정에서 채널 하나에 묶인 URL을 받아 JSON을 POST하는 방식이라 토큰 없이 쓰지만, 보낼 채널을 바꾸거나 보낸 글을 지울 수 없다.

받기는 슬랙이 먼저 연락해 오는 쪽이라 정할 것이 많다. 이벤트를 받는 길, 응답 기한, 요청이 정말 슬랙에서 왔는지 확인하는 법이다.

## 이벤트 수신 방식

슬랙이 봇 서버로 이벤트를 전달하는 길은 두 가지다.

- Events API: 봇 서버가 공개 주소를 열어 두고 슬랙이 보내는 HTTP 요청을 받는다.
- Socket Mode: 봇 서버가 먼저 슬랙에 웹소켓 연결을 열고 그 연결로 받는다.

이벤트의 모양과 Bolt 리스너 코드는 같고, 연결을 누가 여는지만 다르다.

### Events API

봇 서버에 `https://bot.example.com/slack/events` 같은 공개 HTTPS 주소가 있으면, 슬랙은 이벤트가 생길 때마다 이 주소로 POST를 보낸다. 앱 설정의 Event Subscriptions에 주소를 처음 넣을 때는 확인 요청(`url_verification`)이 한 번 오고, 그 안의 `challenge` 값을 그대로 돌려줘야 주소가 등록된다.

두 장면에서 등록 확인과 실제 이벤트 전달을 견줘 보자. 어느 쪽이든 봇 서버가 HTTP 응답을 돌려줘야 한 번의 전달이 끝난다.

<figure class="fig" data-figure="slack-bot-http">
  <figcaption>슬랙이 공개 주소로 POST를 보내고 봇 서버가 응답한다</figcaption>
</figure>

Bolt for Python은 challenge 응답과 서명 검증을 미들웨어로 갖고 있다. 웹 프레임워크에는 요청을 Bolt로 넘기는 라우트 하나만 둔다.

```python
import os
from fastapi import FastAPI, Request
from slack_bolt import App
from slack_bolt.adapter.fastapi import SlackRequestHandler

bolt = App(
    token=os.environ["SLACK_BOT_TOKEN"],                 # xoxb-
    signing_secret=os.environ["SLACK_SIGNING_SECRET"],
)

@bolt.event("app_mention")
def on_mention(event, say):
    say(text=status_of(event["text"]), thread_ts=event["ts"])

handler = SlackRequestHandler(bolt)
api = FastAPI()

@api.post("/slack/events")
async def slack_events(req: Request):
    return await handler.handle(req)
```

앱 설정의 Event Subscriptions, Slash Commands, Interactivity에 같은 주소를 넣으면 이벤트, 명령, 버튼 클릭이 모두 이 라우트로 온다. 메시지 본문은 이벤트의 `text`에 들어 있다. `conversations_history`로 채널의 최신 글을 다시 읽으면 왕복이 늘고, 그사이 다른 글이 올라오면 엉뚱한 글을 집는다.

HTTP 방식은 봇 서버가 인터넷에서 들어오는 HTTPS 요청을 받을 수 있어야 한다. 사내망 서버라면 리버스 프록시나 게이트웨이를 앞에 두고 주소를 연다.

### Socket Mode

방화벽 정책 때문에 들어오는 포트를 열 수 없는 서버도 있다. Socket Mode는 방향을 뒤집어, 봇 서버가 슬랙으로 나가는 웹소켓 연결을 열고 이벤트를 그 연결로 받는다.

연결을 여는 데는 앱 수준 토큰(`xapp-`)을 쓴다. 봇 서버가 이 토큰으로 `apps.connections.open`을 부르면 `wss://` 주소가 오고, 그 주소로 연결을 맺는다. 연결이 열리는 순간과 그 뒤로 이벤트와 ack가 어느 방향으로 흐르는지 지켜보자.

<figure class="fig" data-figure="slack-bot-socket">
  <figcaption>봇 서버가 연 웹소켓으로 이벤트를 받고 envelope_id로 ack한다</figcaption>
</figure>

이벤트는 `envelope_id`가 붙은 봉투에 담겨 오고, 봇 서버는 같은 `envelope_id`를 돌려보내 받았다고 알린다(ack). HTTP 방식의 200 응답과 같은 역할이다. 웹소켓 연결이 토큰으로 이미 인증돼 있어서 요청마다 서명을 검증하지 않는다.

Bolt에서는 리스너를 그대로 두고 핸들러만 바꾼다.

```python
from slack_bolt.adapter.socket_mode import SocketModeHandler

SocketModeHandler(bolt, os.environ["SLACK_APP_TOKEN"]).start()   # xapp-
```

연결은 계속 유지되지 않는다. 슬랙은 끊기 10초쯤 전에 `disconnect` 메시지를 보내고, 경고 없이 `refresh_requested`로 끊기도 한다. 핸들러가 새 연결을 맺지만 앱 하나에 동시 연결은 10개까지다.

두 방식은 이렇게 나눠 쓴다.

- Socket Mode: 개발 중이거나 공개 주소를 열 수 없는 사내 봇. 슬랙 마켓플레이스에는 올릴 수 없다.
- Events API: 운영 환경. 슬랙 문서도 운영에는 HTTP를 권하고, Socket Mode는 슬랙 쪽 컨테이너가 가끔 바뀌면서 연결이 흔들릴 수 있다고 적어 두었다.

공개 주소를 열 수 있으면 Events API로 시작하고, 열 수 없을 때 Socket Mode를 고른다.

## 3초 응답 제한

### 응답 기한

봇에 "지난 배포 로그 모아 줘"라고 시켰더니 같은 답이 두 번 달린다. 봇 서버가 일을 다 끝낸 뒤에 응답했고, 그사이 슬랙이 같은 요청을 다시 보냈기 때문이다. 슬랙은 봇 서버의 응답을 3초까지만 기다린다.

- 이벤트: 3초 안에 2xx가 오지 않으면 실패로 보고 같은 이벤트를 다시 보낸다.
- 슬래시 명령: 3000ms 안에 응답이 없으면 명령을 친 사용자에게 `operation_timeout` 오류가 뜬다.
- 버튼, 메뉴 같은 인터랙션: 3초 안에 200이 없으면 사용자에게 오류가 보인다.

두 장면에서 3초 선을 넘는 순간 슬랙이 무엇을 하는지 본다.

<figure class="fig" data-figure="slack-bot-deadline">
  <figcaption>응답이 3초를 넘길 때 이벤트와 슬래시 명령이 겪는 일</figcaption>
</figure>

이벤트는 다시 오고, 명령은 사용자에게 실패로 보인다. 어느 쪽이든 봇 서버는 일을 계속하고 있어서, 슬랙이 보는 결과와 봇이 실제로 한 일이 어긋난다.

모달을 여는 `trigger_id`도 3초 뒤에 만료된다. 버튼을 누르면 모달이 떠야 하는 기능은 무거운 일보다 모달 열기를 먼저 한다.

### ack 먼저 보내기

3초 안에 끝나지 않는 일은 순서를 바꾼다. 받았다는 응답(ack)을 먼저 보내고, 일은 그 뒤에 해서 결과를 따로 보낸다.

데모는 봇에게 8초 걸리는 로그 모으기를 시키는 장면이다. 모드를 바꿔 가며 버튼을 누르고, 슬랙 줄에 재전송이 생기는지와 채널 줄에 답이 몇 번 달리는지 지켜본다.

<figure class="fig" data-figure="slack-bot-ack">
  <figcaption>무거운 일을 받았을 때 응답 시점에 따른 차이</figcaption>
</figure>

처리 후 응답하면 8초짜리 일이 끝나기 전에 3초가 지나 재전송이 오고, 봇은 같은 일을 한 번 더 해서 답을 두 번 단다. 1분 뒤와 5분 뒤에도 재시도가 이어진다. ack를 먼저 보내면 슬랙은 0.1초 만에 200을 받고 더 보내지 않는다.

두 모드 모두 결과가 나오는 시각은 8초 무렵으로 같다. 일의 양은 그대로이고 **응답을 보내는 시점**만 바뀌었다.

Bolt for Python은 기본 설정에서 이미 이 순서로 돈다.

- 이벤트: Bolt가 리스너를 부르기 전에 ack를 보내고, 리스너는 별도 스레드에서 돈다.
- 명령과 인터랙션: 리스너가 `ack()`를 부르는 순간 응답이 나가고, 리스너의 나머지 코드는 그 뒤에 계속 돈다.

```python
@bolt.command("/deploy-log")
def deploy_log(ack, command, respond):
    ack("로그를 모으는 중이다")                   # 여기서 HTTP 응답이 나간다
    respond(collect_logs(command["text"]))         # 수십 초 걸려도 된다
```

`respond()`는 요청에 딸려 온 `response_url`로 결과를 보낸다. 이 주소는 30분 안에 5번까지 쓸 수 있다.

AWS Lambda 같은 FaaS는 응답을 보내면 함수가 멈출 수 있다. 이때는 `process_before_response=True`로 응답을 리스너 끝까지 미루고, 무거운 일은 lazy 리스너로 따로 실행한다.

```python
def quick_ack(ack):
    ack("로그를 모으는 중이다")

def collect(command, respond):
    respond(collect_logs(command["text"]))

app = App(process_before_response=True)
app.command("/deploy-log")(ack=quick_ack, lazy=[collect])
```

스레드로 미룬 일은 프로세스가 재시작되면 함께 사라진다. 배포 실행처럼 놓치면 안 되는 일은 ack 다음에 큐나 작업 테이블에 넣고 별도 워커가 처리하게 한다.

### 재시도와 중복 처리

ack를 먼저 보내도 같은 이벤트가 두 번 올 수 있다. 배포 중 재시작이나 네트워크 오류로 응답이 슬랙에 닿지 못하면 슬랙은 같은 이벤트를 최대 3번 더 보낸다.

```text
원본    실패 (3초 초과, 연결 실패, 2xx가 아닌 응답)
1회차   거의 즉시
2회차   1분 뒤
3회차   5분 뒤
```

재시도 요청에는 헤더 두 개가 붙는다.

- `X-Slack-Retry-Num`: 몇 번째 재시도인지(1, 2, 3)
- `X-Slack-Retry-Reason`: 이유. `http_timeout`, `connection_failed`, `http_error` 등

`X-Slack-Retry-Num`이 있으면 버리면 되지 않나 싶지만, 이유가 `connection_failed`면 원본이 봇에 닿지도 못한 경우다. 헤더만 보고 버리면 그 이벤트는 아무도 처리하지 않는다. 그래서 헤더가 아니라 이벤트마다 붙는 `event_id`로 거른다.

모드를 바꿔 가며 재전송을 일으키고, 채널에 답이 몇 번 달리는지 본다.

<figure class="fig" data-figure="slack-bot-dedup">
  <figcaption>원본과 재시도 세 번을 event_id로 거를 때와 거르지 않을 때</figcaption>
</figure>

거르지 않으면 원본과 재시도 세 번이 모두 리스너를 지나 답이 네 번 달린다. event_id로 거르면 처음 본 id만 저장소에 남기고 통과시켜, 나머지 세 번은 200만 돌려주고 건너뛴다. 슬랙이 보내는 횟수는 같고, 봇이 일하는 횟수만 1번으로 줄었다.

```python
import redis

r = redis.Redis()

@bolt.event("app_mention")
def on_mention(body, event, say):
    if not r.set(f"slack:event:{body['event_id']}", 1, nx=True, ex=3600):
        return                                     # 이미 처리한 이벤트
    say(text=status_of(event["text"]), thread_ts=event["ts"])
```

저장소는 프로세스 밖에 둔다. 메모리 안의 set은 서버가 여러 대이거나 재시작하면 기억을 잃는다. 재시도는 몇 분 안에 끝나서 보관 시간은 1시간이면 넉넉하다.

재시도와 관련해 알아 둘 값이 두 가지 더 있다.

- 일부러 실패를 돌려주면서 재시도는 막고 싶으면 응답에 `X-Slack-No-Retry: 1`을 붙인다.
- 60분 동안 전달 시도의 95% 넘게 실패하면 슬랙이 이벤트 구독을 잠시 끈다. 시간당 이벤트가 1,000건 미만인 앱은 자동으로 꺼지지 않는다.

이벤트 리스너는 일을 시작하기 전에 `event_id`부터 확인한다.

## 보안과 권한

### 요청 서명 검증

Events API 주소는 인터넷에 열려 있어서, 주소만 알면 누구나 이벤트처럼 생긴 JSON을 POST할 수 있다. 검증하지 않으면 `@봇 배포 롤백` 같은 명령을 아무나 흉내 낸다. 슬랙은 요청마다 앱의 signing secret으로 만든 서명을 헤더에 붙인다.

```text
X-Slack-Request-Timestamp: 1762916400
X-Slack-Signature:         v0=a2114d57b48eac39b9ad189dd8316235a7b4a8d21a10bd27519666489c69b503

basestring = "v0:" + 타임스탬프 + ":" + 요청 본문
서명       = "v0=" + HMAC-SHA256(signing secret, basestring)의 16진수
```

봇 서버는 같은 계산을 해서 헤더의 서명과 견준다. 세 장면에서 정상 요청, 위조 요청, 복사해 다시 보낸 요청이 어느 검사에서 걸리는지 본다.

<figure class="fig" data-figure="slack-bot-signature">
  <figcaption>정상 요청, 위조 요청, 재전송 공격이 서명 검증을 지나는 모습</figcaption>
</figure>

위조 요청은 signing secret을 모르니 서명이 맞지 않는다. 지나간 정상 요청을 통째로 복사해 다시 보내면(재전송 공격, replay attack) 서명은 맞지만 타임스탬프가 오래돼 걸린다. 슬랙 문서는 현재 시각과 5분 넘게 차이 나는 요청을 버리라고 한다. 타임스탬프가 서명 계산에 들어가서 시각만 고쳐 보낼 수도 없다.

Bolt는 `signing_secret`을 받으면 이 검사를 미들웨어로 한다. 직접 짤 때는 이렇게 한다.

```python
import hashlib, hmac, time

def verify(secret: str, ts: str, body: bytes, sig: str) -> bool:
    if abs(time.time() - int(ts)) > 60 * 5:
        return False
    base = b"v0:" + ts.encode() + b":" + body
    mine = "v0=" + hmac.new(secret.encode(), base, hashlib.sha256).hexdigest()
    return hmac.compare_digest(mine, sig)
```

- 본문은 파싱하기 전에 받은 바이트 그대로 쓴다. JSON을 다시 직렬화하면 공백이나 순서가 바뀌어 서명이 맞지 않는다.
- 서명 비교는 `hmac.compare_digest`로 한다. `==`는 다른 글자를 만나는 즉시 끝나서, 응답 시간 차이로 서명을 한 글자씩 추측할 틈을 준다.

예전의 verification token(요청 본문에 실려 오던 고정 값)은 폐기됐고 signing secret이 대신한다. 새로 만드는 핸들러는 signing secret 검증부터 넣는다.

### 토큰과 scope

슬랙 앱에는 비밀 값이 여럿 있고 쓰임이 다르다.

- 봇 토큰(`xoxb-`): 봇 이름으로 Web API를 부른다. 설치한 사람이 퇴사해도 남는다.
- 사용자 토큰(`xoxp-`): 특정 사용자를 대신해 부른다. 글도 그 사람 이름으로 써진다.
- 앱 수준 토큰(`xapp-`): Socket Mode 연결을 연다.
- signing secret: 받은 요청의 서명을 검증한다. API 호출에는 쓰지 않는다.

운영 봇은 봇 토큰 하나로 거의 다 된다. 사용자 토큰은 그 사람의 권한으로 움직여서 새면 피해가 크다.

봇 토큰으로 할 수 있는 일은 앱에 준 권한(scope)이 정한다. 알림과 명령을 다루는 봇이면 이 정도다.

- `chat:write`: 글 쓰기
- `app_mentions:read`: `@봇` 멘션 이벤트 받기
- `commands`: 슬래시 명령 받기

권한을 받아 두어도 호출이 실패하는 경우가 있다. 세 장면에서 같은 봇 토큰으로 부른 호출이 어디서 걸리는지 본다.

<figure class="fig" data-figure="slack-bot-tokens">
  <figcaption>같은 봇 토큰이 채널과 권한에 따라 통과하거나 걸리는 모습</figcaption>
</figure>

`chat:write`만으로는 봇이 들어가 있는 채널에만 쓸 수 있고, 아닌 채널은 `not_in_channel`이 온다. 채널에 봇을 초대하거나, 공개 채널 전체에 쓰는 `chat:write.public`을 더 받는다. 기록 읽기처럼 받지 않은 권한이 필요한 메서드는 `missing_scope`로 끝난다.

scope를 넓게 잡으면 개발은 편하지만, 토큰이 새면 그만큼 많은 일을 할 수 있다. 오류 이름을 보고 필요한 scope만 하나씩 더하고, 토큰은 환경변수나 시크릿 저장소에 둔다.

## 레거시 방식

몇 년 전 슬랙 봇 예제는 대개 RTM API나 `slackeventsapi`로 이벤트를 받고, 첨부(attachments)로 버튼과 메뉴를 만들었다. 지금은 대부분 바뀌었다. 정리 일정이 어떻게 이어졌는지 살펴보자.

<figure class="fig" data-figure="slack-bot-legacy">
  <figcaption>클래식 앱과 레거시 봇의 정리 일정 (슬랙 변경 기록 기준)</figcaption>
</figure>

- RTM API: 웹소켓으로 워크스페이스의 일을 받던 API다. 세분화된 권한(granular permission)을 쓰는 지금의 슬랙 앱은 쓸 수 없고, Events API나 Socket Mode로 옮긴다.
- 클래식 앱과 레거시 커스텀 봇: 2024년 6월 4일부터 새로 만들 수 없다. 레거시 커스텀 봇은 2025년 3월 31일에 멈춘다고 공지됐다. 클래식 앱은 2026년 11월 16일 종료 예정이었다가 보류돼 지금은 계속 동작한다.
- `slackeventsapi`: 저장소가 보관(archived) 처리됐고 Bolt를 쓰라고 안내한다. 이 라이브러리는 리스너가 끝난 뒤에 200을 돌려줘서, 리스너에서 오래 걸리는 일을 하면 앞의 재시도를 그대로 겪는다.
- verification token: signing secret으로 바뀌었다.
- 첨부의 `actions`로 만든 버튼과 메뉴: 레거시 문서로 옮겨졌다. 지금은 Block Kit 블록으로 만들고, 클릭은 `block_actions`로 온다.
- 수신 웹훅: 지금도 쓰는 기능이다. 앱 설정에서 채널마다 URL을 받는다.

봇이 쓴 글이 다시 이벤트로 돌아오는 것도 예전 코드에서 직접 거르던 부분이다. Bolt는 자기 봇이 쓴 이벤트를 기본으로 거르고, 다른 봇의 글은 이벤트의 `bot_id`로 거른다.

오래된 봇을 넘겨받으면 import부터 본다. `slackeventsapi`나 RTM 클라이언트가 보이면 Bolt와 Events API로 옮길 대상이다.

## 정리

| 항목 | 내용 | 기억할 점 |
|---|---|---|
| Events API | 슬랙이 공개 HTTPS 주소로 POST | 운영 환경 기본값. 서명 검증 필수 |
| Socket Mode | 봇이 연 웹소켓으로 수신 | 포트 불필요, `xapp-` 토큰, 동시 연결 10개 |
| 3초 제한 | 이벤트는 재전송, 명령은 사용자 오류 | ack 먼저, 일은 그 뒤 |
| 재시도 | 즉시, 1분, 5분 최대 3번 | 헤더가 아니라 `event_id`로 거른다 |
| 서명 검증 | HMAC-SHA256(signing secret, `v0:ts:body`) | 원본 바이트, 5분 넘은 요청 거부 |
| 토큰 | `xoxb-`, `xoxp-`, `xapp-` | 봇 토큰과 필요한 scope만 |
| 레거시 | RTM, `slackeventsapi`, verification token | Bolt와 Events API로 옮긴다 |
