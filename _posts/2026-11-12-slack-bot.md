## 요약

- 이벤트는 슬랙이 공개 주소로 POST하거나(Events API) 봇이 연 웹소켓으로 온다(Socket Mode). 운영은 HTTP, 들어오는 포트를 못 열 때 Socket Mode다.
- 공개 주소로 오는 요청은 `v0:타임스탬프:본문`의 HMAC-SHA256 서명과 5분 시각 차이로 검증한다. 본문은 파싱 전 바이트를 쓴다.
- 응답 기한은 3초다. ack를 먼저 보내고 일은 그 뒤에 하며, 오래 걸리거나 몰리는 일은 큐와 워커로 넘긴다.
- 응답이 닿지 못하면 즉시, 1분, 5분 뒤 최대 3번 다시 온다. 헤더가 아니라 `event_id`로 거른다.
- 답은 `response_url`(30분, 5번)이나 `chat.postMessage`로 쓴다. scope와 채널, 채널당 초당 1개 한도 안에서 보내고, 429면 `Retry-After`만큼 기다린다.

## 이벤트 전달 경로

채널에서 `@봇 status api`를 치면 슬랙 서버는 이 글을 `app_mention` 이벤트로 만들어 봇 서버에 넘긴다. 봇은 Web API(슬랙이 HTTPS로 열어 둔 메서드 모음, `chat.postMessage` 등)를 불러 답을 채널에 쓴다.

이벤트가 봇 서버로 오는 길은 두 가지이고, 연결을 여는 쪽이 다르다.

- Events API(HTTP): 봇 서버가 공개 HTTPS 주소를 열어 두면 슬랙이 이벤트마다 그 주소로 POST를 보낸다. 요청마다 짧은 연결이 새로 열린다.
- Socket Mode: 봇 서버가 슬랙으로 나가는 웹소켓(WebSocket, 한 번 맺으면 양쪽이 계속 메시지를 주고받는 연결)을 열어 두고, 이벤트를 그 연결로 받는다.

### Events API

앱 설정의 Event Subscriptions에 주소를 처음 넣으면 슬랙은 `url_verification` 요청을 한 번 보낸다. 본문의 `challenge` 값을 그대로 돌려줘야 주소가 등록되고, 그 뒤로는 이벤트마다 POST가 온다. 아래 그림처럼 봇 서버가 2xx로 답해야 한 번의 전달이 끝난다.

<figure class="fig" data-figure="slack-bot-http">
  <figcaption>슬랙이 공개 주소로 POST를 보내고 봇 서버가 응답한다</figcaption>
</figure>

POST 본문은 바깥 봉투와 안쪽 이벤트로 나뉜다.

```json
{
  "type": "event_callback",
  "team_id": "T0123ABCD",
  "event_id": "Ev06ABCDEF",
  "event_time": 1762916400,
  "event": { "type": "app_mention", "user": "U0123ABCD", "text": "<@U0BOT> status api", "ts": "1762916400.000100" }
}
```

`event_id`는 모든 워크스페이스를 통틀어 하나뿐인 값이라 뒤의 중복 제거에 쓴다. 메시지 본문은 `event.text`에 이미 들어 있어서 `conversations.history`로 채널을 다시 읽을 필요가 없다. 다시 읽으면 그사이 올라온 다른 글을 집을 수도 있다.

Bolt for Python은 슬랙이 만든 봇 프레임워크다. 이벤트 종류마다 리스너(listener, 그 이벤트가 오면 실행되는 함수)를 달고, challenge 응답, 서명 검증, 자기 봇이 쓴 글 거르기는 기본 미들웨어(리스너보다 먼저 모든 요청을 거치는 처리 단계)가 맡는다. 웹 프레임워크에는 요청을 Bolt로 넘기는 라우트 하나만 둔다.

```python
from slack_bolt import App
from slack_bolt.adapter.fastapi import SlackRequestHandler

bolt = App(token=os.environ["SLACK_BOT_TOKEN"], signing_secret=os.environ["SLACK_SIGNING_SECRET"])

@bolt.event("app_mention")
def on_mention(event, say):
    say(text=status_of(event["text"]), thread_ts=event["ts"])

handler = SlackRequestHandler(bolt)
api = FastAPI()

@api.post("/slack/events")
async def slack_events(req: Request):
    return await handler.handle(req)
```

Slash Commands와 Interactivity 설정에도 같은 주소를 넣으면 명령과 버튼 클릭도 이 라우트로 온다.

### Socket Mode

들어오는 포트를 열 수 없는 사내망 서버는 방향을 뒤집는다. 봇 서버가 앱 수준 토큰(`xapp-`)으로 `apps.connections.open`을 부르면 `wss://` 주소가 오고, 봇이 그 주소로 웹소켓을 연다. 아래 그림처럼 이벤트는 그 연결을 타고 들어오고, 답은 여전히 Web API로 나간다.

<figure class="fig" data-figure="slack-bot-socket">
  <figcaption>봇 서버가 연 웹소켓으로 이벤트를 받고 envelope_id로 ack한다</figcaption>
</figure>

이벤트는 `envelope_id`가 붙은 봉투로 오고, 봇은 같은 id를 돌려보내 받았다고 알린다(ack). HTTP 방식의 200 응답과 같은 역할이다.

```text
받음  {"envelope_id": "dbdd0ef3-...", "type": "events_api", "payload": {...}}
보냄  {"envelope_id": "dbdd0ef3-..."}
```

연결은 오래 가지 않는다.

- 연결 직후 오는 `hello` 메시지의 `approximate_connection_time`(예: 3600초)이 연결이 유지될 대략의 시간이다. 몇 시간마다 새로 맺어야 한다.
- 끊기 10초쯤 전에 `disconnect` 경고가 오기도 하고, 경고 없이 `refresh_requested`로 끊기기도 한다.
- 앱 하나에 동시 연결은 10개까지이고, 이벤트는 열린 연결 중 아무 곳으로나 온다.

Bolt에서는 리스너를 그대로 두고 `SocketModeHandler(bolt, os.environ["SLACK_APP_TOKEN"]).start()`로 핸들러만 바꾼다. 슬랙 문서는 운영에는 HTTP를 권한다. 슬랙 쪽 웹소켓 서버 컨테이너가 가끔 교체되며 연결이 끊기고, 연결 상태를 들고 있어 수평 확장이 어렵기 때문이다. Socket Mode 앱은 공개 마켓플레이스에도 올릴 수 없다.

## 요청 서명 검증

Events API 주소는 인터넷에 열려 있어서, 주소만 알면 누구나 이벤트처럼 생긴 JSON을 POST할 수 있다. 검증하지 않으면 `/deploy rollback` 같은 명령을 아무나 흉내 낸다. 슬랙은 요청마다 앱의 signing secret으로 만든 서명을 헤더에 붙인다.

```text
X-Slack-Request-Timestamp: 1762916400
X-Slack-Signature:         v0=a2114d57b48eac39b9ad189dd8316235a7b4a8d21a10bd27519666489c69b503

basestring = "v0:" + 타임스탬프 + ":" + 요청 본문
서명       = "v0=" + HMAC-SHA256(signing secret, basestring)의 16진수
```

HMAC은 비밀 키와 메시지를 함께 해시하는 방식이라, 키를 모르면 본문에 맞는 서명을 만들 수 없다. 봇 서버는 같은 계산을 해서 헤더의 서명과 견준다. 아래 그림처럼 정상 요청은 통과하고, 위조 요청은 서명 비교에서, 복사해 다시 보낸 요청은 시각 검사에서 걸린다.

<figure class="fig" data-figure="slack-bot-signature">
  <figcaption>정상 요청, 위조 요청, 재전송 공격이 서명 검증을 지나는 모습</figcaption>
</figure>

지나간 정상 요청을 통째로 복사해 다시 보내면(재전송 공격, replay attack) 서명은 맞는다. 그래서 슬랙 문서는 타임스탬프가 현재 시각과 5분 넘게 차이 나는 요청을 버리라고 한다. 타임스탬프가 basestring에 들어가 있어서 시각만 고쳐 보내면 서명이 깨진다.

```python
def verify(secret: str, ts: str, body: bytes, sig: str) -> bool:
    if abs(time.time() - int(ts)) > 60 * 5:
        return False
    base = b"v0:" + ts.encode() + b":" + body
    mine = "v0=" + hmac.new(secret.encode(), base, hashlib.sha256).hexdigest()
    return hmac.compare_digest(mine, sig)
```

- 본문은 파싱하기 전의 바이트 그대로 쓴다. 이벤트는 JSON이지만 슬래시 명령과 버튼 클릭은 form-urlencoded(`a=1&b=2`처럼 HTML 폼이 쓰는 형식)로 오고, 어느 쪽이든 다시 직렬화하면 공백이나 순서가 바뀌어 서명이 맞지 않는다.
- 비교는 `hmac.compare_digest`로 한다. `==`는 다른 글자를 만나는 즉시 끝나서, 응답 시간 차이로 서명을 앞에서부터 추측할 틈을 준다.

Bolt의 `RequestVerification` 미들웨어가 이 검사를 하고, 실패하면 401과 `{"error": "invalid request"}`를 돌려준다. Socket Mode 요청은 이 검사를 건너뛴다. 연결을 열 때 `xapp-` 토큰으로 이미 인증했기 때문이다.

## 3초 응답 제한

### 응답 기한

서명을 통과한 요청에는 기한이 있다. 슬랙은 봇 서버의 응답을 3초까지만 기다리고, 넘기면 요청 종류에 따라 다르게 처리한다.

- 이벤트: 3초 안에 2xx가 없으면 실패로 보고 같은 이벤트를 다시 보낸다.
- 슬래시 명령: 3000ms 안에 응답이 없으면 명령을 친 사용자에게 `operation_timeout` 오류가 뜬다.
- 버튼, 메뉴 같은 인터랙션: 3초 안에 200이 없으면 사용자에게 오류가 보인다. 모달을 여는 `trigger_id`도 3초 뒤에 만료된다.

아래 그림처럼 3초가 지난 뒤에도 봇 서버는 일을 계속한다. 슬랙이 실패로 본 요청을 봇은 끝까지 처리하고 있어서, 양쪽이 아는 결과가 어긋난다.

  <figcaption>응답이 3초를 넘길 때 이벤트와 슬래시 명령이 겪는 일</figcaption>
</figure>

### ack 먼저 보내기

3초 안에 끝나지 않는 일은 순서를 바꾼다. 받았다는 응답(ack)을 먼저 보내고, 일은 그 뒤에 해서 결과를 따로 보낸다. 아래 데모에서 두 모드로 8초짜리 로그 모으기를 시켜, 슬랙 줄의 재전송과 채널에 달리는 답의 수를 견준다.

<figure class="fig" data-figure="slack-bot-ack">
  <figcaption>무거운 일을 받았을 때 응답 시점에 따른 차이</figcaption>
</figure>

처리 후 응답하면 3초가 지나 재전송이 오고, 봇은 같은 일을 한 번 더 해서 답을 두 번 단다. ack를 먼저 보내면 슬랙은 0.1초 만에 200을 받고 더 보내지 않는다. 두 모드 모두 결과는 8초 무렵에 나온다. 슬랙이 3초 동안 기다리는 것은 일의 결과가 아니라 **2xx 응답 하나**라서, 응답을 일보다 앞에 두면 8초짜리 일도 기한 안에 받은 요청이 된다.

Bolt for Python은 기본 설정에서 이 순서로 돈다.

- 이벤트: 리스너를 부르기 전에 ack를 보내고, 리스너는 스레드 풀에서 돈다.
- 명령과 인터랙션: 리스너가 `ack()`를 부르는 순간 HTTP 응답이 나가고, 나머지 코드는 그 뒤에 이어 돈다. Bolt는 `ack()`를 최대 3초(`ack_timeout=3`) 기다린다.

```python
@bolt.command("/deploy-log")
def deploy_log(ack, command, respond):
    ack("로그를 모으는 중이다")                  # 여기서 HTTP 응답이 나간다
    respond(collect_logs(command["text"]))        # 수십 초 걸려도 된다
```

리스너를 돌리는 스레드 풀은 기본 5개(`ThreadPoolExecutor(max_workers=5)`)다. 8초짜리 명령 5개가 돌고 있으면 여섯 번째 명령은 `ack()`를 부르기도 전에 빈 스레드를 기다리고, 3초를 넘기면 사용자는 `operation_timeout`을 본다.

스레드로 미룬 일은 프로세스가 재시작되면 함께 사라지기도 한다. 무거운 일이 몰리거나 놓치면 안 되는 봇은 ack 다음에 큐나 작업 테이블에 넣고 별도 워커가 처리하게 한다.

## 재시도와 중복 제거

ack를 먼저 보내도 같은 이벤트가 두 번 올 수 있다. 배포 중 재시작이나 네트워크 오류로 응답이 슬랙에 닿지 못하면, 슬랙은 같은 이벤트를 간격을 늘려 가며 최대 3번 더 보낸다.

```text
원본    실패 (3초 초과, 연결 실패, 2xx가 아닌 응답)
1회차   거의 즉시
2회차   1분 뒤
3회차   5분 뒤
```

재시도 요청에는 헤더 두 개가 붙는다.

- `X-Slack-Retry-Num`: 몇 번째 재시도인지(1, 2, 3)
- `X-Slack-Retry-Reason`: 이유. `http_timeout`(3초 초과), `connection_failed`(연결 실패), `http_error`(2xx가 아닌 응답), `ssl_error` 등

`X-Slack-Retry-Num`이 있으면 버리면 되지 않나 싶지만, 이유가 `connection_failed`면 원본이 봇에 닿지도 못한 경우다. 헤더만 보고 버리면 그 이벤트는 아무도 처리하지 않는다. 그래서 헤더가 아니라 봉투의 `event_id`로 거른다. 아래 데모에서 두 모드로 재전송을 일으켜, 채널에 달리는 답의 수를 견준다.

<figure class="fig" data-figure="slack-bot-dedup">
  <figcaption>원본과 재시도 세 번을 event_id로 거를 때와 거르지 않을 때</figcaption>
</figure>

거르지 않으면 원본과 재시도 세 번이 모두 리스너를 지나 답이 네 번 달린다. event_id로 거르면 처음 본 id만 저장소에 남겨 통과시키고 나머지는 200만 돌려준다. 슬랙은 앞선 전달이 처리됐는지 알 길이 없어 네 번을 그대로 보내므로, 중복은 이미 본 id를 기억하는 봇 쪽에서만 끊을 수 있다.

```python
r = redis.Redis()

@bolt.event("app_mention")
def on_mention(body, event, say):
    if not r.set(f"slack:event:{body['event_id']}", 1, nx=True, ex=3600):
        return                                     # 이미 처리한 이벤트
    say(text=status_of(event["text"]), thread_ts=event["ts"])
```

Redis의 `SET NX`는 키가 없을 때만 쓰고 성공 여부를 돌려준다. 확인과 쓰기가 한 명령 안에서 끝나 사이에 다른 요청이 끼어들 수 없어서, 서버 여러 대가 같은 재시도를 동시에 받아도 한 곳만 통과한다. 프로세스 메모리 안의 set은 서버가 여러 대이거나 재시작하면 기억을 잃는다. 재시도는 5분 남짓이면 끝나서 보관 시간은 1시간이면 넉넉하다.

실패가 쌓일 때 쓰는 값이 두 가지 더 있다.

- 일부러 실패를 돌려주면서 재시도는 막고 싶으면 응답에 `X-Slack-No-Retry: 1`을 붙인다.
- 60분 동안 전달 시도의 95% 넘게 실패하면 슬랙이 이벤트 구독을 잠시 끄고 앱 소유자에게 메일을 보낸다. 시간당 이벤트가 1,000건 미만인 앱은 자동으로 꺼지지 않는다.

Socket Mode도 ack가 오지 않은 이벤트는 다시 보내므로, 같은 방식으로 `event_id`를 거른다.

## 답 보내기

### 응답 경로와 권한

답이 채널로 돌아가는 길은 두 가지다.

- `response_url`: 슬래시 명령과 인터랙션 요청에 딸려 오는 임시 웹훅 주소다. 받은 뒤 30분 안에 5번까지 쓸 수 있고 토큰이 필요 없다. 기본은 명령을 친 사람에게만 보이는 ephemeral이고, `response_type`을 `in_channel`로 주면 채널 모두에게 보인다. Bolt의 `respond()`가 이 주소를 쓴다.
- Web API: 봇 토큰(`xoxb-`)을 `Authorization: Bearer` 헤더에 실어 `chat.postMessage`를 부른다. 기한은 없지만 토큰의 권한(scope)과 봇이 들어가 있는 채널이 정한 범위 안에서만 쓸 수 있다. Bolt의 `say()`가 이쪽이다.

이벤트에는 `response_url`이 없어서 멘션에 대한 답은 Web API로 쓴다. Web API는 실패하면 응답의 `ok`가 false이고 `error`에 이유가 담긴다. 아래 그림처럼 같은 봇 토큰이라도 채널과 권한에 따라 통과하기도 하고 오류가 나기도 한다.

</figure>

- `not_in_channel`: `chat:write`만으로는 봇이 들어가 있는 채널에만 쓸 수 있다. 봇을 채널에 초대하거나, 공개 채널 전체에 쓰는 `chat:write.public`을 더 받는다.
- `missing_scope`: 받지 않은 권한이 필요한 메서드를 불렀다. 채널 기록을 읽는 `conversations.history`는 `channels:history`가 있어야 한다.

scope를 넓게 잡으면 토큰이 샐 때 피해도 그만큼 크다. 오류 이름을 보고 필요한 scope만 하나씩 더한다.

### 호출 한도

Web API는 메서드마다 호출 한도가 있고, 워크스페이스와 앱 조합마다 따로 센다. 대부분의 메서드는 네 등급(tier) 중 하나에 속한다.

- Tier 1: 분당 1회 이상
- Tier 2: 분당 20회 이상
- Tier 3: 분당 50회 이상
- Tier 4: 분당 100회 이상

`chat.postMessage`는 등급 대신 특별 한도를 따른다. 한 채널에 초당 1개 정도이고 짧은 몰림은 허용하며, 워크스페이스 전체 한도가 따로 있다. 수신 웹훅도 초당 1개다. 배포 알림 60개를 한 채널에 보내려면 1분에 걸쳐 나눠 보내야 하는 셈이다.

한도를 넘으면 HTTP 429와 함께 몇 초 뒤에 다시 부를지 적은 `Retry-After` 헤더가 온다. Python SDK의 `WebClient`는 기본으로 연결 오류만 재시도해서, 429를 받고 기다리려면 핸들러를 더해야 한다.

```python
from slack_sdk.http_retry.builtin_handlers import RateLimitErrorRetryHandler

client = WebClient(token=os.environ["SLACK_BOT_TOKEN"])
client.retry_handlers.append(RateLimitErrorRetryHandler(max_retry_count=2))
```

이 핸들러는 `Retry-After`만큼 기다린 뒤 다시 부르고, 그동안 호출한 스레드도 묶인다. 알림이 몰리는 봇은 큐에 넣고 채널마다 초당 1개씩 꺼내 보낸다.

받는 쪽에도 한도가 있다. Events API는 워크스페이스마다 앱 하나에 60분 동안 3만 건까지 전달하고, 넘으면 매분 `app_rate_limited` 이벤트로 알린다.
