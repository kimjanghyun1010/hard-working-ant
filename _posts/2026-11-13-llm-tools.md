## 토큰

### 토큰 단위

질문 수는 그대로인데 이번 달 API 요금이 두 배로 나왔다. LLM API는 요청 수가 아니라 토큰(token) 수로 요금을 매기고, 토큰 수는 프롬프트에 무엇을 실었는지에 따라 달라진다.

토큰은 모델이 글을 읽고 쓰는 단위다. 단어보다 작은 조각이고, 어디서 자를지는 모델의 토크나이저가 정한다. 같은 문장도 모델마다 토큰 수가 다르다.

- 입력 토큰: 시스템 지시, 이전 대화, 붙인 문서, 도구 정의까지 모델에 보내는 전부
- 출력 토큰: 모델이 새로 만든 답

문장이 토큰으로 쪼개진 뒤, 답이 토큰 하나씩 붙어 나오는 순서를 살펴보자.

<figure class="fig" data-figure="llm-tools-token">
  <figcaption>토큰으로 나뉘는 입력과 하나씩 생성되는 출력 (조각은 예시)</figcaption>
</figure>

모델은 답을 한 번에 만들지 않는다. 지금까지의 토큰을 보고 다음 토큰 하나를 고르고, 그 토큰을 붙여 다시 다음 토큰을 고른다. 그래서 답이 길수록 그만큼 오래 걸린다.

요금도 입력 토큰과 출력 토큰에 단가를 따로 매긴다. 응답의 `usage` 필드에 요청마다 두 수가 찍히니, 청구서가 늘었다면 요청 수보다 요청 하나의 입력과 출력 토큰부터 나눠 본다.

### 컨텍스트 창

챗봇이 처음엔 빠르다가 대화가 길어질수록 느려지고, 어느 순간 앞에서 한 말을 잊는다. 모델은 이전 대화를 기억하지 않아서, 앱이 요청마다 대화 전체를 다시 보낸다.

컨텍스트 창(context window)은 요청 하나에 담을 수 있는 토큰의 상한이다. 넘으면 요청이 거절되거나 앞부분이 잘린다. 어느 쪽인지는 API와 서버 설정에 따라 다르다.

아래 그림은 시스템 지시 500토큰, 질문 100토큰, 답 500토큰인 대화를 창 4,096토큰 안에서 이어 간다. 턴마다 막대가 얼마나 길어지는지, 7번째 질문에서 무슨 일이 생기는지 본다.

<figure class="fig" data-figure="llm-tools-context">
  <figcaption>질문마다 다시 보내는 대화 기록 (토큰 수는 예시)</figcaption>
</figure>

1턴에 600토큰이던 입력이 7턴에는 4,200토큰이 되어 창을 넘는다. 질문 하나는 100토큰인데, 7번 묻는 동안 보낸 입력은 다 합쳐 16,800토큰이다. 대화가 길어지면 비용은 턴 수보다 빠르게 는다.

- 오래된 대화는 요약해서 짧게 바꿔 넣는다.
- 창 크기는 모델의 최대치만이 아니라 서버 설정으로도 정해진다. 로컬 서버는 기본값이 작을 수 있다.

긴 대화가 느려지면 요청 하나의 입력 토큰이 턴마다 어떻게 늘었는지부터 본다.

### 문서 검색 결합

사내 문서로 답하는 챗봇을 만들면서 문서를 통째로 프롬프트에 붙이면, 질문 한 줄이 수만 토큰짜리 요청이 된다. 원글에서는 Jenkins 문서를 긁어 와 이 문제를 검색으로 풀었다.

검색 결합 생성(RAG, retrieval-augmented generation)은 질문과 가까운 문서 조각만 골라 프롬프트에 넣는 방식이다.

1. 문서를 조각으로 나누고, 조각마다 임베딩 모델로 벡터를 만들어 저장한다.
2. 질문이 오면 질문도 벡터로 바꾸고, 가장 가까운 조각 몇 개를 찾는다.
3. 찾은 조각과 질문을 합쳐 모델에 보낸다.

유사도 검색은 모델이 아니라 앱이 한다. 모델은 앱이 골라 준 조각만 보고 답한다.

모드를 바꿔 가며 질문을 보내 본다. 가운데 입력 막대가 얼마나 차는지, 맨 아래 입력 처리 막대가 얼마나 길어지는지 견줘 본다.

<figure class="fig" data-figure="llm-tools-rag">
  <figcaption>문서를 통째로 넣을 때와 관련 조각만 넣을 때 (토큰 수는 예시)</figcaption>
</figure>

통째로 넣으면 40조각 20,000토큰에 지시와 질문 600토큰을 더해 20,600토큰이다. 관련 조각 3개만 넣으면 2,100토큰으로 약 10분의 1이다. 질문은 같고, 바뀌는 건 **모델이 읽어야 할 양**뿐이다.

```python
q = client.embeddings.create(model=EMBED, input=[question]).data[0].embedding
_, idx = index.search(np.array([q]), 3)   # faiss 인덱스에서 가까운 조각 3개
context = "\n\n".join(chunks[i] for i in idx[0])
```

조각을 너무 잘게 자르면 답에 필요한 맥락이 끊기고, 너무 크게 자르면 다시 입력이 커진다. 답이 엉뚱하면 모델보다 검색이 고른 조각이 맞는지부터 본다.

## API 호출

### 호출 한 번의 흐름

같은 모델에 같은 질문을 했는데, 문서를 붙이자 답이 늦게 시작한다. 답이 나오기까지는 두 단계를 거치고, 단계마다 시간을 정하는 것이 다르다.

- 입력 처리(prefill): 입력 토큰 전부를 한꺼번에 읽는다. GPU가 병렬로 처리하지만 입력이 길수록 오래 걸린다.
- 생성(decode): 출력 토큰을 하나씩 만든다. 앞 토큰이 있어야 다음 토큰을 고를 수 있어 병렬로 못 한다.

그래서 지연은 두 숫자로 나눠 본다.

- 첫 토큰까지 시간(TTFT, time to first token): 대부분 입력 처리 시간이라 입력 길이를 따라간다.
- 토큰 생성 속도: 초당 출력 토큰 수. 출력이 길면 끝나는 시각이 뒤로 밀린다.

두 장면에서 출력 토큰 40개는 같고 입력 길이만 다르다. 빨간 점선이 어디에 찍히는지 본다.

<figure class="fig" data-figure="llm-tools-flow">
  <figcaption>입력 길이에 따라 달라지는 첫 토큰 시각 (시간은 모양을 보여 주는 대략값)</figcaption>
</figure>

입력이 600토큰이면 0.3초, 20,600토큰이면 1.3초에 첫 토큰이 나온다. 토큰 40개를 만드는 2.4초는 두 장면이 같다. 입력이 길면 시작이 늦고, 출력이 길면 끝이 늦다.

응답이 느리다는 말이 나오면 첫 토큰까지 시간과 생성 시간을 나눠 잰다. 앞쪽이 길면 입력을 줄이고, 뒤쪽이 길면 출력 길이 상한이나 답 형식을 손본다.

### 스트리밍

같은 답을 3초에 받아도 사용자는 빈 화면 3초를 길게 느낀다. 스트리밍(streaming)은 토큰을 끝까지 모으지 않고 만들어지는 대로 보내는 방식이다.

OpenAI 형식 API에서는 요청에 `stream: true`를 주면 응답이 SSE(server-sent events)로 조각조각 온다. Responses API에서는 글자 조각이 `response.output_text.delta` 이벤트로 온다.

모드를 바꿔 가며 질문을 보내 본다. 화면에 첫 글자가 뜨는 순간과 모델이 일을 끝내는 순간을 견줘 본다.

<figure class="fig" data-figure="llm-tools-stream">
  <figcaption>한 번에 받기와 스트리밍의 화면 (시간은 대략값)</figcaption>
</figure>

한 번에 받으면 3초 동안 빈 화면을 보다가 답이 통째로 뜬다. 스트리밍이면 0.3초에 첫 글자가 보인다. 모델이 일하는 시간은 같고, 바뀌는 건 **사용자가 기다리는 동안 보는 것**뿐이다.

스트리밍에도 챙길 것이 있다.

- 중간에 연결이 끊기면 앞부분만 받은 상태가 된다. 끊김을 처리하는 코드가 필요하다.
- 내용 검사(moderation) 결과는 답이 다 나온 뒤에야 나와서, 조각 단위로 거르기 어렵다.
- 사이에 프록시가 있으면 버퍼링 때문에 조각이 모였다가 한꺼번에 온다. nginx라면 응답에 `X-Accel-Buffering: no`를 붙인다.

사람이 읽는 화면은 스트리밍으로 받고, 다른 프로그램이 받아 쓰는 응답은 통째로 받는다.

### 프롬프트 캐시

시스템 지시와 도구 정의가 3,000토큰인데 질문은 50토큰이다. 요청마다 앞의 3,000토큰을 처음부터 다시 처리하면 첫 토큰이 그만큼 늦다.

프롬프트 캐시(prompt caching)는 앞부분이 똑같은 요청이 오면 처리해 둔 결과를 다시 쓴다. 앞부분 전체가 글자 하나까지 같아야 하고, 재사용한 입력 토큰은 할인된 단가로 계산한다.

세 요청을 나란히 놓았다. 요청 2와 요청 3의 주황 막대 길이를 견줘 본다.

<figure class="fig" data-figure="llm-tools-cache">
  <figcaption>앞부분이 같은 요청과 앞부분이 바뀐 요청 (시간은 대략값)</figcaption>
</figure>

요청 2는 요청 1과 앞부분이 같아 새 질문만 처리하고 바로 답을 시작한다. 요청 3은 맨 앞에 현재 시각을 넣은 경우다. 한 글자만 달라도 처음부터 다시 처리한다.

- 바뀌지 않는 것(시스템 지시, 도구 정의, 고정 문서)을 앞에 둔다.
- 바뀌는 것(시각, 사용자 이름, 질문)을 뒤에 둔다.
- 도구 목록도 매번 같은 순서로 넣는다. MCP 사양도 캐시 적중률을 이유로 서버가 도구를 같은 순서로 돌려주라고 권한다.

캐시가 안 맞으면 프롬프트를 만드는 코드가 맨 앞에 시각이나 요청 ID를 붙이고 있지 않은지부터 본다.

## 도구 호출

### 도구 호출 루프

"서울 날씨 알려줘"라고 물으면 모델은 지금 날씨를 모른다. 학습 뒤에 생긴 정보나 내 DB 안의 데이터는 모델 혼자 답할 수 없다.

도구 호출(tool calling)은 모델이 답 대신 "이 함수를 이 인자로 불러 달라"는 요청을 돌려주게 하는 방식이다.

1. 앱이 질문과 함께 쓸 수 있는 도구 목록(이름, 설명, 인자 스키마)을 보낸다.
2. 모델이 도구 호출 요청(함수 이름과 JSON 인자)을 돌려준다.
3. 앱이 그 함수를 실행한다.
4. 앱이 실행 결과를 대화에 붙여 모델을 다시 부른다.
5. 모델이 결과를 읽고 답하거나, 도구를 또 부른다.

세 장면에서 칩이 누구를 거쳐 가는지, 아래 상자에 무엇이 쌓이는지 본다.

<figure class="fig" data-figure="llm-tools-loop">
  <figcaption>도구 호출 한 번의 왕복</figcaption>
</figure>

모델은 함수를 실행하지 않는다. 모델이 내놓는 건 호출 요청이라는 글이고, 실행은 앱이 한다. 그래서 어떤 도구를 줄지, 실행 전에 사용자에게 물을지도 앱이 정한다.

```python
tools = [{
    "type": "function", "name": "get_weather", "description": "도시의 현재 날씨",
    "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
}]
resp = client.responses.create(model=MODEL, input=items, tools=tools)
for call in (o for o in resp.output if o.type == "function_call"):
    result = get_weather(**json.loads(call.arguments))      # 실행은 앱이 한다
    items += [call, {"type": "function_call_output", "call_id": call.call_id, "output": json.dumps(result)}]
resp = client.responses.create(model=MODEL, input=items, tools=tools)
```

도구 정의도 입력 토큰이다. 도구를 30개 붙이면 질문 한 줄에도 30개의 설명이 매번 같이 간다. 도구는 그 기능에 필요한 것만 붙이고, 지우기나 결제처럼 되돌릴 수 없는 도구는 실행 전에 사용자 확인을 받는다.

### 왕복 횟수

에이전트에게 "지난주 장애 원인 정리해 줘"라고 시키면 답이 나오기까지 한참 걸린다. 도구를 한 번 쓸 때마다 모델 호출이 한 번씩 늘기 때문이다.

아래는 도구를 두 번 쓰고 답하는 질문 하나의 시간축이다. 모델 줄의 주황 블록이 몇 번 나오는지, 뒤로 갈수록 길어지는지 본다.

<figure class="fig" data-figure="llm-tools-rounds">
  <figcaption>도구를 두 번 쓰는 질문의 시간축 (시간은 대략값)</figcaption>
</figure>

모델을 세 번 불렀고, 부를 때마다 앞의 호출 요청과 도구 결과가 대화에 붙어 입력 처리가 길어졌다. 도구 실행 시간에 모델 호출 시간이 더해지고, 도구 결과가 길면 다음 호출의 입력도 그만큼 커진다.

- 도구 결과는 모델이 읽을 만큼만 돌려준다. DB 행 1만 개를 그대로 넣지 않는다.
- 서로 기다릴 필요 없는 도구는 한 번에 여러 개를 부르게 한다(`parallel_tool_calls`).
- 왕복 횟수에 상한을 둔다. 모델이 같은 도구를 되풀이해 부를 때가 있다.

에이전트가 느리면 전체 시간보다 왕복 횟수와 왕복마다의 입력 토큰부터 센다.

## MCP

### 호스트, 클라이언트, 서버

같은 날씨 도구를 Cursor에도, 다른 AI 편집기에도, 사내 챗봇에도 붙이려면 앱마다 연결 코드를 따로 짜야 한다. MCP(Model Context Protocol)는 이 연결을 규격으로 맞춘다. 도구를 MCP 서버로 한 번 만들면 MCP를 지원하는 어느 앱에서나 쓸 수 있다.

역할은 셋이다.

- 호스트: 사용자가 쓰는 LLM 앱(Cursor 등). 모델을 부르고, 사용자 동의를 받고, 도구 목록을 모은다.
- 클라이언트: 호스트 안에서 서버 하나와의 연결을 맡는다. 서버마다 하나씩 1:1로 있다.
- 서버: 도구(tools), 리소스(resources), 프롬프트(prompts)를 내놓는 프로그램. 파일, Unity 에디터, DB 같은 실제 대상을 다룬다.

메시지 형식은 JSON-RPC 2.0이고, 도구에 쓰는 메서드는 둘이다.

- `tools/list`: 서버가 가진 도구의 이름, 설명, 입력 스키마를 받는다.
- `tools/call`: 도구 이름과 인자를 보내 실행하고 결과를 받는다.

두 장면에서 tools/list로 도구를 모으는 길과, tools/call 한 번이 어느 서버로 가는지 따라가 보자.

<figure class="fig" data-figure="llm-tools-mcp">
  <figcaption>호스트 하나에 서버마다 클라이언트 하나</figcaption>
</figure>

MCP가 바꾼 건 앞 절 루프의 3번, 앱이 도구를 찾고 실행하는 방법이다. 루프는 그대로 호스트가 돌리고, 도구를 찾고 부르는 방법만 표준이 됐다. 서버는 대화 전체를 보지 못하고 자기에게 온 호출의 인자만 받는다.

사양은 날짜로 버전을 매기고 지금 최신은 2026-07-28 개정이다. 이 개정에서 연결 처음에 주고받던 `initialize` 핸드셰이크와 세션이 빠지고, 요청마다 프로토콜 버전을 싣는 상태 없는(stateless) 방식이 됐다. 서버의 버전과 기능은 `server/discover`로 묻는다.

호스트 설정 파일(Cursor의 `mcp.json`)에는 도구 함수가 아니라 **서버를 띄우는 명령**을 적는다. 도구 목록은 서버를 띄운 뒤 `tools/list`로 받아 온다.

```json
{
  "mcpServers": {
    "unityMCP": {
      "command": "uv",
      "args": ["--directory", "<unity-mcp 경로>/Python", "run", "server.py"]
    }
  }
}
```

원글에서 켠 자동 실행(YOLO) 모드는 도구 호출마다 묻는 확인을 건너뛴다. MCP 사양은 사람이 도구 호출을 거부할 수 있어야 한다고 권한다. 파일을 지우거나 명령을 실행하는 서버를 붙였다면 자동 실행은 버려도 되는 작업 폴더에서만 켠다.

서버를 붙였는데 도구가 안 보이면 설정 파일의 명령이 터미널에서 그대로 실행되는지부터 본다.

### 전송 방식

MCP 서버 설정이 어떤 건 `command`이고 어떤 건 `url`이다. 서버가 같은 PC에서 도는지, 다른 서버에서 도는지에 따라 전송 방식이 다르다.

- stdio: 호스트가 서버를 자식 프로세스로 띄우고, 표준 입력(stdin)과 표준 출력(stdout)으로 JSON-RPC 메시지를 한 줄씩 주고받는다. 로그는 표준 에러(stderr)로 쓴다.
- Streamable HTTP: 서버가 독립 프로세스로 HTTP 엔드포인트 하나(예: `/mcp`)를 연다. 클라이언트는 메시지마다 POST를 보내고, 서버는 JSON 하나나 그 요청 전용 SSE 스트림으로 답한다.

예전 HTTP+SSE 전송(2024-11-05 사양)은 2025-03-26부터 폐기 예정(deprecated)이고 Streamable HTTP로 바뀌었다. 새로 만든다면 Streamable HTTP로 한다.

두 장면에서 메시지가 오가는 길을 견줘 본다.

<figure class="fig" data-figure="llm-tools-transport">
  <figcaption>같은 PC의 stdio와 원격 서버의 Streamable HTTP</figcaption>
</figure>

stdio는 설정이 간단하고 네트워크를 거치지 않지만, 서버가 호스트와 같은 PC에 있어야 한다. Streamable HTTP는 여러 사용자가 원격 서버 하나를 같이 쓸 수 있는 대신 인증과 접근 제어를 직접 챙겨야 한다.

- stdio 서버는 표준 출력에 MCP 메시지가 아닌 것을 쓰면 안 된다. 디버그 메시지를 `print`로 찍으면 호스트가 메시지를 못 읽는다.
- 로컬에서 HTTP 서버를 띄운다면 `127.0.0.1`에만 열고 `Origin` 헤더를 검사한다. 사양이 DNS 리바인딩 공격을 막으려고 요구하는 것이다.

stdio 서버가 갑자기 끊기면 서버 코드의 표준 출력 로그부터 찾는다.

## 로컬 실행

### 모델 크기와 GPU 메모리

`ollama run llama3:70b`로 받은 모델이 답을 아주 느리게 낸다. 모델이 GPU 메모리에 다 들어가지 못해서, 못 들어간 몫을 CPU 쪽에서 처리하고 있다.

모델 파일은 대부분 파라미터(가중치)다. 필요한 메모리는 파라미터 수에 파라미터 하나의 바이트 수를 곱해 어림한다.

```text
8B  모델, FP16(2바이트)  →  80억 × 2  ≈ 16GB
70B 모델, FP16(2바이트)  →  700억 × 2 ≈ 140GB
```

두 장면에서 막대가 GPU 24GB 점선을 넘는지 본다.

<figure class="fig" data-figure="llm-tools-weights">
  <figcaption>정밀도별 모델 크기와 GPU 24GB</figcaption>
</figure>

8B 모델은 FP16 16GB라 24GB GPU에 들어간다. 70B 모델은 4비트로 줄여도 40GB라 GPU 하나에 들어가지 않는다. 원글의 "4.7GB 버전"과 "40GB 버전"은 둘 다 4비트로 줄인 파일이다.

크기는 Ollama 라이브러리의 llama3 태그(`fp16`, `q8_0`, `q4_0`) 값이다. 실제로 쓰는 메모리는 여기에 뒤에 나올 KV 캐시와 런타임 몫이 더해진다.

로컬 모델은 성능표보다 GPU 메모리부터 보고, 파라미터 수와 정밀도로 들어가는지 먼저 계산한다.

### 양자화

GPU 메모리가 12GB인 PC에서 8B 모델을 돌리려 한다. FP16 그대로는 16GB라 넘친다.

양자화(quantization)는 파라미터 하나를 더 적은 비트로 저장하는 방법이다. 16비트를 8비트로 줄이면 크기가 절반, 4비트면 4분의 1 남짓이 된다. 대신 표현할 수 있는 값이 거칠어져 답의 품질이 조금 떨어질 수 있다.

정밀도를 바꿔 가며 모델을 올려 본다. 파란 가중치 칸이 GPU 칸을 넘어 아래 시스템 메모리로 넘치는지 지켜보자.

<figure class="fig" data-figure="llm-tools-quant">
  <figcaption>GPU 12GB에 8B 모델 올리기</figcaption>
</figure>

FP16은 16GB 중 4GB가 GPU에 못 들어가 시스템 메모리로 밀려난다. 4비트는 4.7GB라 GPU에 다 들어가고 7GB가 남는다. 모델의 구조와 파라미터 수는 같고, 바뀐 건 **파라미터 하나에 쓰는 비트 수**뿐이다.

양자화는 속도에도 영향을 준다. 생성 단계는 토큰 하나를 만들 때마다 가중치를 메모리에서 읽어야 해서, 계산보다 메모리에서 읽어 오는 속도가 병목이다. 읽을 바이트가 줄면 토큰도 빨리 나오는 경우가 많다.

Ollama에서 `llama3:8b`처럼 정밀도를 적지 않으면 `q4_0` 파일을 받는다. 다른 정밀도는 `llama3:8b-instruct-q8_0`처럼 태그로 고른다.

모델이 느리면 `ollama ps`의 PROCESSOR 열부터 본다. `100% GPU`가 아니면 일부가 CPU 쪽으로 넘어간 것이다.

### KV 캐시

모델이 GPU에 다 들어가는데도 컨텍스트 길이를 늘리자 GPU 메모리가 모자라다. 컨텍스트에도 메모리가 든다.

모델은 다음 토큰을 만들 때마다 앞 토큰 전부를 참고한다. 매번 다시 계산하지 않으려고 앞 토큰의 중간 결과(key와 value)를 GPU 메모리에 쌓아 두는데, 이것이 KV 캐시다. 크기는 토큰 수에 비례한다.

```text
KV 캐시 = 2 × 레이어 수 × hidden 크기 × 바이트 × 토큰 수
Llama 2 7B, FP16  →  2 × 32 × 4096 × 2바이트 = 토큰당 0.5MB
4,096토큰 → 2GB,  32,768토큰 → 16GB
```

컨텍스트를 0에서 32k까지 늘리며 보라 선이 빨간 점선을 넘는 지점을 본다.

<figure class="fig" data-figure="llm-tools-kv">
  <figcaption>컨텍스트 길이에 따른 GPU 메모리 (Llama 2 7B FP16, 요청 하나)</figcaption>
</figure>

가중치 14GB는 그대로인데 KV 캐시가 늘어 약 2만 토큰에서 24GB를 넘긴다. 32k에서는 KV 캐시만 16GB로 가중치보다 크다. 동시 요청을 받으면 요청마다 KV 캐시가 따로 생겨 이 값에 요청 수를 곱한다.

- Ollama는 GPU 메모리에 따라 기본 컨텍스트 길이를 정한다. 24GiB 미만이면 4k다. 늘리려면 `OLLAMA_CONTEXT_LENGTH`를 바꾼다.
- KV 캐시도 양자화할 수 있다. Ollama는 Flash Attention을 켠 상태에서 `OLLAMA_KV_CACHE_TYPE`을 `q8_0`이나 `q4_0`으로 둔다.
- vLLM은 PagedAttention으로 KV 캐시를 블록 단위로 나눠 관리해, 동시 요청이 많을 때 메모리를 덜 버린다.

컨텍스트 길이는 필요한 만큼만 잡고, 늘릴 때는 가중치와 KV 캐시가 GPU 메모리에 같이 들어가는지 계산한다.

### OpenAI 호환 API

클라우드 API로 만든 챗봇을 로컬 모델로 바꿔 보려는데, 원글처럼 웹 UI를 따로 띄울 필요는 없다. Ollama, llama.cpp, vLLM이 모두 OpenAI 형식의 API를 연다. 클라우드용으로 짠 코드에서 주소만 바꾸면 로컬 모델에 붙는다.

Azure OpenAI도 2025년 8월부터 v1 API를 연다. 예전에는 `api_version="2023-03-15-preview"`처럼 날짜 붙은 버전을 코드에 적고 Azure 전용 클라이언트를 썼다. v1은 주소 끝에 `/openai/v1/`을 붙이고 날짜 버전 없이 OpenAI 기본 클라이언트로 부른다.

두 장면에서 앱은 그대로 두고 아래 `base_url`만 바뀌는 것을 본다.

<figure class="fig" data-figure="llm-tools-local">
  <figcaption>같은 클라이언트 코드로 부르는 클라우드 API와 로컬 서버</figcaption>
</figure>

```python
from openai import OpenAI

cloud = OpenAI(base_url="https://<리소스>.openai.azure.com/openai/v1/", api_key=AZURE_KEY)
local = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")  # Ollama는 키를 보지 않는다

resp = local.chat.completions.create(model="llama3:8b", messages=[{"role": "user", "content": "배포가 느린 이유?"}])
```

세 도구의 쓰임은 이렇게 갈린다.

- Ollama: 모델 내려받기, GPU 배치, API 서버를 한 번에 해 준다. 혼자 쓰는 PC에 맞다.
- llama.cpp: 여러 하드웨어에서 돌아가는 C/C++ 추론 엔진. GGUF 파일을 읽고 OpenAI 호환 서버를 띄운다.
- vLLM: 여러 사용자의 동시 요청을 받는 서버용 엔진. 들어오는 요청을 이어서 묶어 처리하는 continuous batching과 PagedAttention으로 처리량을 높인다.

Ollama는 기본으로 `127.0.0.1:11434`에만 열린다. `OLLAMA_HOST`로 바깥에 열 때는 원글처럼 앞단에 인증을 둔다.

혼자 써 볼 때는 Ollama로 시작하고, 여러 사람이 같이 쓰는 서버가 되면 vLLM 같은 서버용 엔진을 검토한다.

## 정리

| | 정하는 것 | 기억할 점 |
|---|---|---|
| 입력 토큰 | 요금, 첫 토큰까지 시간 | 대화 기록, 붙인 문서, 도구 정의가 매번 같이 간다 |
| 출력 토큰 | 요금, 끝나는 시각 | 하나씩 만든다. 길이 상한을 둔다 |
| 컨텍스트 창 | 요청 하나에 담는 양 | 넘으면 거절되거나 앞부분이 잘린다 |
| 검색 결합 | 넣을 문서의 양 | 관련 조각만 넣는다. 검색은 앱이 한다 |
| 스트리밍 | 체감 지연 | 총 시간은 같다. 사람이 읽는 화면에 쓴다 |
| 프롬프트 캐시 | 반복되는 앞부분의 처리 | 고정 내용은 앞에, 바뀌는 내용은 뒤에 |
| 도구 호출 | 모델이 바깥 시스템을 쓰는 방법 | 실행은 앱이 한다. 왕복마다 모델 호출 한 번 |
| MCP | 도구 연결 규격 | 호스트, 클라이언트, 서버. stdio와 Streamable HTTP |
| GPU 메모리 | 로컬 실행 가능 여부 | 파라미터 수 × 바이트에 KV 캐시를 더한다 |
| 양자화 | 모델 크기와 생성 속도 | 4비트면 FP16의 4분의 1 남짓 |
