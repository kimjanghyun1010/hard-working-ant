## 컨텍스트 창과 토큰

LLM은 학습으로 굳은 가중치와 이번 요청에 실린 글만 보고 답한다. 사내 문서나 지금 날씨처럼 학습에 없던 것을 쓰게 하려면 앱이 그 내용을 요청에 실어 주거나 모델 대신 가져다줘야 한다.

모델이 읽고 쓰는 단위는 토큰(token)이다. 단어보다 작은 조각이고 어디서 자를지는 모델마다 다른 토크나이저가 정한다. 요청 하나에 담을 수 있는 토큰의 상한을 컨텍스트 창(context window)이라 하고, 시스템 지시, 이전 대화, 붙인 문서, 도구 정의, 새로 만들 답까지 모두 이 안에 들어가야 한다.

모델은 이전 요청을 기억하지 않는다. 대화가 이어지는 것처럼 보이는 건 앱이 요청마다 대화 전체를 다시 싣기 때문이다. 아래 그림처럼 질문은 100토큰이어도 입력은 턴마다 600토큰씩 늘어 7번째에 창 4,096을 넘는다.

<figure class="fig" data-figure="llm-tools-context">
  <figcaption>질문마다 다시 보내는 대화 기록 (토큰 수는 예시)</figcaption>
</figure>

넘치면 API는 요청을 거절하거나 앞부분을 잘라 낸다. 창은 모델의 최대치만이 아니라 서버 설정으로도 정해진다. Ollama는 GPU 메모리가 24GiB 미만이면 기본 창을 4k로 잡아서, 모델 카드에 128k라고 적혀 있어도 4k 밖은 보지 못한다.

실은 양은 시간도 정한다. 답은 두 단계를 거쳐 나온다.

- 입력 처리(prefill): 입력 토큰 전부를 한꺼번에 읽어 토큰마다 key와 value라는 벡터 한 쌍을 만든다. 뒤 토큰은 key로 앞 토큰 중 어디를 참고할지 고르고 value에서 내용을 가져온다. GPU 연산을 꽉 채우는 단계라 입력이 길수록 오래 걸린다.
- 생성(decode): 답을 토큰 하나씩 만든다. 토큰마다 가중치를 메모리에서 다시 읽어야 해서 연산보다 메모리 대역폭이 속도를 정한다.

아래 그림은 출력 40토큰은 같고 입력만 600토큰과 20,600토큰으로 다른 두 요청이다.

<figure class="fig" data-figure="llm-tools-flow">
  <figcaption>입력 길이에 따라 달라지는 첫 토큰 시각 (시간은 모양을 보여 주는 대략값)</figcaption>
</figure>

첫 토큰까지 시간(TTFT, time to first token)은 입력 길이를 따라가고, 끝나는 시각은 출력 길이를 따라간다. 요금도 입력과 출력 토큰에 따로 매긴다. 문서를 통째로 붙이면 창에 들어가더라도 질문마다 수만 토큰의 값과 시간을 치른다.

## 검색 결합 생성

입력 처리 시간과 요금이 실은 토큰 수를 따라가므로, 줄일 곳은 실을 양이다. 검색 결합 생성(RAG, retrieval-augmented generation)은 문서 전체가 아니라 질문과 가까운 조각만 골라 싣는다. 가까움을 계산하려면 글을 숫자로 바꿔야 하고, 이 일을 임베딩(embedding) 모델이 한다.

임베딩은 글 한 덩어리를 길이가 정해진 숫자 배열(벡터)로 바꾼 것이다. OpenAI `text-embedding-3-small`은 1,536개, `text-embedding-3-large`는 3,072개의 숫자를 돌려준다. 뜻이 비슷한 글은 벡터 방향도 비슷해서, 두 벡터 사이 각도의 코사인(cosine similarity)으로 가까움을 잰다. 1이면 같은 방향, 0이면 무관하다.

1. 문서를 조각(chunk)으로 자르고 조각마다 임베딩을 만들어 저장한다.
2. 질문이 오면 질문도 임베딩으로 바꾸고 가장 가까운 조각 k개를 찾는다.
3. 찾은 조각과 질문을 합쳐 모델에 보낸다.

검색은 모델이 아니라 앱이 하고, 모델은 앱이 골라 넣은 조각만 본다. 모드를 바꿔 질문을 보내고 입력 막대와 입력 처리 막대의 길이를 비교한다.

<figure class="fig" data-figure="llm-tools-rag">
  <figcaption>문서를 통째로 넣을 때와 관련 조각만 넣을 때 (토큰 수는 예시)</figcaption>
</figure>

통째로 넣으면 40조각 20,000토큰에 지시와 질문 600토큰이 붙어 20,600토큰이다. 가까운 3조각만 넣으면 2,100토큰으로 약 10분의 1이 되고, 입력 처리 막대도 그만큼 짧아진다. 입력 처리는 토큰마다 key와 value를 만드는 일이라 **읽을 토큰 수에 비례해** 시간과 요금이 준다. 답에 필요한 문장이 그 3조각 밖에 있으면 모델은 그 문장을 보지 못한다.

벡터는 검색용 저장소에 둔다. PostgreSQL 확장 pgvector라면 거리 연산자로 정렬해 앞의 몇 개를 자른다.

```sql
CREATE TABLE chunks (id bigserial, body text, embedding vector(1536));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT body FROM chunks ORDER BY embedding <=> $1 LIMIT 3;  -- <=>: 코사인 거리
```

색인이 없으면 pgvector는 모든 행과 거리를 재는 정확 검색을 한다. HNSW 색인은 벡터를 여러 층의 그래프로 엮어 일부만 훑는 근사 검색이라, 빠른 대신 가장 가까운 조각을 가끔 놓치고 메모리를 더 쓴다.

조각 크기는 맞바꿈이다. 잘게 자르면 답에 필요한 앞뒤 문맥이 끊기고, 크게 자르면 입력이 다시 커지고 관계없는 문장이 섞인다. OpenAI 벡터 저장소의 기본값은 조각 800토큰, 앞뒤 겹침 400토큰이고, 검색은 기본 10개(최대 50개)를 돌려준다.

RAG가 가져오는 건 미리 잘라 저장해 둔 글뿐이다. 지금 날씨, 방금 바뀐 주문 상태처럼 저장해 둘 수 없는 정보와 티켓 만들기 같은 행동은 다른 길이 필요하다.

## 도구 호출

저장해 둘 수 없는 정보는 질문이 온 순간 가져와야 한다. 도구 호출(tool calling)은 모델이 답 대신 "이 함수를 이 인자로 불러 달라"는 요청을 돌려주게 하는 방식이다. OpenAI 문서가 정리한 흐름은 다섯 단계다.

1. 앱이 질문과 함께 도구 목록(이름, 설명, 인자 JSON 스키마)을 보낸다.
2. 모델이 함수 이름과 JSON 인자를 담은 호출 요청을 돌려준다.
3. 앱이 그 함수를 실행한다.
4. 앱이 실행 결과를 대화에 붙여 모델을 다시 부른다.
5. 모델이 결과를 읽고 답하거나 도구를 또 부른다.

아래 그림처럼 모델은 함수를 실행하지 않는다. 모델이 내놓는 건 호출 요청이라는 글이고, 실행하고 결과를 대화에 다시 싣는 일은 앱이 한다.

<figure class="fig" data-figure="llm-tools-loop">
  <figcaption>도구 호출 한 번의 왕복</figcaption>
</figure>

```python
tools = [{
    "type": "function", "name": "get_weather", "description": "도시의 현재 날씨",
    "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
}]
resp = client.responses.create(model=MODEL, input=items, tools=tools)
for call in (o for o in resp.output if o.type == "function_call"):
    result = get_weather(**json.loads(call.arguments))      # 실행은 앱이 한다
    items += [call, {"type": "function_call_output", "call_id": call.call_id, "output": json.dumps(result)}]
resp = client.responses.create(model=MODEL, input=items, tools=tools)
```

루프를 앱이 쥐고 있어서 어떤 도구를 줄지, 실행 전에 사용자에게 물을지도 앱이 정한다. 비용도 같은 구조에서 나온다.

- 도구 정의는 입력 토큰으로 계산된다. 도구 30개를 붙이면 질문 한 줄에도 설명 30개가 매번 같이 간다. OpenAI는 한 번에 붙이는 함수를 20개 아래로 두라고 권한다.
- 도구를 한 번 쓸 때마다 모델 호출이 하나 늘고, 앞의 호출 요청과 결과가 입력에 쌓여 입력 처리가 길어진다.
- 서로 기다릴 필요 없는 호출은 한 응답에 여러 개 나올 수 있다(`parallel_tool_calls`). 앱이 동시에 실행하면 왕복이 하나로 준다.

남는 문제는 연결 코드다. 날씨 도구를 사내 챗봇, 편집기, 터미널 에이전트에 모두 붙이려면 앱마다 스키마를 적고 실행 코드를 따로 짠다. 앱이 N개, 도구가 M개면 연결은 N×M개다.

## MCP

MCP(Model Context Protocol)는 앞 절 루프의 3번, 도구를 찾고 실행하는 부분을 규격으로 맞춘다. 도구를 MCP 서버로 한 번 만들면 MCP를 지원하는 어느 앱에서나 쓸 수 있어 연결이 N+M개로 준다.

- 호스트: 사용자가 쓰는 LLM 앱(Cursor 등). 모델을 부르고 루프를 돌리며 사용자 동의를 받는다.
- 클라이언트: 호스트 안에서 서버 하나와의 연결을 맡는다. 서버마다 하나씩 있다.
- 서버: 도구를 내놓는 프로그램. 파일, Unity 에디터, DB 같은 실제 대상을 다룬다.

메시지는 JSON-RPC 2.0이다. 요청은 `id`, `method`, `params`를 싣고 응답은 같은 `id`로 돌아온다. 도구에 쓰는 메서드는 `tools/list`(이름, 설명, `inputSchema` 받기)와 `tools/call`(이름과 `arguments`를 보내 실행) 둘이다.

아래 그림처럼 호스트는 서버마다 `tools/list`로 모은 도구를 합쳐 모델에 넘기고, 모델이 하나를 고르면 그 서버의 클라이언트로 `tools/call`을 보낸다.

<figure class="fig" data-figure="llm-tools-mcp">
  <figcaption>호스트 하나에 서버마다 클라이언트 하나</figcaption>
</figure>

```json
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"location": "Seoul"}}}
{"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete",
 "content": [{"type": "text", "text": "맑음 12도"}], "isError": false}}
```

서버는 대화 전체를 보지 못하고 자기에게 온 인자만 받는다. 날짜 형식이 틀렸다는 식의 실행 오류는 JSON-RPC 오류가 아니라 `isError: true`인 결과로 돌려준다. 모델이 그 글을 읽고 인자를 고쳐 다시 부르게 하려는 것이다.

서버가 내놓는 것은 셋이고, 누가 쓰기로 정하느냐로 나뉜다.

- 도구(tools): 모델이 고른다. API 호출, 파일 쓰기.
- 리소스(resources): 앱이 골라 컨텍스트에 붙인다. 파일 내용, git 기록. RAG 조각이 들어갈 자리다.
- 프롬프트(prompts): 사용자가 고른다. 슬래시 명령 같은 틀.

### 전송 방식

아래 그림처럼 같은 PC의 서버는 표준 입출력으로, 원격 서버는 HTTP로 붙는다.

<figure class="fig" data-figure="llm-tools-transport">
  <figcaption>같은 PC의 stdio와 원격 서버의 Streamable HTTP</figcaption>
</figure>

- stdio: 호스트가 서버를 자식 프로세스로 띄우고 stdin과 stdout으로 JSON-RPC 메시지를 한 줄에 하나씩 주고받는다. 그래서 Cursor의 `mcp.json` 같은 호스트 설정에는 도구가 아니라 서버를 띄우는 명령을 적고, 도구 목록은 띄운 뒤 `tools/list`로 받는다. 서버는 stdout에 MCP 메시지가 아닌 것을 쓰면 안 되고 로그는 stderr로 쓴다. 디버그 출력을 `print`로 찍으면 호스트가 그 줄을 해석하지 못한다.
- Streamable HTTP: 서버가 독립 프로세스로 엔드포인트 하나(예: `/mcp`)를 연다. 메시지마다 POST를 보내고, 서버는 JSON 하나로 답하거나, 응답을 열어 둔 채 메시지를 여러 번 흘려보내는 SSE(Server-Sent Events) 스트림으로 답한다. 오래 걸리는 도구가 진행 상황을 중간에 보낼 때 쓴다.

로컬에서 HTTP 서버를 띄우면 `127.0.0.1`에만 열고 `Origin` 헤더를 검사해야 한다. 악성 웹페이지가 브라우저를 거쳐 내 PC의 로컬 서버를 부르는 DNS 리바인딩 공격을 막으려고 사양이 요구하는 것이다.

사양은 사람이 도구 호출을 거부할 수 있어야 하고, 클라이언트가 실행 전에 인자를 보여 주라고 권한다. Cursor의 YOLO 모드 같은 자동 실행은 이 확인을 건너뛰므로, 파일을 지우거나 명령을 실행하는 서버를 붙였다면 버려도 되는 작업 폴더에서만 켠다.

## 로컬 실행

여기까지의 문서 조각, 도구 결과, 대화는 모두 모델 API로 나간다. 사내 문서를 밖으로 보내지 않으려면 모델을 직접 띄워야 하고, 먼저 막히는 곳은 GPU 메모리다.

모델 파일은 대부분 가중치(파라미터)라서 필요한 메모리는 파라미터 수에 파라미터 하나의 바이트 수를 곱해 어림한다.

```text
Llama 3.1 8B,  FP16(2바이트)  80억 × 2  ≈ 16GB
Llama 3.1 70B, FP16(2바이트)  700억 × 2 ≈ 141GB
```

양자화(quantization)는 파라미터 하나를 더 적은 비트로 저장한다. Ollama의 `llama3.1:8b`는 4비트 계열 `q4_K_M`으로 4.9GB, `q8_0`은 8.5GB다. 값이 거칠어지는 만큼 답의 품질이 조금 떨어질 수 있다. 모드를 바꿔 12GB GPU에 모델을 올리고 시스템 메모리 칸이 차는지 비교한다.

<figure class="fig" data-figure="llm-tools-quant">
  <figcaption>GPU 12GB에 Llama 3.1 8B 올리기 (크기는 Ollama 태그 값)</figcaption>
</figure>

FP16은 16GB 중 4GB가 GPU에 못 들어가 시스템 메모리로 밀려나고, 그 레이어는 CPU가 계산한다. 4비트는 4.9GB라 다 들어간다. 생성은 토큰마다 가중치 전체를 읽는 속도에 묶여 있어서, **읽을 바이트가 3분의 1로 줄면** 토큰도 빨리 나오고 대역폭이 낮은 시스템 메모리를 거치는 레이어도 없어진다. `ollama ps`의 PROCESSOR 열이 `100% GPU`가 아니라 `48%/52% CPU/GPU`처럼 나뉘면 넘친 상태다.

가중치 다음은 KV 캐시다. 입력 처리에서 만든 key와 value를 토큰마다 GPU 메모리에 쌓아 두고 다음 토큰을 만들 때 다시 쓰는 것으로, 크기는 컨텍스트 길이에 비례한다.

모델은 같은 계산 블록을 여러 번 쌓은 구조이고 이 블록 하나를 레이어(layer)라 한다. 레이어 안에서 앞 토큰을 참고하는 계산은 헤드(head) 여러 개로 나뉜다. 질의(query) 헤드는 지금 토큰이 무엇을 찾는지 담고, KV 헤드는 토큰마다 key와 value를 내놓는다. 캐시에 쌓이는 것은 KV 헤드의 출력이다.

```text
토큰당 KV = 2(key, value) × 레이어 수 × KV 헤드 수 × 헤드 크기 × 바이트
Llama 3.1 8B, FP16 → 2 × 32 × 8 × 128 × 2 = 131,072바이트(128KB)
128k 토큰 → 16GB
```

Llama 3.1 8B는 질의 헤드 32개가 KV 헤드 8개를 나눠 쓰는 GQA(grouped-query attention)라서, KV 헤드가 32개인 Llama 2 7B(토큰당 0.5MB)의 4분의 1이다. 그래도 아래 그림처럼 가중치 16GB에 컨텍스트 64k가 더해지면 24GB GPU가 찬다.

<figure class="fig" data-figure="llm-tools-kv">
  <figcaption>컨텍스트 길이에 따른 GPU 메모리 (Llama 3.1 8B FP16, 요청 하나)</figcaption>
</figure>

- Ollama의 기본 창은 GPU 메모리로 정한다. 24GiB 미만 4k, 24~48GiB 32k, 48GiB 이상 256k이고 `OLLAMA_CONTEXT_LENGTH`로 바꾼다.
- KV 캐시도 양자화한다. Flash Attention이 켜진 상태에서 `OLLAMA_KV_CACHE_TYPE=q8_0`이면 f16의 약 절반, `q4_0`이면 약 4분의 1이다.
- 동시 요청은 KV 캐시를 따로 쓴다. 2K 창에 `OLLAMA_NUM_PARALLEL=4`면 실제 창은 8K가 된다.

모델을 올리면 앞 절의 코드는 거의 그대로 쓴다. Ollama, vLLM, llama.cpp의 `llama-server`가 모두 OpenAI 형식 API를 열어 `base_url`만 바꾸면 되고, Ollama는 도구 정의와 `/v1/embeddings`도 같은 형식으로 받는다.

```python
from openai import OpenAI
local = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")  # Ollama는 키를 보지 않는다
resp = local.chat.completions.create(model="llama3.1:8b", messages=msgs, tools=tools)
```

여러 사용자가 동시에 붙으면 KV 캐시가 GPU 메모리를 먼저 채운다. vLLM은 KV 캐시를 작은 블록으로 나눠 필요한 만큼만 잡는 PagedAttention으로 같은 GPU에 더 많은 요청을 올린다.

Ollama는 기본으로 `127.0.0.1:11434`에만 열리고 API에 인증이 없다. `OLLAMA_HOST`로 바깥에 열 때는 앞단 프록시에 인증을 둔다.

## 정리

- 모델은 가중치와 요청에 실린 토큰만 본다. 앱이 대화 전체를 매번 다시 싣고, 실은 양만큼 첫 토큰이 늦고 요금이 는다.
- RAG는 문서 조각을 임베딩으로 바꿔 두고, 질문과 코사인 유사도가 가까운 조각 몇 개만 싣는다.
- 저장해 둘 수 없는 정보와 행동은 도구 호출로 맡긴다. 모델은 호출 요청만 쓰고, 실행과 결과 전달은 앱이 한다.
- MCP는 그 연결을 JSON-RPC의 `tools/list`와 `tools/call`로 표준화한다. 같은 PC는 stdio, 원격은 Streamable HTTP로 붙는다.
- 로컬 모델의 메모리는 파라미터 수 × 바이트에 KV 캐시를 더한 값이다. 양자화로 줄이고 OpenAI 호환 API로 같은 코드를 돌린다.
