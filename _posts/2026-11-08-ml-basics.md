## 학습 코드 구성

ML 팀이 `train.py` 하나를 건네며 "GPU 한 장에 14 에폭이면 된다"고 한다. 노드를 잡고 학습이 멈췄을 때 원인을 읽으려면 이 코드가 무엇을 반복하는지 알아야 한다. PyTorch 공식 예제인 MNIST 학습 코드(손글씨 숫자 이미지 6만 장)로 따라가 본다.

학습 코드는 객체 세 개로 이뤄진다.

- 데이터: `Dataset`이 이미지와 정답(label)을 한 쌍씩 꺼내고, `DataLoader`가 여러 쌍을 묶어 넘긴다.
- 모델: `nn.Module`. 입력을 받아 답을 내는 계산식이고, 그 안의 숫자인 가중치(weight)를 학습으로 고친다. MNIST 예제 모델의 가중치는 1,199,882개다.
- 옵티마이저(optimizer): 손실을 보고 가중치를 얼마나 고칠지 정한다.

인프라에서는 이 셋이 어느 장치에 있는지로 보인다. 학습 스텝 한 번 동안 이미지 묶음이 디스크에서 GPU까지 가는 길을 따라가 보자.

<figure class="fig" data-figure="ml-basics-parts">
  <figcaption>학습 스텝 한 번이 지나가는 장치</figcaption>
</figure>

이미지 묶음은 스텝마다 PCIe를 건너 GPU로 가고, 가중치와 옵티마이저 상태는 GPU 메모리에 계속 머문다. 그래서 학습이 느릴 때 병목은 GPU 계산뿐 아니라 디스크 읽기, CPU 전처리, PCIe 복사 어디에서도 생긴다.

장치는 코드 첫머리에서 고르고, 모델을 그 장치로 옮긴다.

```python
use_accel = torch.accelerator.is_available()
device = torch.accelerator.current_accelerator() if use_accel else torch.device("cpu")
model = Net().to(device)
```

`torch.accelerator`는 CUDA(NVIDIA), MPS(Apple 실리콘 GPU), XPU(Intel GPU)를 한 API로 다룬다. 예전 예제는 `cuda`와 `mps`를 따로 검사했는데 지금 공식 예제는 이렇게 바뀌었다. GPU 노드에서 학습이 CPU로 돌고 있다면 이 분기에서 가속기를 못 찾은 것이니, 드라이버와 컨테이너의 GPU 할당부터 본다.

## 학습 스텝

### 순전파와 손실

학습 로그에 `Loss: 2.30`으로 시작해 `0.02`까지 내려가는 숫자가 찍힌다. 이 숫자가 손실(loss)이다.

순전파(forward)는 입력을 모델에 통과시켜 답을 얻는 계산이다. MNIST 모델은 이미지 한 장을 받아 0부터 9까지 숫자 열 개 각각의 확률을 낸다. 손실은 정답 칸의 확률이 낮을수록 커진다.

```text
손실 = -log(정답 칸의 확률)

정답 확률 10%  →  손실 2.30
정답 확률 98%  →  손실 0.02
```

같은 7 이미지를 학습 전과 뒤의 모델에 넣어 보자. 오른쪽 막대에서 정답 7의 칸이 얼마나 솟는지 본다.

<figure class="fig" data-figure="ml-basics-forward">
  <figcaption>이미지 한 장의 순전파와 손실</figcaption>
</figure>

학습 전 모델은 가중치가 무작위라 열 칸에 고르게 답하고, 손실은 열 칸 중 하나를 찍는 값인 2.30 근처에서 시작한다. 학습이 진행되면 정답 칸으로 확률이 몰리고 손실이 0으로 다가간다.

```python
output = model(data)               # 순전파: 배치의 이미지마다 열 칸 확률
loss = F.nll_loss(output, target)  # 정답과 비교한 손실, 배치 평균
```

예제는 모델 끝에서 `log_softmax`를 하고 `nll_loss`를 쓴다. 둘을 합친 것이 `F.cross_entropy`라서, 요즘 코드는 모델이 날값을 내고 `cross_entropy` 하나로 손실을 구하는 경우가 많다.

첫 로그의 손실이 2.3 근처가 아니면 학습률이나 정답 데이터가 잘못 들어간 경우가 많다. 학습을 처음 띄웠을 때 첫 손실부터 본다.

### 역전파와 가중치 갱신

학습 함수를 읽어 보면 모델을 직접 고치는 코드가 없다. 데이터를 넣고 손실을 구할 뿐인데 모델이 바뀐다.

역전파(backpropagation)는 손실에서 거꾸로 거슬러 가며 가중치마다 기울기(gradient)를 구한다. 기울기는 "이 가중치를 조금 올리면 손실이 얼마나 변하는지"다. 옵티마이저는 만들 때 `model.parameters()`로 가중치를 넘겨받아 두었다가, `step()`에서 기울기 반대 방향으로 가중치를 고친다.

```python
optimizer = optim.Adadelta(model.parameters(), lr=1.0)  # 가중치를 넘겨받는다

optimizer.zero_grad()  # 이전 스텝의 기울기를 비운다
loss.backward()        # 역전파: 가중치마다 기울기를 구한다
optimizer.step()       # 기울기 반대 방향으로 가중치를 고친다
```

고치는 폭은 학습률(learning rate)이 정한다. 가장 단순한 경사 하강법(gradient descent)은 이렇다.

```text
새 가중치 = 가중치 - 학습률 × 기울기
```

손실이 w²인 골짜기에서 가중치 하나를 10번 고쳐 본다. 모드를 바꿔 가며 공이 바닥에 얼마나 가까워지는지 지켜본다.

<figure class="fig" data-figure="ml-basics-lr">
  <figcaption>학습률에 따라 달라지는 갱신 폭</figcaption>
</figure>

학습률 0.02에서는 10번을 고쳐도 손실이 2.56에서 1.13으로 반쯤만 내려온다. 1.02에서는 한 번에 골짜기를 넘어가 손실이 5.61로 오히려 커진다. 기울기는 같고 바뀐 것은 한 번에 움직이는 폭뿐이다.

Adadelta와 Adam은 이 폭을 가중치마다 따로 조절하지만, 기울기 반대 방향으로 간다는 원리는 같다. 예제의 `StepLR(gamma=0.7)`은 에폭마다 학습률을 0.7배로 줄여, 처음에는 크게 움직이고 바닥 근처에서는 잘게 움직이게 한다.

실제 학습에서 너무 큰 학습률은 손실이 줄지 않고 튀다가 `nan`이 되는 모습으로 나타난다. 손실 로그가 `nan`으로 바뀌면 코드나 장비보다 학습률부터 낮춰 본다.

## 반복 학습

### 배치와 스텝

같은 코드에서 `--batch-size`를 64에서 1024로 올렸더니 GPU 메모리를 더 쓰고 정확도는 떨어졌다. 배치가 무엇을 바꾸는지 알아야 이 결과가 읽힌다.

- 배치(batch): 가중치를 한 번 고치기 전에 함께 보는 데이터 묶음
- 스텝(step): 가중치 갱신 한 번
- 에폭(epoch): 학습 데이터 전체를 한 바퀴 보는 것

```text
6만 장 ÷ 배치 64    = 938 스텝
6만 장 ÷ 배치 1024  =  59 스텝
```

배치 크기만 바꿔 1 에폭을 돌린다. 모드를 바꿔 가며 같은 6만 장을 보는 동안 갱신 횟수와 GPU 메모리가 어떻게 갈리는지 본다.

<figure class="fig" data-figure="ml-basics-batch">
  <figcaption>같은 1 에폭, 배치 크기만 다른 학습 (메모리는 계산값, 손실 선은 CPU 실측)</figcaption>
</figure>

배치 64는 1 에폭 동안 가중치를 938번 고치고, 배치 1024는 59번만 고친다. 본 데이터는 같고 **가중치를 고친 횟수**만 다르다. 같은 학습률이면 1 에폭이 끝났을 때 배치 64 쪽 손실이 더 내려가 있다.

메모리는 반대로 움직인다. 순전파 중간 결과(활성값)를 배치만큼 쌓아 두기 때문에, 활성값이 배치 64에서 42MB, 1024에서 610MB로 16배 가까이 커진다. 대신 GPU가 한 번에 많은 이미지를 처리해 한 에폭은 빨리 끝난다.

배치를 키우면 갱신 횟수가 줄어드는 만큼 학습률을 함께 키우는 경우가 많다. 그래서 배치를 바꾼 학습이 결과가 나빠졌다면 학습률도 같이 바뀌었는지 확인한다. GPU 메모리가 남는다고 배치부터 키우지 않고, 학습률과 한 묶음으로 ML 팀과 정한다.

### 에폭과 손실 곡선

14 에폭짜리 학습에서 정확도가 몇 에폭 만에 더 오르지 않는다. 나머지 에폭이 GPU 시간을 쓸 만한지는 손실 곡선으로 판단한다.

첫 장면은 첫 에폭 안에서 갱신 횟수에 따른 손실이고, 둘째 장면은 에폭마다의 평균 손실이다. 두 장면에서 곡선이 평평해지는 지점을 본다.

<figure class="fig" data-figure="ml-basics-epochs">
  <figcaption>MNIST 예제의 손실 곡선 (CPU 실측)</figcaption>
</figure>

첫 에폭 안에서 손실은 처음 몇십 번의 갱신 만에 2.3에서 크게 떨어지고, 배치마다 들쭉날쭉하다. 배치 하나는 데이터의 일부라서, 배치 손실 하나하나보다 흐름을 본다.

에폭 단위로 보면 학습 손실은 끝까지 내려가지만 테스트 손실은 몇 에폭 만에 평평해진다. 테스트 손실이 멈춘 뒤의 에폭은 학습 데이터에만 더 맞춰 갈 뿐이다.

에폭마다 학습 손실과 테스트 손실을 같이 찍어 두면 이 판단을 할 수 있다. 예제는 테스트 전에 `model.eval()`로 드롭아웃을 끄고, `torch.no_grad()`로 기울기 계산을 꺼 메모리를 아낀다.

```python
model.eval()
with torch.no_grad():
    output = model(data)
```

곡선이 평평해진 뒤의 에폭은 GPU 시간만 쓴다. 학습 작업이 에폭마다 검증 지표를 로그로 남기는지부터 본다.

## 표 데이터 학습

같은 코드를 이미지가 아닌 표 데이터에 쓰면 MNIST에서 보이지 않던 문제가 나온다. 예시는 폐암 수술 환자 470명의 기록으로 1년 안 사망 여부를 예측하는 데이터(UCI Thoracic Surgery)다. 열은 18개이고 마지막 열이 정답이다.

모델은 입력 17개를 받는 3층짜리 다층 퍼셉트론(MLP)이다. `nn.Linear`만 쌓은 단순한 모델이고, 이미지처럼 픽셀 사이의 위치 관계가 없으니 합성곱 층은 쓰지 않는다.

```python
self.fc1 = nn.Linear(17, 64)
self.fc2 = nn.Linear(64, 32)
self.fc3 = nn.Linear(32, 2)   # 생존, 사망 두 칸
```

### 전처리 일관성

학습 때 결과는 괜찮았는데, 저장한 모델로 새 환자를 예측하니 답이 엉뚱하다. 학습과 서빙이 같은 입력을 받지 않을 때 생기는 일이다.

표 데이터는 열마다 단위가 다르다. 나이는 60 근처, 폐활량은 3 근처라서 그대로 넣으면 큰 값의 열이 학습을 끌고 간다. 그래서 열마다 평균을 빼고 표준편차로 나누는 표준화(standardization)를 한다. 학습 데이터의 나이 평균은 62.6이고, 68세는 0.62가 된다.

스케일러가 학습과 서빙에서 같은 자리에 있는지에 따라 모델이 받는 값이 어떻게 달라지는지 보자. 둘째 장면에서 모델에 들어가는 칩의 숫자를 본다.

<figure class="fig" data-figure="ml-basics-scaler">
  <figcaption>학습 때와 서빙 때 모델이 받는 값</figcaption>
</figure>

같은 68세 환자를 표준화해 넣으면 사망 확률이 17%, 원래 값을 그대로 넣으면 0%가 나왔다. 모델은 학습 때 본 적 없는 크기의 입력에도 오류 없이 숫자를 내기 때문에, 서빙 로그만 봐서는 잘못을 알아채기 어렵다.

원글의 예측 코드가 이 경우였다. 학습 코드는 표준화를 했는데 예측 코드는 `sample.csv`를 그대로 넣었다. 학습 코드에도 고칠 곳이 두 군데 더 있었다.

- 스케일러를 데이터를 나누기 전에 전체에 맞췄다(`fit`). 테스트 데이터의 평균이 학습에 섞이는 데이터 누수(data leakage)다. 학습 데이터에만 맞추고, 같은 객체로 테스트와 서빙 데이터를 바꾼다.
- 첫 열은 1부터 470까지 겹치지 않는 값이라 환자 번호로 보인다. 원글은 이것도 입력으로 넣었다. 번호는 정답과 관계가 없으니 뺀다.

```python
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=1)
scaler = StandardScaler().fit(X_train)        # 학습 데이터에만 맞춘다
X_train, X_test = scaler.transform(X_train), scaler.transform(X_test)
joblib.dump(scaler, "scaler.joblib")          # 모델 파일과 같이 배포한다
```

학습 때와 서빙 때 입력이 달라지는 일을 training-serving skew라고 한다. 모델 배포를 받으면 전처리 객체가 같이 오는지부터 본다.

### 불균형 데이터

원글 코드를 그대로 돌리면 테스트 정확도가 86%로 나온다. 그런데 예측을 열어 보면 94명 모두 "생존"이다.

데이터 470명 중 1년 안에 사망한 환자는 70명(15%)이다. 한쪽 정답이 훨씬 많은 데이터를 불균형 데이터(imbalanced data)라고 한다. 테스트 환자 94명을 점으로 놓고, 모두 생존이라고 답하는 모델을 채점해 보자. 셋째 장면에서 빨간 테두리 점이 어떻게 되는지 본다.

<figure class="fig" data-figure="ml-basics-imbalance">
  <figcaption>테스트 환자 94명과 모두 생존이라고 답하는 모델</figcaption>
</figure>

생각 없이 다수 쪽만 답해도 85%가 맞는다. 정확도(accuracy)는 많은 쪽을 맞히는 것만으로 올라가서, 적은 쪽이 중요한 문제에서는 정확도로 모델을 고르면 안 된다.

원글은 마지막 열을 "0 사망, 1 생존"으로 읽었다. UCI 원본 설명은 이 열이 1년 안에 사망하면 참이고, 실제 값도 0이 400명, 1이 70명이다. 1이 사망이다.

### 평가 지표

모델은 환자마다 사망 확률을 내고, 기준(threshold)을 넘으면 사망으로 판정한다. 이때 두 가지를 따로 센다.

- 재현율(recall): 실제 사망 환자 중 모델이 찾아낸 비율
- 정밀도(precision): 모델이 사망으로 짚은 환자 중 실제 사망 비율

같은 모델에서 기준만 바꿔 테스트 환자 94명을 판정한다. 모드를 바꿔 가며 찾은 사망 환자와 잘못 짚은 생존 환자가 함께 움직이는 모습을 지켜본다.

<figure class="fig" data-figure="ml-basics-threshold">
  <figcaption>같은 모델, 판정 기준만 다른 결과 (실측)</figcaption>
</figure>

기준 50%에서는 사망 14명 중 한 명도 찾지 못한다. 15%로 내리면 7명을 찾지만 생존 환자 47명을 사망으로 잘못 짚는다. 모델은 그대로이고 바뀐 것은 기준 하나다.

기준을 내려도 정밀도는 13%(54명 중 7명)에 머문다. 이 데이터의 열만으로는 사망을 가려낼 신호가 약하다는 뜻이라, 기준을 만지기보다 데이터를 더 모아야 하는 경우다.

어느 기준을 쓸지는 놓친 사망과 잘못된 경보 중 무엇이 더 비싼지로 업무 쪽이 정한다. 학습 결과 보고에 정확도 하나만 있으면 재현율과 정밀도를 같이 요청한다.

### 과적합

학습 손실은 끝까지 줄었는데, 테스트 결과는 처음 몇십 에폭보다 나빠졌다. 학습 데이터의 우연한 특징까지 외워 새 데이터에서 틀리는 과적합(overfitting)이다.

과적합을 보려면 데이터를 세 갈래로 나눈다. 원글은 테스트 세트로 매 에폭 성능을 봤는데, 이렇게 고르는 데 쓴 데이터는 검증 세트가 된다.

- 학습(train): 가중치를 고치는 데 쓴다
- 검증(validation): 언제 멈출지, 어떤 설정이 나은지 고르는 데 쓴다
- 테스트(test): 다 고른 뒤 마지막에 한 번만 쓴다

학습 손실과 검증 손실을 300 에폭 동안 그려 본다. 두 선이 갈라지기 시작하는 에폭을 본다.

<figure class="fig" data-figure="ml-basics-overfit">
  <figcaption>폐암 데이터의 학습 손실과 검증 손실 (CPU 실측)</figcaption>
</figure>

검증 손실은 21 에폭에서 0.459로 가장 낮고, 300 에폭에서는 0.818까지 올라간다. 그동안 학습 손실은 0.63에서 0.20까지 계속 내려간다. 학습 데이터가 376명뿐이라 6만 장인 MNIST보다 훨씬 빨리 외운다.

검증 손실이 가장 낮았던 에폭의 가중치를 저장해 쓰고, 일정 에폭 동안 나아지지 않으면 학습을 멈춘다. 이를 조기 종료(early stopping)라고 한다. 드롭아웃(`nn.Dropout`)이나 가중치 감쇠(옵티마이저의 `weight_decay`)도 과적합을 늦춘다.

학습 작업에 조기 종료와 "검증 지표가 가장 좋은 체크포인트 저장"이 있는지 본다. 없으면 과적합된 마지막 가중치를 배포하고, 그 뒤의 에폭만큼 GPU 시간을 버린다.

## 학습과 인프라 자원

### GPU 메모리 구성

같은 모델인데 배치만 올렸더니 `CUDA out of memory`로 죽는다. 학습이 GPU 메모리에 올리는 것은 네 가지다.

- 가중치: 모델의 숫자. 32비트 실수면 개당 4바이트다.
- 기울기: 가중치마다 하나씩, 가중치와 같은 크기다.
- 옵티마이저 상태: Adam과 Adadelta는 가중치마다 값을 두 개씩 더 들고 다닌다.
- 활성값: 역전파 때 쓰려고 보관하는 순전파 중간 결과. 배치 크기에 비례한다.

MNIST 모델과 70억(7B) 파라미터 모델을 같은 막대로 쌓아 본다. 둘째 장면에서 막대가 80GB 선을 넘는 순간을 본다.

<figure class="fig" data-figure="ml-basics-memory">
  <figcaption>학습 중 GPU 메모리를 차지하는 네 가지</figcaption>
</figure>

MNIST 예제는 배치 64에서 가중치 4.6MB, 기울기 4.6MB, 옵티마이저 상태 9.2MB, 활성값 42MB다. 배치를 1024로 올리면 앞의 셋은 그대로이고 활성값만 610MB로 커진다. OOM이 배치를 올릴 때 나는 이유다.

큰 모델에서는 활성값보다 앞의 셋이 문제가 된다. 혼합 정밀도(mixed precision)와 Adam으로 학습하면 가중치 하나에 16바이트가 든다.

```text
가중치 2 (bf16) + 기울기 2 (bf16) + fp32 사본과 Adam 상태 12  =  16바이트
70억 × 16바이트 = 112GB   →  80GB GPU 한 장에 안 들어간다
```

MNIST 수치는 PyTorch로 텐서 크기를 합산한 계산값이고, 7B 수치는 ZeRO 논문의 계산 방식을 따른 대략값이다. 활성값은 배치와 입력 길이에 따라 달라서 7B 장면에서는 예시로만 넣었다.

OOM이 나면 배치부터 줄인다. 같은 효과를 내려면 작은 배치 여러 번의 기울기를 모아 한 번에 고치는 기울기 누적(gradient accumulation)을 쓴다. 그래도 모자라면 가중치와 옵티마이저 상태를 여러 GPU에 나눠 두는 FSDP 같은 분산 학습으로 넘어간다.

`nvidia-smi`의 사용량은 PyTorch가 실제로 쓰는 양보다 크다. PyTorch는 한 번 받은 메모리를 바로 돌려주지 않고 다음 스텝을 위해 들고 있기 때문이다. 학습 코드 안에서는 `torch.cuda.max_memory_allocated()`로 최대 사용량을 찍어 본다.

### 데이터 로딩

GPU 사용률이 40%에서 오르지 않는다. GPU가 느린 게 아니라 다음 배치를 기다리고 있을 때가 많다.

`DataLoader`의 `num_workers` 기본값은 0이다. 0이면 학습을 돌리는 메인 프로세스가 직접 이미지를 읽고 변환하고, 그동안 GPU는 논다. 워커를 두면 별도 프로세스들이 다음 배치를 미리 만들어 둔다. 두 장면에서 GPU 줄의 빈칸을 견줘 보자.

<figure class="fig" data-figure="ml-basics-loader">
  <figcaption>num_workers에 따른 GPU 대기 (시간은 모양을 보여 주는 대략값)</figcaption>
</figure>

워커가 없으면 배치를 만드는 동안 GPU가 매번 기다린다. 워커 둘이 번갈아 만들면 첫 배치 뒤로는 GPU가 쉬지 않는다. 배치를 만드는 일은 CPU가 하므로, GPU를 빨리 돌리려면 CPU도 함께 있어야 한다.

공식 예제가 가속기를 쓸 때 넣는 설정은 이렇다.

```python
loader_kwargs = {"num_workers": 1, "persistent_workers": True, "pin_memory": True, "shuffle": True}
```

- `pin_memory`: 배치를 페이지가 고정된 메모리에 두어 GPU로 복사를 빠르게 한다.
- `persistent_workers`: 에폭이 끝나도 워커 프로세스를 내리지 않아 에폭마다 다시 띄우는 시간을 아낀다.
- `shuffle`: 에폭마다 순서를 섞는다. 순서가 학습에 끼치는 영향을 줄인다.

컨테이너에서는 두 가지를 같이 챙긴다.

- 워커 수만큼 CPU request를 잡는다. GPU 파드의 CPU를 1로 두면 워커가 서로 기다린다.
- 워커는 공유 메모리로 배치를 넘긴다. Docker 기본 `/dev/shm`은 작아서 워커를 늘리면 오류가 난다. `--shm-size`나 `--ipc=host`, 쿠버네티스에서는 `medium: Memory`인 emptyDir을 `/dev/shm`에 붙인다.

GPU 사용률이 낮으면 GPU를 늘리기 전에 `num_workers`와 CPU request부터 본다.

### 체크포인트

비용을 아끼려고 스팟 인스턴스에서 학습을 돌렸는데, 노드가 회수될 때마다 학습이 처음부터 다시 돈다.

체크포인트(checkpoint)는 학습 상태를 파일로 남긴 것이다. 가중치만 저장하면 이어서 학습할 수 없고, 옵티마이저 상태와 학습률 스케줄러, 몇 에폭까지 했는지를 같이 저장해야 한다. 9 에폭 도중 노드가 회수된 경우를 두 장면으로 견줘 보자.

<figure class="fig" data-figure="ml-basics-ckpt">
  <figcaption>14 에폭 학습 중 노드가 회수될 때</figcaption>
</figure>

체크포인트가 없으면 14 에폭을 끝내는 데 23.5 에폭어치 GPU 시간을 쓴다. 에폭마다 저장하면 잃는 것은 회수 직전의 반 에폭뿐이다.

```python
torch.save({
    "epoch": epoch,
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "scheduler": scheduler.state_dict(),
}, "/ckpt/last.pt")

ckpt = torch.load("/ckpt/last.pt", map_location=device)
model.load_state_dict(ckpt["model"])
optimizer.load_state_dict(ckpt["optimizer"])
scheduler.load_state_dict(ckpt["scheduler"])
start_epoch = ckpt["epoch"] + 1
```

PyTorch 2.6부터 `torch.load`는 기본값이 `weights_only=True`다. 텐서와 기본 자료형만 읽고 임의 코드 실행을 막는다. 원글처럼 `state_dict`를 저장하는 방식은 그대로 읽히지만, 모델 객체를 통째로 저장한 옛 파일은 오류가 난다. 출처를 모르는 파일에 `weights_only=False`를 주지 않는다.

체크포인트는 노드 로컬 디스크가 아니라 PVC나 오브젝트 스토리지에 쓴다. 노드와 함께 사라지는 곳에 쓰면 저장하지 않은 것과 같다.

## 프레임워크 현황

"TensorFlow는 정적 그래프라 어렵고, PyTorch는 동적 그래프라 쉽다"는 비교는 TensorFlow 1 시절의 이야기다. TensorFlow 2는 PyTorch처럼 코드를 한 줄씩 바로 실행하는 즉시 실행(eager execution)이 기본이고, 그래프는 `tf.function`을 붙일 때만 만든다.

지금은 세 프레임워크 모두 같은 방식이다. 평소에는 즉시 실행으로 쓰고, 빠르게 돌리고 싶은 부분만 컴파일한다(`torch.compile`, `tf.function`, `jax.jit`). 두 장면에서 GPU 줄의 빈틈을 견줘 보자.

<figure class="fig" data-figure="ml-basics-compile">
  <figcaption>즉시 실행과 컴파일에서 GPU가 일하는 모습 (시간은 모양을 보여 주는 대략값)</figcaption>
</figure>

즉시 실행은 연산마다 GPU 작업(커널)을 따로 띄워서, 작은 연산이 많을수록 띄우는 시간과 빈틈이 쌓인다. 컴파일은 여러 연산을 커널 하나로 합쳐 그 빈틈을 줄인다. 대신 처음 컴파일하는 시간이 들어서, 학습 첫 몇 스텝이 느린 것은 정상이다.

2026년 11월 기준 상황은 이렇다.

- PyTorch: 2.15(2026-10-28)가 최신이다. Python 3.11 이상이 필요하다. Hugging Face Transformers도 v5부터 PyTorch만 공식 백엔드로 남겼다.
- TensorFlow: 2.21(2026-03)이 최신이다. 구글은 앞으로 보안과 버그 수정, 의존성 업데이트에만 집중한다고 밝혔고, 생성형 AI 새 작업에는 Keras 3, JAX, PyTorch를 권한다.
- JAX: 구글의 배열 계산 라이브러리다. NumPy 같은 코드에 `jit`(컴파일)과 `grad`(기울기)를 붙여 쓴다. TPU와 대규모 학습에서 많이 쓴다.
- Keras 3: 모델 코드를 한 번 쓰고 JAX, PyTorch, TensorFlow 중 하나를 백엔드로 골라 돌린다.

새 학습 인프라는 PyTorch를 기준으로 잡는다. TensorFlow로 된 기존 작업은 유지보수 대상으로 따로 분류해 두고, 옮길지는 모델을 쓰는 쪽과 정한다.

## MLOps

모델을 배포하고 석 달 뒤, 코드는 하나도 바꾸지 않았는데 예측 정확도가 떨어진다. 들어오는 데이터가 학습 때와 달라졌기 때문이다.

MLOps는 DevOps의 CI/CD를 머신러닝에 옮기고, 지속적 학습(CT, continuous training)을 더한 것이다. 일반 서비스는 코드가 바뀔 때 다시 배포하지만, 모델은 데이터가 바뀔 때도 다시 학습해 배포해야 한다. 세 장면에서 모델 버전 칩이 고리를 도는 모습을 보자.

<figure class="fig" data-figure="ml-basics-loop">
  <figcaption>데이터, 학습, 레지스트리, 서빙, 모니터링의 고리</figcaption>
</figure>

고리의 각 칸이 인프라가 맡는 자리다.

- 데이터: 학습에 쓴 데이터를 스냅샷으로 남겨 어떤 데이터로 만든 모델인지 되짚을 수 있게 한다.
- 학습: 앞에서 본 학습 작업을 파이프라인으로 묶는다. 체크포인트, 조기 종료, 검증 지표 기록이 여기 들어간다.
- 레지스트리: 모델 파일, 전처리 객체, 코드 커밋, 데이터 버전, 평가 지표를 한 버전으로 묶어 보관한다.
- 서빙: 레지스트리의 특정 버전을 받아 요청에 답한다. 문제가 생기면 이전 버전으로 되돌린다.
- 모니터링: 응답 시간뿐 아니라 입력값의 분포와 예측값의 분포를 본다.

구글의 MLOps 문서는 재학습을 거는 때를 다섯 가지로 든다.

- 사람이 필요할 때 직접
- 매일, 매주처럼 정해진 주기
- 새 학습 데이터가 들어왔을 때
- 모델 성능이 눈에 띄게 떨어졌을 때
- 입력 데이터의 분포가 크게 바뀌었을 때

모니터링에 응답 시간과 오류율만 있으면 이 그림의 둘째 장면을 볼 수 없다. 서빙 로그에 입력과 예측 분포를 남기는 것부터 시작한다.

## 정리

| | 하는 일 | 인프라에서 볼 것 |
|---|---|---|
| 순전파와 손실 | 모델이 답을 내고 정답과의 차이를 숫자로 잰다 | 첫 손실이 2.3 근처인지, `nan`이 되는지 |
| 역전파와 갱신 | 기울기를 구해 가중치를 학습률만큼 고친다 | 손실이 튀면 학습률부터 |
| 배치와 에폭 | 배치마다 한 번 고치고, 전체를 몇 바퀴 본다 | 배치는 메모리와 정확도를 같이 바꾼다 |
| 전처리 일관성 | 학습과 서빙에 같은 변환을 쓴다 | 스케일러가 모델과 함께 배포되는지 |
| 불균형과 지표 | 적은 쪽이 중요하면 정확도로 고르지 않는다 | 재현율과 정밀도를 같이 받는다 |
| 과적합 | 학습 데이터를 외워 새 데이터에서 틀린다 | 조기 종료와 최고 검증 체크포인트 |
| GPU 메모리 | 가중치, 기울기, 옵티마이저 상태, 활성값 | OOM이면 배치부터 줄인다 |
| 데이터 로딩 | CPU 워커가 다음 배치를 미리 만든다 | GPU가 놀면 `num_workers`와 CPU request |
| 체크포인트 | 가중치, 옵티마이저, 스케줄러, 에폭을 저장한다 | 노드 밖 저장소에 쓴다 |
| MLOps | 데이터가 바뀌면 다시 학습해 배포한다 | 입력과 예측 분포를 모니터링한다 |
