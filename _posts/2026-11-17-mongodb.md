## 요약

- 레플리카 셋은 쓰기를 프라이머리 한 대가 받고, 세컨더리가 oplog를 당겨 가 같은 순서로 다시 실행한다. 프라이머리가 사라지면 투표 멤버 과반의 표를 얻은 멤버가 새 프라이머리가 된다.
- `w: "majority"`는 과반이 저널에 적을 때까지 응답을 미룬다. `w: 1`은 그 기다림을 없애는 대신, 장애 조치 때 복제되지 않은 쓰기를 롤백으로 잃는다.
- 드라이버는 앱 프로세스마다, 멤버마다 풀을 둔다. 서버 쪽 연결은 하나에 스레드 하나와 최대 1MB라서, 파드 수와 풀 크기의 곱이 프라이머리가 떠안는 연결 상한이다.
- WiredTiger 캐시의 dirty 비율이 트리거를 넘으면 요청 스레드가 축출에 끌려가고, 쓰기 티켓이 바닥나면 모든 쓰기가 멈춘다. 이런 1초 단위 정지는 15초 평균에 묻히고 FTDC에서 보인다.
- 멤버 둘의 볼륨이 한 저장 노드에 있으면 그 노드의 정지가 과반을 함께 멈춘다.
- 레플리카 셋은 읽기만 나눈다. 쓰기가 프라이머리 한 대에 몰리면 샤드 키로 데이터를 나눠 프라이머리를 여럿 두고, 쿼리에 샤드 키를 넣어 샤드 하나로 보낸다.

## 레플리카 셋과 oplog

레플리카 셋(replica set)은 같은 데이터를 가진 mongod 여러 대의 묶음이다. 쓰기는 프라이머리(primary) 한 대만 받고, 세컨더리(secondary)는 프라이머리의 변경을 받아 같은 상태를 유지한다. 공식 문서가 권하는 최소 구성은 데이터를 가진 멤버 3대, 프라이머리 하나와 세컨더리 둘이다.

멤버는 용도에 따라 설정을 달리한다.

- hidden: 드라이버가 받는 멤버 목록(`hello` 응답)에서 빠져 앱의 읽기를 받지 않는다. 백업이나 분석을 따로 돌릴 때 쓰고, 프라이머리가 되지 않게 priority 0으로 둔다.
- delayed: `secondaryDelaySecs`만큼 늦게 따라간다. 실수로 지운 데이터를 그 시간 안에 되살리는 용도이고, hidden이면서 priority 0으로 둔다.
- arbiter: 데이터 없이 투표만 한다. 프라이머리, 세컨더리, 아비터 구성에서 세컨더리가 빠지면 과반 쓰기를 확인해 줄 데이터 멤버가 프라이머리뿐이라 `w: "majority"` 쓰기가 끝나지 않는다. 그래서 데이터 멤버 3대를 쓴다.

프라이머리는 데이터를 바꾼 연산마다 `local.oplog.rs` 컬렉션에 한 줄을 적는다. 이 oplog는 크기가 정해진 컬렉션(capped collection)이라 오래된 줄부터 지워지고, 기본 크기는 빈 디스크의 5%(최소 990MB, 최대 50GB, 공식 문서 기본값)다. 줄마다 몇 번 다시 실행해도 결과가 같게(멱등) 적힌다. `$inc`도 더한 뒤의 값으로 바꿔 적는다.

세컨더리는 프라이머리가 밀어 주기를 기다리지 않고 직접 당겨 간다. 동기화 소스(sync source)를 하나 골라 그 멤버의 oplog를 스트리밍으로 이어 받고, 자기 oplog에 적은 뒤 적용한다. 소스는 자기보다 앞선 멤버 중에서 고르고, 체이닝(chaining, 기본 켜짐)이 켜져 있으면 다른 세컨더리도 소스가 된다.

아래 그림처럼 세컨더리 B가 세컨더리 A에게서 받으면 프라이머리가 보내는 양은 줄지만, A가 늦으면 B도 같이 늦는다.

멤버끼리는 2초마다 하트비트를 주고받는다. 세컨더리가 10초(`electionTimeoutMillis` 기본값) 동안 프라이머리와 연락이 끊기면 후보가 되어 선거를 연다. 투표 멤버 과반의 표를 먼저 얻은 후보가 프라이머리가 되고, 공식 문서 기준으로 새 프라이머리가 서기까지 보통 12초를 넘지 않는다.

선거마다 term(임기 번호)이 하나씩 오른다. 멤버는 한 term에 한 표만 주고, 자기보다 oplog가 뒤처진 후보에게는 표를 주지 않는다. 네트워크가 갈라져 옛 프라이머리가 남아 있어도 과반과 연락이 안 되면 스스로 물러나고, 더 높은 term을 본 멤버는 옛 term의 요청을 거절한다.

투표 멤버는 최대 7대이고 멤버는 50대까지 둘 수 있다(공식 제한값). 4대는 과반이 3이라 3대처럼 1대 고장만 견디므로, 투표 멤버는 3, 5, 7처럼 홀수로 둔다.

## 쓰기 확인과 읽기 선호

쓰기 확인(write concern)은 서버가 "됐다"고 답하기 전에 무엇을 기다릴지 정한다.

- `w: 1`: 프라이머리가 적용하면 답한다.
- `w: "majority"`: 투표하는 데이터 멤버 과반이 oplog에 적으면 답한다. 기본값이고, `writeConcernMajorityJournalDefault`가 기본 true라 각 멤버의 저널(디스크에 먼저 남기는 변경 기록)까지 기다린다.
- `j: true`: 저널을 디스크에 쓴 뒤 답한다. 프라이머리 재시작에는 버티지만 장애 조치 롤백은 막지 못한다.

프라이머리는 세컨더리가 보고하는 진행 위치를 모아, 과반이 가진 가장 새 위치를 과반 커밋 지점(majority commit point)으로 삼는다. `rs.status()`의 `optimes.lastCommittedOpTime`이 그 값이다. majority 쓰기는 커밋 지점이 자기 연산을 지날 때까지 기다리고, 느린 작업 로그에는 그 대기 시간이 `waitForWriteConcernDurationMillis`로 따로 남는다.

아래 데모에서 `w: 1`과 `w: "majority"`를 골라 쓰기를 보내고, 앱이 응답을 받는 시각을 비교한다.

</figure>

프라이머리가 쓰기를 적용하는 시간은 두 모드에서 같다. majority는 그 뒤에 세컨더리 하나가 받아 저널에 적고 위치를 보고하는 왕복을 더 기다린다. 세컨더리가 바쁘거나 디스크가 늦으면 그 차이가 그대로 응답 시간이 된다.

거래 서비스에서 트래픽이 몰린 시간대의 느린 쿼리 로그를 모아 보니, 대부분 쿼리 실행보다 `waitForWriteConcernDurationMillis`가 길었다(사례). 인덱스로 고칠 문제가 아니라 복제를 기다린 시간이라서, 늦게 확인해도 되는 쓰기를 `w: 1`로 낮추는 안이 나왔다.

그 대가는 롤백이다. `w: 1`로 응답한 쓰기가 세컨더리에 닿기 전에 프라이머리가 죽으면 새 프라이머리는 그 쓰기 없이 시작한다. 옛 프라이머리가 돌아오면 새 프라이머리에 없는 쓰기를 되돌려 `<dbpath>/rollback/` 아래 BSON 파일로 남긴다. 앱은 성공 응답을 받았는데 데이터는 없는 상태라서, **몇 건 잃어도 되는 쓰기에만** `w: 1`을 쓴다.

읽기 선호(read preference)는 드라이버가 읽기를 어느 멤버로 보낼지 정한다.

- primary: 기본값. 항상 최신을 읽고, 프라이머리가 없으면 에러다.
- primaryPreferred: 프라이머리에서 읽고, 없을 때만 세컨더리로 간다.
- secondaryPreferred: 세컨더리에서 읽고, 쓸 수 있는 세컨더리가 없으면 프라이머리로 간다.

세컨더리는 비동기로 따라오므로 primary가 아닌 모드는 모두 낡은 데이터를 읽을 수 있다. `maxStalenessSeconds`(최솟값 90초)로 많이 뒤처진 세컨더리는 빼지만 몇 초 지연은 막지 못한다. 방금 쓴 것을 바로 보여 줘야 하는 화면은 primary로 읽는다.

## 커넥션 풀

드라이버의 클라이언트(MongoClient)는 멤버마다 커넥션 풀을 하나씩 둔다. 풀 크기는 세 값으로 정한다(드라이버 공통 기본값).

```text
maxPoolSize   = 100   멤버 하나에 열 수 있는 최대 연결
minPoolSize   = 0     쉬고 있어도 유지할 최소 연결
maxIdleTimeMS = 0     쉬는 연결을 닫기까지의 시간, 0은 닫지 않음
```

풀과 별도로 멤버마다 상태 감시용 연결을 최대 2개 연다. 하나는 서버 상태가 바뀔 때까지 응답을 미루는 `hello` 요청(awaitable hello)을 걸어 두고, 하나는 왕복 시간을 잰다. 3대 레플리카 셋이면 앱 프로세스 하나가 감시 연결만 6개를 연다.

서버 쪽에서 연결 하나는 스레드 하나와 파일 디스크립터 2개를 쓰고, 메모리는 최대 1MB를 쓴다(공식 문서). 연결이 쉬고 있어도 스레드와 메모리는 남는다. 프라이머리가 받는 연결 수는 앱 쪽 숫자의 곱이다.

```text
프라이머리 연결 ≈ 앱 프로세스 수 × (풀에 열린 연결 + 감시 연결 2)
파드 300개 × maxPoolSize 100 = 최대 30,000
```

API 처리량을 늘리려 파드를 늘리면 DB 연결도 같은 배수로 는다. 앱은 수평으로 늘어나지만 쓰기를 받는 프라이머리는 한 대다.

### 연결이 많을 때 DB 쪽 문제

연결은 쉬고 있어도 서버 자원을 쥐고 있다. 수가 커지면 문제가 여러 곳에서 같이 생긴다.

- 메모리: 연결 2만 5천 개면 최대 25GB가 WiredTiger 캐시 밖에서 쓰인다. 캐시 기본값이 (메모리 - 1GB) × 50%라 64GB 서버는 캐시 31.5GB와 합쳐 메모리가 거의 찬다. OS 페이지 캐시가 밀려나고, 모자라면 스왑이 일어나 요청이 디스크를 기다린다.
- 스레드: 연결마다 스레드가 하나라 스레드만 수만 개다. 일하는 연결이 늘면 적은 CPU를 두고 차례를 다퉈 컨텍스트 스위칭이 늘고, 프로세스 수 제한(`ulimit -u`)에 닿으면 새 스레드를 만들지 못한다.
- 파일 디스크립터: `ulimit -n`에 닿으면 새 연결이 거부되고 `connections.rejected`가 오른다.
- 연결 폭주: 새 연결은 TCP, TLS 핸드셰이크와 인증(SCRAM)을 거친다. SCRAM은 해시를 수천 번 반복하는 일부러 느린 계산이라 CPU를 쓴다. 롤링 배포로 파드 수백 개가 한꺼번에 다시 붙으면 이 비용이 몰려 CPU가 튄다.
- 페일오버: 프라이머리가 바뀌면 옛 프라이머리의 연결이 모두 끊기고 같은 수가 새 프라이머리로 몰린다. 평소 연결 수가 곧 장애 순간 재연결 폭주의 크기다.

진단은 `serverStatus`의 연결 항목에서 시작한다(사례 값).

```text
db.serverStatus().connections
  current   24764   열린 연결
  active      922   지금 명령을 처리하는 연결
  rejected      0   한도에 걸려 거부한 연결
```

current와 active의 차이가 쉬는 연결이다. 어느 앱이 많이 여는지는 `$currentOp`에 `idleConnections: true`를 주고 클라이언트 주소별로 묶어 본다.

이벤트 API는 파드 약 300개가 각자 풀 min 5, max 100으로 붙어 있었다. 프라이머리에 연결이 약 25,000개 열려 있었는데 실제로 명령을 처리하던 연결은 약 900개였다(사례 대략값). 몰린 순간 열린 연결이 `maxIdleTimeMS` 0 때문에 닫히지 않고 남았고, 연결 메모리가 쌓여 메모리 압박과 스왑으로 이어졌다.

아래 데모에서 maxPoolSize를 고르고 실행을 눌러, 파드가 늘고 트래픽이 몰린 뒤 프라이머리에 남는 연결 수를 비교한다.

<figure class="fig" data-figure="mongodb-pool">
  <figcaption>파드 수와 풀 크기로 곱해지는 프라이머리 연결</figcaption>
</figure>

몰림이 지나간 뒤 일하는 연결은 두 모드 모두 900개 안팎이다. 처리할 요청 양이 같아서다. 풀이 100이면 몰린 순간 연 연결이 그대로 남아 2만 5천 개가 되고, 10이면 파드당 10개에서 멈춘다.

풀을 줄이면 몰린 순간 넘치는 요청은 앱의 풀 대기열에서 기다린다. 프라이머리도 한 번에 저장 엔진에 들이는 작업 수가 정해져 있어서(뒤의 티켓), 연결을 많이 열어 둬도 줄 서는 자리가 DB 안으로 옮겨질 뿐이다. 조치는 이렇게 정했다(사례).

- maxPoolSize 10, 무거운 서버 몇 개만 50
- 지연을 견디는 읽기는 secondaryPreferred로 세컨더리에 보냄
- 몰린 뒤 남은 연결을 닫도록 maxIdleTimeMS 설정을 제안

연결 수 말고도 프라이머리로 새는 읽기가 있었다.

- 파드가 뜰 때 메모리 캐시를 채우려 컬렉션을 크게 읽었다. 롤링 배포는 파드를 차례로 다시 띄우므로 배포 때마다 프라이머리 CPU가 튀었다.
- 세컨더리 사양을 바꾸는 동안 읽을 수 있는 세컨더리가 없어지자, secondaryPreferred 읽기가 규칙대로 프라이머리로 넘어왔다.
- 모니터링 에이전트가 스키마를 보려고 `$sample`로 문서를 뽑는 쿼리가 프라이머리에서 돌았다.

## WiredTiger 쓰기 정지

WiredTiger는 MongoDB의 저장 엔진이다. 문서를 고치면 메모리의 WiredTiger 캐시에서 페이지를 바꾸고, 변경은 저널에 먼저 적는다(기본 100ms마다 디스크에 동기화). 캐시에서 바뀌었지만 데이터 파일에 아직 안 쓴 페이지를 dirty 페이지라고 한다. 캐시 크기는 기본으로 (RAM − 1GB)의 50%와 256MB 중 큰 값이다.

dirty 페이지가 데이터 파일로 가는 길은 둘이다.

- 체크포인트(checkpoint): 60초마다 그 시점의 데이터를 데이터 파일에 쓴다.
- 축출(eviction): 캐시 자리를 비우려 페이지를 내보낸다. dirty 페이지면 먼저 쓴다.

축출은 캐시 대비 비율로 움직인다(WiredTiger 기본값). MongoDB는 축출 전용 스레드를 최소 4개, 최대 4개로 띄운다(소스 기본값).

```text
eviction_target         80%   전체 사용량이 넘으면 축출 스레드가 일한다
eviction_trigger        95%   넘으면 요청 스레드도 축출에 끌려간다
eviction_dirty_target    5%   dirty가 넘으면 축출 스레드가 dirty부터 내린다
eviction_dirty_trigger  20%   넘으면 요청 스레드가 끌려가 쓰기가 느려진다
```

요청 스레드가 축출에 끌려가면 문서를 고치던 스레드가 디스크 쓰기를 기다린다. 저장 엔진에 동시에 들어갈 수 있는 작업 수는 읽기와 쓰기 티켓으로 제한된다(각각 최대 128, 부하에 따라 자동 조정). 티켓을 쥔 쓰기가 디스크를 기다리며 놓지 않으면 티켓이 바닥나고, 다음 쓰기는 대기열(`serverStatus`의 `queues.execution`)에서 기다린다.

OS의 페이지 캐시도 한 겹 더 있다. 리눅스는 dirty 페이지가 `vm.dirty_background_ratio`(커널 기본 10%)를 넘으면 백그라운드로 쓰기 시작하고, `vm.dirty_ratio`(커널 기본 20%)를 넘으면 쓰는 프로세스를 직접 멈춰 세운다. 메모리가 큰 서버에서 20%는 수십 GB라서 체크포인트가 그만큼을 한꺼번에 디스크로 밀어낼 수 있다. 메모리가 모자라 스왑을 쓰면 캐시 접근까지 디스크 읽기가 된다.

거래 서비스의 저녁 쓰기 몰림에서는 아래 그림처럼 이 순서로 모든 쓰기가 약 4초 멈췄다(사례 대략값).

1. 쓰기가 몰려 dirty 데이터가 쌓인다.
2. 축출이 따라가지 못해 요청 스레드가 축출에 끌려가고, 체크포인트가 쌓인 dirty를 한꺼번에 내린다.
3. 디스크 대기 시간(io_await)이 튄다.
4. 쓰기 티켓이 바닥난다.

<figure class="fig" data-figure="mongodb-stall">
  <figcaption>dirty 비율, 쓰기 티켓, 초당 쓰기 (사례를 단순화한 모양)</figcaption>
</figure>

정지가 4초뿐이라 10~15초 간격으로 평균을 내는 모니터링 그래프에서는 쓰기가 조금 줄어든 정도로 보인다. MongoDB는 FTDC(Full-Time Diagnostic Data Capture)로 `serverStatus`, `replSetGetStatus`, CPU와 디스크 지표를 1초마다 `dbPath/diagnostic.data`에 압축해 남긴다. 쿼리 내용은 담지 않고 폴더 크기 상한을 넘으면 오래된 것부터 덮어쓰므로, 사고 직후 폴더를 복사해 둔다.

기본값으로 쌓일 수 있는 양을 계산하면 정지의 크기가 보인다. 메모리 64GB 서버 기준이다.

```text
WiredTiger 캐시    (64GB - 1GB) × 50%  ≈ 31.5GB
dirty_target  5%   ≈ 1.6GB까지는 축출 스레드가 천천히 내린다
dirty_trigger 20%  ≈ 6.3GB에서 요청 스레드가 축출에 끌려간다
OS dirty_background_ratio 10%  ≈ 6.4GB부터 백그라운드 쓰기
OS dirty_ratio            20%  ≈ 12.8GB에서 쓰는 프로세스가 직접 멈춘다
```

두 겹 모두 수 GB를 쌓아 둘 수 있어서, 디스크가 초당 수백 MB를 쓰면 한 번 비우는 데 수 초가 걸린다. 그래서 튜닝은 축출이 dirty를 더 일찍 꾸준히 내리게 하고(dirty target과 축출 스레드 수), OS가 쌓아 두는 비율을 낮추는 쪽으로 한다. 값은 디스크 처리량에 맞춰 정한다.

사례에서는 이렇게 튜닝한 뒤 체크포인트 한 번에 내리는 양이 약 800MB에서 약 45MB로 줄었다(사례 대략값). 그래도 1초짜리 정지는 남았다.

FTDC를 세 멤버 나란히 1초 단위로 놓자, 프라이머리와 세컨더리 하나가 같은 초에 디스크 쓰기 0바이트를 찍고 세 번째 멤버는 멀쩡했다. 두 멤버의 볼륨이 같은 공유 스토리지 노드에 있었다. 3대 중 2대가 함께 멈추면 아래 그림처럼 과반 커밋 지점이 앞으로 가지 못하고, 세 번째 멤버는 프라이머리에게서 oplog를 당겨 오고 있어서 받을 것도 없었다.

<figure class="fig" data-figure="mongodb-storage">
  <figcaption>저장 노드 하나의 정지와 과반</figcaption>
</figure>

멤버 하나를 다른 저장 노드로 옮기자 정지가 사라졌다. 저장 노드 하나가 멈춰도 그 위의 멤버 하나만 늦고 나머지 둘로 과반이 선다. **레플리카 셋의 고장 단위는 서버가 아니라 디스크까지 내려간 물리 자원**이라서, 멤버를 나눌 때 볼륨이 어느 저장 노드에 놓이는지까지 나눈다.

## 샤드 클러스터

세컨더리를 늘리면 읽기와 복사본은 늘지만 쓰기는 모든 멤버가 똑같이 다시 실행한다. 레플리카 셋은 쓰기를 나누지 못한다. 거래 서비스는 쓰기가 많은 컬렉션 몇 개가 한 프라이머리에 몰렸고, 서버도 이미 고를 수 있는 가장 큰 사양이었다(사례).

샤드 클러스터(sharded cluster)는 아래 그림처럼 데이터를 샤드 키(shard key) 값의 범위로 나눠 여러 레플리카 셋에 둔다.

- 샤드: 데이터 일부를 가진 레플리카 셋. 샤드마다 프라이머리가 있어 쓰기를 따로 받는다.
- config 서버: 어느 범위가 어느 샤드에 있는지 적은 메타데이터를 가진 레플리카 셋.
- mongos: 라우터. 메타데이터를 캐시해 두고 쿼리를 맞는 샤드로 보낸다. 자체 상태가 없어 여러 대 띄운다.

<figure class="fig" data-figure="mongodb-shard">
  <figcaption>레플리카 셋과 샤드 클러스터의 쓰기 분산</figcaption>
</figure>

샤드 키는 공식 문서의 세 기준으로 고른다.

- 카디널리티(cardinality): 값의 가짓수. 같은 키 값은 한 청크를 넘어 나뉘지 못해서, 값이 7가지면 샤드를 7개 넘게 둬도 쓸모가 없다.
- 빈도(frequency): 특정 값에 문서가 몰리면 그 값의 범위가 병목이 되고, 더 쪼갤 수도 없다.
- 단조 증가: 시각이나 ObjectId처럼 계속 커지는 키는 새 문서가 전부 마지막 범위(maxKey 쪽)로 가서 샤드 하나가 쓰기를 다 받는다.

나누는 방식은 둘이다.

- 범위(ranged): 키 값 순서대로 나눈다. 범위 쿼리가 샤드 몇 개로 좁혀지지만 단조 증가 키에 약하다.
- 해시(hashed): 키의 해시 값으로 나눈다. 단조 증가 키도 고르게 퍼지지만 키 범위 쿼리는 모든 샤드로 간다.

거래 서비스에는 계정 ID를 샤드 키로 제안했다(사례). 계정이 많아 카디널리티가 높고, 쿼리 대부분이 계정 하나의 데이터를 읽어 샤드 하나로 간다.

mongos는 쿼리에 샤드 키(복합 샤드 키면 그 앞부분)가 있으면 캐시에서 그 값이 든 범위를 찾아 해당 샤드에만 보낸다(targeted). 없으면 모든 샤드에 보내고 응답을 다 기다려 합친다(scatter-gather). 아래 그림처럼 scatter-gather는 가장 느린 샤드에 맞춰 끝나고, 샤드를 늘려도 빨라지지 않는다.

<figure class="fig" data-figure="mongodb-route">
  <figcaption>mongos가 쿼리를 샤드로 보내는 두 경로</figcaption>
</figure>

데이터는 범위(청크, 기본 128MB) 단위로 샤드에 놓인다. config 서버 프라이머리에서 도는 밸런서는 컬렉션 하나에서 두 샤드의 데이터 차이가 범위 크기의 3배(기본 384MB)를 넘으면 범위를 옮긴다. 옮기는 동안 원래 샤드가 쓰기를 계속 받고, 다 옮기면 메타데이터를 바꾼 뒤 원본을 지운다. 복사와 삭제가 디스크와 캐시를 쓰므로 밸런서가 도는 시간대를 정해 둘 수 있다.

샤딩의 비용은 기존 데이터와 쿼리에서 나온다.

- 레플리카 셋을 샤드 클러스터로 바꾸려면 config 서버와 mongos를 더하고, 앱이 mongos로 붙게 바꾼 뒤 컬렉션을 샤딩해야 한다. 샤드 키는 나중에 `reshardCollection`으로 바꿀 수 있지만 컬렉션 전체를 다시 쓴다.
- 쿼리마다 샤드 키를 넣도록 고친다. `updateOne`, `deleteOne`은 샤드 키나 `_id`가 없으면 에러다.

그래서 제안은 새 기능부터 샤드 클러스터에서 시작하고, 기존 컬렉션은 데이터 이전과 쿼리 수정을 거쳐 옮기는 순서였다(사례).

샤드 키가 쿼리를 샤드 하나로 보내도, 샤드 안에서 문서를 찾는 것은 인덱스다. 한 사용자의 기록을 날짜 범위로 걸러 `createdAt` 내림차순으로 정렬하는 쿼리가 약 20초 걸렸다(사례 대략값).

```js
db.history.find({ userId: 42, createdAt: { $gte: from, $lt: to } }).sort({ createdAt: -1 })
db.history.createIndex({ userId: 1, createdAt: -1 })
```

복합 인덱스의 필드는 ESR(같음, 정렬, 범위) 순서로 둔다. 같음 조건인 `userId`를 앞에 두면 그 사용자의 항목이 한데 모이고, 그 안에서 `createdAt`이 이미 내림차순이라 메모리 정렬 없이 읽는다. 범위 조건도 같은 `createdAt`이라 필요한 구간만 잘라 읽는다. 인덱스를 만든 뒤 지연을 견디는 이 조회는 세컨더리로 옮겼다.
