## push 방식과 pull 방식

운영 클러스터의 replicas가 저장소에는 3으로 적혀 있는데 실제로는 5다. 누가 언제 바꿨는지는 어디에도 남아 있지 않다.

흔한 배포는 push 방식이다. CI 파이프라인이 빌드 끝에 `kubectl apply`나 `helm upgrade`로 클러스터에 직접 밀어 넣는다.

- CI가 클러스터 접속 정보(kubeconfig)를 들고 있어야 한다. CI가 털리면 클러스터도 열린다.
- CI는 배포하는 순간에만 클러스터를 본다. 그 뒤에 누가 손으로 바꿔도 알 길이 없다.

GitOps는 pull 방식이다. 클러스터 안의 에이전트가 Git 저장소를 주기적으로 읽어 와서, 클러스터를 저장소에 적힌 상태와 같게 맞춘다. 아래 두 장면에서 클러스터 접속 정보가 어디에 있는지, 누가 손으로 replicas를 바꾼 뒤 무엇이 일어나는지 본다.

<figure class="fig" data-figure="gitops-push-pull">
  <figcaption>push 방식과 pull 방식에서 손으로 바꾼 값의 행방</figcaption>
</figure>

push 방식에서는 손으로 바꾼 5가 그대로 남고, Git과 클러스터가 서로 다른 말을 한다. pull 방식에서는 클러스터 안의 에이전트가 차이를 찾아 Git의 3으로 되돌린다. 접속 정보도 클러스터 밖으로 나가지 않는다.

OpenGitOps는 이 방식을 원칙 네 가지로 정리해 두었다.

- 선언형(Declarative): 원하는 상태를 선언으로 적는다.
- 버전 관리와 불변(Versioned and Immutable): 원하는 상태를 고칠 수 없는 이력과 함께 저장한다.
- 자동으로 가져옴(Pulled Automatically): 에이전트가 원하는 상태를 저장소에서 가져간다.
- 계속 맞춤(Continuously Reconciled): 에이전트가 실제 상태를 계속 보고 원하는 상태로 맞춘다.

Git이 기준이 되면 배포 기록은 커밋 기록이 되고, 되돌리기는 `git revert`가 된다. 배포 경로를 고를 때는 클러스터 접속 정보가 어디에 있는지부터 본다.

## CI 파이프라인

GitOps에서 CI의 몫은 이미지를 만들고 매니페스트의 태그를 바꾸는 데까지다. 클러스터에는 손대지 않는다.

### PR 검사

테스트가 깨진 코드가 main에 들어가 그대로 배포까지 간다. PR 단계에서 막을 장치가 없어서다.

GitHub Actions는 PR이 열리거나 커밋이 더해질 때마다 워크플로를 돌린다.

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: '3.13'
      - run: pip install -r requirements.txt
      - run: pytest
```

워크플로가 돈다고 merge가 막히지는 않는다. 저장소의 브랜치 보호 규칙에서 "Require status checks to pass before merging"을 켜고 이 잡을 필수 검사로 등록해야, 검사가 실패한 PR의 merge 버튼이 잠긴다.

아래 두 장면에서 PR이 검사를 지나 main에 닿는지, 검사 하나가 실패하면 어디서 멈추는지 본다.

<figure class="fig" data-figure="gitops-ci-gate">
  <figcaption>필수 검사를 통과한 PR만 main에 들어간다</figcaption>
</figure>

검사가 모두 초록이면 PR이 main에 들어가고, 하나라도 빨강이면 merge 버튼에서 멈춘다. 워크플로 파일만 두고 필수 검사를 등록하지 않으면 빨강이어도 merge된다. 새 저장소를 만들면 브랜치 보호 규칙에 테스트 잡 이름을 등록하는 것부터 한다.

### 이미지 빌드와 태그

장애가 나서 이전 버전으로 되돌리려는데, 돌고 있는 이미지가 `app:latest`라 어느 커밋에서 만든 것인지 알 수 없다.

main에 merge되면 이미지를 빌드해 레지스트리에 올린다. GitHub의 컨테이너 레지스트리(ghcr.io)는 워크플로가 자동으로 받는 `GITHUB_TOKEN`으로 올릴 수 있어서, 따로 토큰을 만들 필요가 없다.

{% raw %}
```yaml
# .github/workflows/cd.yml
name: CD
on:
  push:
    branches: [main]
permissions:
  contents: read
  packages: write
jobs:
  image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```
{% endraw %}

태그는 커밋 SHA로 붙인다. 이미지 태그는 이름표라서 `latest`처럼 같은 이름에 다른 내용을 계속 덮어쓸 수 있다. 같은 새 버전을 두 가지 태그로 내보낼 때 클러스터에서 무엇이 달라지는지 두 장면으로 견줘 보자.

<figure class="fig" data-figure="gitops-image-tag">
  <figcaption>latest 태그와 커밋 SHA 태그로 새 버전을 내보낼 때</figcaption>
</figure>

`latest`는 이미지 내용만 바뀌고 매니페스트의 글자는 그대로라, ArgoCD가 보기에는 바뀐 게 없다. 그 뒤로 새로 뜨는 파드만 새 이미지를 받아서 버전이 섞인다. SHA 태그는 매니페스트 한 줄이 바뀌므로 배포가 Git 커밋으로 남고, 되돌릴 때는 그 커밋을 되돌린다.

배포에 쓰는 태그는 한 번 쓰면 다시 쓰지 않는 값(커밋 SHA, 릴리스 버전)으로 정한다.

## 매니페스트 저장소

### 앱 저장소와 매니페스트 저장소

CI가 새 이미지 태그를 앱 저장소에 커밋했더니, 그 커밋이 다시 CI를 돌린다. 매니페스트를 앱 코드와 같은 저장소에 두면 흔히 생기는 일이다.

Argo CD 문서는 매니페스트를 별도 저장소에 두라고 권한다.

- CI가 매니페스트를 고쳐 커밋해도 빌드가 다시 돌지 않는다.
- replicas만 바꾸는 커밋에 전체 빌드를 돌리지 않는다.
- 매니페스트 저장소의 커밋 기록이 곧 배포 기록이 된다.
- 앱 코드를 고칠 권한과 운영 설정을 고칠 권한을 나눌 수 있다.

흐름은 다섯 단계다. 아래 그림에서 CI가 클러스터에 직접 닿지 않고 매니페스트 저장소까지만 가는 것을 본다.

<figure class="fig" data-figure="gitops-two-repos">
  <figcaption>앱 저장소의 커밋 하나가 클러스터까지 가는 길</figcaption>
</figure>

CI의 마지막 단계는 매니페스트 저장소에 태그 한 줄을 커밋하는 것이다. 클러스터에 배포하는 일은 ArgoCD가 그 커밋을 읽어 가서 한다.

`GITHUB_TOKEN`은 워크플로가 있는 저장소에만 권한이 있다. 다른 저장소에 푸시하려면 그 저장소에만 쓰기 권한을 준 GitHub App 토큰이나 fine-grained 개인 토큰을 시크릿으로 넣는다.

{% raw %}
```yaml
      - uses: actions/checkout@v7
        with:
          repository: kimjanghyun1010/argo-kustomize
          token: ${{ secrets.MANIFEST_TOKEN }}
          path: manifests
      - run: |
          cd manifests/overlays/dev
          kustomize edit set image app=ghcr.io/${{ github.repository }}:${{ github.sha }}
          git config user.name ci-bot
          git config user.email ci-bot@users.noreply.github.com
          git commit -am "dev: app ${{ github.sha }}"
          git push
```
{% endraw %}

GitHub가 제공하는 Ubuntu 러너에는 kustomize가 깔려 있어서 설치 단계가 필요 없다. 토큰은 매니페스트 저장소 하나에만, 쓰기 권한만 주는 것부터 지킨다.

### kustomize 오버레이

dev와 prod의 매니페스트는 replicas와 이미지 태그만 다른데, 폴더 두 벌을 복사해 두었더니 한쪽만 고쳐진 채 배포된다.

kustomize는 공통 YAML을 base에 두고, 환경마다 다른 값만 overlay에 적는다. kubectl 1.14부터 kubectl에 들어 있다.

```text
argo-kustomize/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/kustomization.yaml
    └── prod/kustomization.yaml
```

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
replicas:
  - name: app
    count: 5
images:
  - name: app
    newName: ghcr.io/kimjanghyun1010/app
    newTag: 3f2a91c
```

두 장면에서 같은 base가 overlay를 지나며 어느 줄만 바뀌는지 본다.

<figure class="fig" data-figure="gitops-kustomize">
  <figcaption>base 하나에 overlay를 덮어 환경별 매니페스트를 만든다</figcaption>
</figure>

base는 한 벌이고, 결과물에서 달라지는 줄은 overlay에 적은 두 줄뿐이다. 공통 설정을 고칠 때는 base 하나만 고치면 두 환경에 같이 들어간다. 결과물은 `kubectl kustomize overlays/prod`로 미리 본다.

Helm도 같은 문제를 푼다. 방식이 다르다.

- Helm: 템플릿에 빈칸을 두고 values.yaml의 값을 끼워 넣는다. 남에게 배포할 패키지를 만들 때 맞는다.
- kustomize: 완성된 YAML 위에 바뀐 부분만 덮어쓴다. 템플릿 문법이 없어서 base가 그대로 유효한 매니페스트다.

환경이 둘 이상이면 폴더를 복사하기 전에 base와 overlay로 나눈다.

## ArgoCD

### 동기화 루프

매니페스트 저장소에 커밋했는데 클러스터가 몇 분 동안 그대로다. ArgoCD가 저장소를 아직 읽어 가지 않아서다.

ArgoCD에서 배포 단위는 Application이다. 어느 저장소의 어느 경로를 어느 클러스터에 맞출지 적는다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: app-dev
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/kimjanghyun1010/argo-kustomize.git
    targetRevision: main
    path: overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

ArgoCD는 이 Application마다 같은 루프를 돈다.

1. 저장소를 읽어 kustomize나 Helm으로 매니페스트를 만든다(repo-server).
2. 만든 매니페스트와 클러스터의 실제 리소스를 견준다(application-controller).
3. 같으면 Synced, 다르면 OutOfSync다. 자동 동기화가 켜져 있으면 다른 부분을 적용한다.

저장소는 기본으로 3분마다 읽는다. 정확히는 120초에 최대 60초의 흔들림(jitter)을 더한 간격이다. 모드를 바꿔 가며 커밋을 푸시해 보고, 클러스터가 새 버전으로 바뀌는 시각을 본다.

<figure class="fig" data-figure="gitops-sync">
  <figcaption>커밋에서 클러스터 반영까지 걸리는 시간</figcaption>
</figure>

폴링만 쓰면 커밋은 다음 폴링까지 기다렸다가 반영된다. 이 예에서는 140초를 기다렸고, 직전 폴링 바로 뒤에 커밋하면 3분 가까이 기다린다. 웹훅을 걸면 Git 서버가 푸시 순간 ArgoCD에 알려서 몇 초 안에 반영된다. 바뀐 것은 **ArgoCD가 저장소를 읽는 시점**뿐이고 동기화 과정은 같다.

ArgoCD는 GitHub, GitLab, Bitbucket, Azure DevOps 등의 웹훅을 받는다. 배포가 몇 분씩 늦다면 웹훅이 걸려 있는지부터 본다.

### 드리프트와 selfHeal

장애 대응 중에 `kubectl scale`로 replicas를 3에서 5로 늘렸다. 저장소에는 여전히 3이 적혀 있다.

실제 상태가 Git과 달라진 것을 드리프트(drift)라고 한다. ArgoCD는 드리프트를 OutOfSync로 표시하지만, 되돌릴지는 설정에 달렸다. 모드를 바꿔 가며 kubectl로 직접 고쳐 보고, 파드 수가 어떻게 되는지 지켜본다.

<figure class="fig" data-figure="gitops-drift">
  <figcaption>클러스터를 손으로 고쳤을 때 selfHeal의 동작</figcaption>
</figure>

selfHeal이 꺼져 있으면 파드는 5개로 남고 화면에 OutOfSync만 뜬다. 켜져 있으면 ArgoCD가 몇 초 안에 Git의 3으로 되돌린다. 두 모드 모두 차이는 알아채고, 바뀌는 것은 **알아챈 뒤 되돌리느냐**다.

자동 동기화의 기본값은 보수적이다.

- `selfHeal`: 기본 꺼짐. 클러스터를 직접 고친 것은 자동 동기화를 일으키지 않는다.
- `prune`: 기본 꺼짐. Git에서 지운 리소스를 클러스터에서 지우지 않는다.

selfHeal을 켜면 긴급 수정도 Git 커밋으로 해야 한다. 손으로 고친 값은 몇 초 뒤 사라진다. HPA처럼 다른 컨트롤러가 바꾸는 필드는 매니페스트에서 빼거나 `ignoreDifferences`로 비교에서 뺀다. 그러지 않으면 ArgoCD와 HPA가 replicas를 두고 계속 서로 되돌린다.

운영 환경에는 selfHeal을 켜고, 긴급 수정 절차를 "Git에 커밋하고 웹훅으로 바로 반영"으로 정해 둔다.

## 여러 앱 관리

### App of Apps

앱이 30개로 늘었다. Application YAML을 하나씩 `kubectl apply`로 올리다 보니, 어떤 Application이 클러스터에 있는지가 Git 밖에 있다.

App of Apps는 Application을 계층으로 쌓는다. 루트 Application 하나가 Application YAML만 들어 있는 폴더를 가리킨다. Argo CD 문서의 정의도 한 줄이다. "다른 앱들로만 이뤄진 Argo CD 앱 하나를 선언한다."

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/kimjanghyun1010/gitops-repo.git
    targetRevision: main
    path: apps
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated: {}
```

```text
gitops-repo/apps/
├── bookinfo.yaml
├── istio-base.yaml
└── todo-api.yaml
```

아래 두 장면에서 루트가 폴더를 읽어 자식 Application을 만들고, 파일 하나를 더하면 앱이 하나 늘어나는 것을 본다.

<figure class="fig" data-figure="gitops-app-of-apps">
  <figcaption>루트 Application 하나가 apps 폴더의 Application을 데려온다</figcaption>
</figure>

루트가 만드는 것은 파드가 아니라 Application이고, 각 Application이 다시 자기 매니페스트를 동기화한다. 앱을 늘리는 일은 YAML 한 장을 커밋하는 일이 되고, 빼는 일은 파일 하나를 지우는 일이 된다.

> **부모 저장소에 푸시할 수 있으면 관리자다.** 자식 Application의 `project` 필드를 바꾸면 아무 프로젝트에나 배포할 수 있다. 문서도 App of Apps를 관리자 전용 도구로 분류하고, 부모 저장소의 푸시 권한은 관리자만 갖게 하라고 적어 두었다. 그 저장소의 PR에서는 `project` 필드부터 본다.
{: .warn}

### ApplicationSet

dev, staging, prod 클러스터마다 apps 폴더를 복사해 두었다. 앱 하나를 추가할 때마다 세 폴더를 고치고, 클러스터가 늘면 폴더를 또 복사한다.

Argo CD 문서는 App of Apps를 대안으로 분류하고, 이 경우 ApplicationSet의 cluster generator를 권한다. ApplicationSet은 generator가 만든 목록마다 template으로 Application을 하나씩 찍어 낸다.

{% raw %}
```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: app
  namespace: argocd
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            env: prod
  template:
    metadata:
      name: 'app-{{name}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/kimjanghyun1010/argo-kustomize.git
        targetRevision: main
        path: overlays/prod
      destination:
        server: '{{server}}'
        namespace: app
```
{% endraw %}

ArgoCD에 등록된 클러스터 중 `env: prod` 라벨이 붙은 것마다 Application이 생긴다. 두 장면에서 라벨이 맞는 클러스터에만 Application이 생기고, 새 클러스터를 등록하면 저절로 하나가 더 생기는 것을 본다.

<figure class="fig" data-figure="gitops-appset">
  <figcaption>cluster generator가 라벨로 고른 클러스터마다 Application을 만든다</figcaption>
</figure>

클러스터를 늘릴 때 고치는 것은 폴더가 아니라 클러스터의 라벨이다. 라벨이 맞지 않는 dev 클러스터에는 아무것도 생기지 않는다.

generator는 목록을 어디서 가져오느냐에 따라 나뉜다.

- List: YAML에 직접 적은 목록
- Cluster: ArgoCD에 등록된 클러스터
- Git: 저장소의 디렉터리나 파일
- Matrix, Merge: 두 generator의 조합
- Pull Request: 열린 PR마다 미리보기 환경

클러스터가 늘 때마다 폴더를 복사하고 있다면, 그때가 ApplicationSet으로 옮길 지점이다.

## 점진 배포

### 카나리

새 버전에 버그가 있었는데, 롤링 업데이트가 2분 만에 파드를 전부 바꿔서 모든 사용자가 에러를 봤다.

쿠버네티스의 Deployment가 주는 전략은 롤링 업데이트(RollingUpdate)와 재생성(Recreate) 둘이다. 카나리와 블루그린은 Argo Rollouts를 설치하고 Deployment 대신 Rollout 리소스를 쓴다.

카나리(canary)는 새 버전에 트래픽 일부만 보내 놓고 지켜본다. `setWeight`로 비율을 정하고 `pause`로 기다린다.

```yaml
strategy:
  canary:
    steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - setWeight: 50
      - pause: { duration: 5m }
```

모드를 바꿔 가며 버그 있는 버전을 배포해 보고, 에러를 받는 요청 비율이 어디까지 올라가는지 본다.

<figure class="fig" data-figure="gitops-canary">
  <figcaption>버그 있는 버전을 배포했을 때 에러를 받는 요청 비율 (시간은 설명용 대략값)</figcaption>
</figure>

롤링 업데이트는 파드가 바뀌는 만큼 에러 비율이 올라 2분 뒤 100%가 된다. 카나리는 10%에서 멈춰 기다리는 동안 문제를 찾고 중단해서, 에러가 10% 안에서 끝난다. 두 모드 모두 새 버전은 같고, 바뀐 것은 **한 번에 노출하는 비율**이다.

트래픽 라우팅을 설정하지 않으면 비율은 파드 수로 맞춘다. 파드 10개에 10%면 새 버전 1개, 이전 버전 9개다. 파드 수로 나눠떨어지지 않는 비율은 가장 가까운 정수 개수로 맞춘다. 비율을 정확히 나누려면 `trafficRouting`에 nginx나 Istio 같은 인그레스를 지정한다.

중단을 사람이 하지 않게 하려면 분석(AnalysisTemplate)을 붙인다. 에러율 같은 지표를 재다가 기준을 넘으면 롤아웃을 중단하고 이전 버전으로 되돌린다. 카나리를 쓴다면 에러율 지표를 분석에 거는 것부터 한다.

### 블루그린

새 버전을 운영 트래픽에 내보내기 전에 운영 환경에서 직접 확인하고 싶다. 문제가 보이면 몇 초 안에 되돌리고 싶다.

블루그린(blue-green)은 새 버전을 통째로 띄워 두고 트래픽을 한 번에 넘긴다. 서비스가 둘이다.

- activeService: 운영 트래픽을 받는다. 승격 전까지 이전 버전을 가리킨다.
- previewService: 새 버전을 가리킨다. 승격 전에 이 주소로 확인한다.

```yaml
strategy:
  blueGreen:
    activeService: app
    previewService: app-preview
    autoPromotionEnabled: false
    scaleDownDelaySeconds: 30
```

세 장면에서 운영 트래픽이 v1에서 v2로 넘어가는 순간과, 승격 뒤 문제가 생겼을 때 다시 v1로 돌아오는 길을 본다.

<figure class="fig" data-figure="gitops-bluegreen">
  <figcaption>preview로 확인하고, 한 번에 넘기고, 필요하면 되돌린다</figcaption>
</figure>

승격은 activeService가 가리키는 대상을 바꾸는 일이라 한 번에 끝난다. 승격 뒤에도 v1은 `scaleDownDelaySeconds`(기본 30초) 동안 살아 있어서, 그 안에 되돌리면 파드를 새로 띄울 필요가 없다. 대신 전환하는 동안 두 버전이 다 떠 있어 자원이 두 배로 든다.

`autoPromotionEnabled`의 기본값은 true라, 그대로 두면 새 버전이 준비되는 대로 바로 넘어간다. 확인 단계를 두려면 false로 바꾸고 `kubectl argo rollouts promote`로 승격한다.

- 블루그린: 두 버전이 겹치는 시간을 줄인다. 넘기기 전에 확인하고, 한 번에 넘기고, 한 번에 되돌린다.
- 카나리: 겹치는 시간을 일부러 두고, 일부 사용자에게만 먼저 보내 지켜본다.

트래픽을 나눠 받을 수 없는 앱(스키마가 바뀌는 배치, 세션이 버전에 묶인 앱)은 블루그린으로, 요청 단위로 나눠도 되는 API는 카나리로 시작한다.

## 정리

| | 하는 일 | 기억할 점 |
|---|---|---|
| pull 방식 | 클러스터 안의 에이전트가 Git을 읽어 맞춘다 | 접속 정보가 클러스터 밖으로 나가지 않는다 |
| PR 검사 | 테스트 잡을 필수 검사로 등록한다 | 등록하지 않으면 실패해도 merge된다 |
| 이미지 태그 | 커밋 SHA로 붙인다 | latest는 Git에 변경이 남지 않는다 |
| 매니페스트 저장소 | 앱 코드와 나눈다 | CI는 태그 한 줄만 커밋한다 |
| kustomize | base 하나에 환경별 overlay | 폴더를 복사하지 않는다 |
| 동기화 루프 | 기본 3분마다 저장소를 읽는다 | 웹훅으로 바로 반영한다 |
| selfHeal | 드리프트를 Git 값으로 되돌린다 | 기본 꺼짐. HPA 필드는 비교에서 뺀다 |
| App of Apps | 루트 하나가 Application 폴더를 가리킨다 | 부모 저장소 푸시 권한은 관리자 권한이다 |
| ApplicationSet | generator 목록마다 Application을 찍는다 | 클러스터가 늘면 라벨로 고른다 |
| 카나리 | 일부 트래픽만 새 버전에 보낸다 | 분석을 붙여 자동으로 중단한다 |
| 블루그린 | 통째로 띄우고 한 번에 넘긴다 | 전환 동안 자원이 두 배다 |
