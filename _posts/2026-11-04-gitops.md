## 요약

- pull 방식은 클러스터 안의 에이전트가 Git을 읽어 계속 맞춘다. 접속 정보가 밖으로 나가지 않는다.
- 에이전트는 Git의 글자만 본다. 이미지는 커밋 SHA로 고정하고, CI는 매니페스트 저장소에 태그 한 줄을 커밋하고 멈춘다.
- ArgoCD는 저장소를 120초에 jitter 60초를 더한 주기로 읽고, 웹훅이면 몇 초 안에 반영한다.
- selfHeal과 prune은 기본 꺼짐이다. HPA가 바꾸는 replicas는 매니페스트에서 빼거나 `RespectIgnoreDifferences`와 함께 비교에서 뺀다.
- Application 자체도 App of Apps나 ApplicationSet으로 Git에 둔다.
- ArgoCD는 버전의 옳고 그름을 모른다. 카나리와 분석이 노출 비율을 묶고, 실패하면 안정 버전으로 돌린다.

## push와 pull

GitOps는 Git 저장소에 적힌 상태를 클러스터의 정답으로 삼는다. 커밋 한 줄은 어떤 길로 운영 클러스터에 닿고, 클러스터가 Git과 어긋나면 누가 되돌릴까?

흔한 push 방식에서는 CI 파이프라인이 빌드 끝에 `kubectl apply`나 `helm upgrade`로 클러스터에 직접 적용한다.

- CI가 클러스터 접속 정보(kubeconfig)를 들고 있어야 한다. CI가 털리면 클러스터도 열린다.
- CI는 배포하는 순간에만 클러스터를 본다. 그 뒤에 누가 `kubectl scale`로 replicas(띄워 둘 파드 수)를 3에서 5로 바꿔도 알 길이 없다.

pull 방식에서는 클러스터 안에서 도는 에이전트(ArgoCD, Flux)가 Git 저장소를 주기적으로 읽고, 클러스터를 저장소에 적힌 상태와 같게 맞춘다. 접속 정보는 클러스터 안에만 있고, 밖으로 나가는 것은 Git을 읽는 요청뿐이다. 아래 그림처럼 손으로 바꾼 값도 다음 비교에서 드러난다.

<figure class="fig" data-figure="gitops-push-pull">
  <figcaption>push 방식과 pull 방식에서 손으로 바꾼 값의 행방</figcaption>
</figure>

pull 방식에서는 배포 기록이 커밋 기록이 되고, 되돌리기는 `git revert`가 된다. 대신 Git에 글자로 남지 않는 변경은 에이전트 눈에 보이지 않는다.

## 불변 태그와 매니페스트 저장소

에이전트는 Git에 적힌 글자만 본다. 새 버전을 내보냈는데 매니페스트의 글자가 그대로면 바뀐 것이 없다. 이미지 태그를 `latest`로 쓰면 이 일이 생긴다.

태그는 이미지에 붙인 이름표라서, 레지스트리의 `app:latest`가 오늘은 v1을, 내일은 v2를 가리킬 수 있다. 쿠버네티스는 `imagePullPolicy`를 적지 않으면 태그를 보고 정한다.

- 태그가 `latest`이거나 없다: `Always`. 파드가 뜰 때마다 레지스트리에 다시 묻는다.
- 그 밖의 태그나 다이제스트: `IfNotPresent`. 노드에 이미지가 있으면 그대로 쓴다.

매니페스트 글자가 그대로라 기존 파드는 v1으로 계속 돌고, 노드 장애나 스케일 아웃으로 새로 뜬 파드만 `Always` 정책에 따라 레지스트리에서 v2를 받는다. 아래 그림처럼 Deployment(같은 파드를 정해진 수만큼 띄워 두는 리소스) 하나 안에 두 버전이 섞이고, ArgoCD 화면은 Git과 같다는 뜻의 Synced에 머문다.

<figure class="fig" data-figure="gitops-image-tag">
  <figcaption>latest 태그와 커밋 SHA 태그로 새 버전을 내보낼 때</figcaption>
</figure>

태그는 커밋 SHA처럼 한 번 쓰면 다시 쓰지 않는 값으로 붙인다. 새 버전마다 매니페스트의 `image:` 한 줄이 바뀌므로 배포가 Git 커밋으로 남고, 되돌릴 때는 그 커밋을 되돌린다. 태그도 레지스트리에서 덮어쓸 수는 있어서, 완전히 고정하려면 `app@sha256:45b2...`처럼 다이제스트(이미지 내용의 해시)로 적는다.

CI는 main에 merge되면 이미지를 SHA 태그로 올린다. GitHub 컨테이너 레지스트리(ghcr.io)에는 워크플로가 자동으로 받는 `GITHUB_TOKEN`으로 올린다.

{% raw %}
```yaml
# .github/workflows/cd.yml (일부)
permissions:
  contents: read
  packages: write
jobs:
  image:
    runs-on: ubuntu-latest
    steps:
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```
{% endraw %}

바뀐 태그는 매니페스트에 적는다. Argo CD 문서는 매니페스트를 앱 코드와 다른 저장소에 두라고 권한다.

- replicas만 바꾸는 커밋에 전체 빌드가 돌지 않는다.
- 앱 코드 권한과 운영 설정 권한을 나눌 수 있다.
- CI의 태그 커밋이 다시 빌드를 부르는 무한 루프가 없다.

마지막 항목은 토큰과 얽혀 있다. `GITHUB_TOKEN`으로 일으킨 이벤트는 새 워크플로 실행을 만들지 않아서, 같은 저장소 안의 루프는 GitHub가 막아 준다. 대신 이 토큰은 워크플로가 있는 저장소에만 권한이 있다. 매니페스트 저장소에 푸시하려면 그 저장소에만 쓰기 권한을 준 토큰(GitHub App 토큰이나 저장소 단위로 권한을 고르는 fine-grained 개인 토큰)을 시크릿으로 넣는다.

kustomize는 공통 YAML을 `base/`에 두고 환경마다 다른 값만 `overlays/<환경>/`에 적는 도구다. 템플릿 문법이 없어서 base가 그대로 유효한 매니페스트다. CI가 쓰는 `kustomize edit set image`는 overlay의 `images:` 항목만 고친다.

```yaml
# overlays/prod/kustomization.yaml
resources:
  - ../../base
replicas:
  - name: app
    count: 5
images:
  - name: app
    newName: ghcr.io/example-org/app
    newTag: 3f2a91c
```

CI는 dev overlay의 태그만 고쳐 매니페스트 저장소에 커밋한다.

{% raw %}
```yaml
      - uses: actions/checkout@v7
        with:
          repository: example-org/app-manifests
          token: ${{ secrets.MANIFEST_TOKEN }}
          path: manifests
      - run: |
          cd manifests/overlays/dev
          kustomize edit set image app=ghcr.io/${{ github.repository }}:${{ github.sha }}
          git config user.name ci-bot
          git config user.email ci-bot@users.noreply.github.com
          git commit -am "dev: app ${{ github.sha }}"
          git push
```
{% endraw %}

prod 승격은 dev에서 확인한 태그를 prod overlay로 옮기는 커밋 하나다. 아래 그림처럼 CI는 매니페스트 저장소에 커밋하고 멈추며, 클러스터에 접속하지 않는다.

## 동기화 루프

ArgoCD에서 배포 단위는 Application이다. 어느 저장소의 어느 경로를 어느 클러스터의 어느 네임스페이스에 맞출지 적는다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: app-dev
spec:
  source:
    repoURL: https://github.com/example-org/app-manifests.git
    targetRevision: main
    path: overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Application 하나를 맞추는 일은 두 구성 요소가 나눠 한다.

1. repo-server가 저장소를 받아 `targetRevision`의 커밋에서 kustomize나 Helm으로 매니페스트를 만든다. 결과는 커밋 SHA를 키로 기본 24시간 캐시해서, 커밋이 그대로면 다시 만들지 않는다.
2. application-controller가 만든 매니페스트와 클러스터의 실제 리소스를 견준다. 실제 리소스는 쿠버네티스 watch API로 받아 둔 클러스터 캐시에서 읽어서, 비교할 때마다 API 서버에 묻지 않는다.
3. 같으면 Synced, 다르면 OutOfSync다. 자동 동기화가 켜져 있으면 다른 리소스를 적용한다.

새 커밋은 다음 폴링에서 알아챈다. 폴링 주기는 `argocd-cm` ConfigMap의 두 값이다.

```text
timeout.reconciliation: 120s
timeout.reconciliation.jitter: 60s
```

120초에 0~60초의 흔들림(jitter)을 더하므로, 직전 폴링 바로 뒤에 한 커밋은 3분 가까이 기다린다.

웹훅을 걸면 이 기다림이 사라진다. Git 서버가 푸시 순간 ArgoCD의 `/api/webhook`으로 알리고, ArgoCD는 그 저장소를 쓰는 Application에 `argocd.argoproj.io/refresh` 어노테이션을 달아 바로 다시 비교하게 한다. 아래 데모에서 모드를 바꿔 커밋을 푸시하고, 클러스터가 v2가 되는 시각을 견준다.

<figure class="fig" data-figure="gitops-sync">
  <figcaption>커밋에서 클러스터 반영까지 걸리는 시간</figcaption>
</figure>

폴링만 쓰면 10초에 한 커밋이 150초의 다음 폴링에야 보여 140초를 기다린다. 웹훅이면 푸시 알림이 바로 다시 비교를 일으켜 7초 만에 반영된다.

그렇다고 `timeout.reconciliation: 0`으로 폴링을 끄면 네트워크 문제나 설정 실수로 웹훅 하나를 놓쳤을 때 그 커밋이 반영되지 않는다. Argo CD FAQ도 0을 권하지 않고, 웹훅을 쓰면서 부하를 줄이려면 주기를 `15m`이나 `1h`로 늘리라고 한다. ArgoCD가 인터넷에 열려 있으면 `webhook.github.secret` 같은 웹훅 시크릿을 넣는다.

자동 동기화에는 멈추는 규칙이 둘 있다.

- OutOfSync일 때만 동기화한다. Synced거나 오류 상태인 앱은 건드리지 않는다.
- 같은 커밋 SHA와 파라미터로 한 번 실패한 동기화는 다시 시도하지 않는다. `syncPolicy.retry`로 재시도를 켜거나, 매니페스트를 고친 새 커밋을 넣어야 다시 돈다.

## 드리프트와 selfHeal

OutOfSync는 클러스터 쪽 변경으로도 생긴다. `kubectl scale`로 replicas를 5로 늘리면 Git의 3과 어긋나고, 이렇게 실제 상태가 Git과 달라진 것을 드리프트(drift)라고 한다. controller는 watch로 리소스 변경을 받으므로 드리프트는 다음 폴링을 기다리지 않고 OutOfSync로 뜬다.

되돌릴지는 설정에 달렸고, 기본값은 둘 다 꺼짐이다.

- `selfHeal`: 꺼져 있으면 클러스터를 직접 고친 것은 자동 동기화를 일으키지 않는다. 파드는 5개로 남고 화면에 OutOfSync만 뜬다.
- `prune`: 꺼져 있으면 Git에서 지운 리소스를 클러스터에서 지우지 않는다.

기본값이 보수적인 까닭은 둘 다 사람이 한 일을 지우기 때문이다. selfHeal은 장애 중에 손으로 늘린 replicas를 되돌리고, prune은 실수로 지운 YAML 파일 하나로 운영 리소스를 지운다.

selfHeal을 켜면 controller는 드리프트를 찾는 대로 Git 값을 다시 적용하고, 그래도 어긋나 있으면 2초부터 3배씩 늘려 최대 5분 간격으로 다시 시도한다(Argo CD 3.x의 `--self-heal-backoff-*` 기본값). 그래서 selfHeal을 켠 클러스터의 긴급 수정은 Git 커밋으로 한다. 웹훅이 걸려 있으면 커밋도 몇 초 안에 반영된다.

다른 컨트롤러가 바꾸는 필드는 selfHeal과 부딪힌다. HPA(부하에 따라 파드 수를 바꾸는 오토스케일러)가 replicas를 7로 올리면 ArgoCD가 Git의 3으로 내리고 HPA가 다시 올리는 줄다리기가 이어진다. 푸는 방법은 둘이다.

- 매니페스트에서 `replicas`를 뺀다. Argo CD 모범 사례 문서가 권하는 방법이다.
- `ignoreDifferences`로 그 필드를 비교에서 뺀다.

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

`ignoreDifferences`는 기본으로 OutOfSync 판정에만 쓰이고, 동기화할 때는 Git의 매니페스트를 그대로 적용한다. 다른 이유로 동기화가 돌면 HPA의 7이 3으로 덮인다. `RespectIgnoreDifferences=true`를 함께 줘야 적용할 때도 그 필드를 건드리지 않는다.

자동 동기화가 켜진 Application은 ArgoCD의 Rollback(이전 동기화 이력으로 되돌리기)도 쓸 수 없고, 되돌리기는 `git revert` 커밋으로 한다.

## App of Apps와 ApplicationSet

selfHeal은 Application이 관리하는 리소스를 Git과 같게 지킨다. 그런데 Application 자체는 처음에 `kubectl apply`로 올린 YAML이라 Git 밖에 있다. 앱이 30개로 늘면 어떤 Application이 클러스터에 있는지 Git만 봐서는 알 수 없다.

App of Apps는 Application을 계층으로 쌓는다. 루트 Application 하나가 Application YAML만 들어 있는 폴더를 가리킨다.

```text
gitops-repo/
├── root.yaml          # source.path: apps, destination.namespace: argocd
└── apps/
    ├── bookinfo.yaml  # kind: Application
    ├── istio-base.yaml
    └── todo-api.yaml
```

루트가 만드는 것은 파드가 아니라 Application이고, 각 Application이 다시 자기 매니페스트를 동기화한다. 아래 그림처럼 앱 추가는 YAML 한 장의 커밋이 된다.

<figure class="fig" data-figure="gitops-app-of-apps">
  <figcaption>루트 Application 하나가 apps 폴더의 Application을 데려온다</figcaption>
</figure>

> **부모 저장소에 푸시할 수 있으면 관리자다.** 자식 Application의 `project` 필드를 바꾸면 아무 프로젝트에나 배포할 수 있어서, 문서도 App of Apps를 관리자 전용 도구로 분류한다.
{: .warn}

클러스터가 dev, staging, prod로 늘면 apps 폴더를 클러스터마다 복사하게 된다. Argo CD 문서는 이 경우 ApplicationSet을 권한다. ApplicationSet은 generator가 만든 목록마다 template으로 Application을 하나씩 찍어 낸다.

{% raw %}
```yaml
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            env: prod
  template:
    metadata:
      name: 'app-{{name}}'
    spec:
      destination:
        server: '{{server}}'
```
{% endraw %}

cluster generator는 ArgoCD에 등록된 클러스터 중 `env: prod` 라벨이 붙은 것마다 Application을 만든다. 클러스터를 늘릴 때 고치는 것은 폴더가 아니라 클러스터의 라벨이다.

## 점진 배포

ArgoCD는 Git에 적힌 것을 그대로 적용할 뿐, 그 버전이 멀쩡한지는 모른다. 버그 있는 태그가 커밋되면 Deployment의 롤링 업데이트(RollingUpdate)가 파드를 차례로 바꾼다. 기본값 `maxSurge: 25%`, `maxUnavailable: 25%`면 파드 4개짜리는 하나씩 띄우고 내리며 금방 전부 바뀐다.

롤링 업데이트는 readiness probe(파드가 요청을 받을 준비가 됐는지 묻는 검사)만 보므로, 응답은 하지만 500을 돌려주는 버전도 끝까지 퍼진다. `progressDeadlineSeconds`(기본 600초)를 넘겨도 쿠버네티스는 상태에 실패를 적을 뿐 되돌리지 않는다.

Argo Rollouts는 Deployment 대신 Rollout 리소스를 쓰게 하고, 파드 템플릿은 같은 채 교체 순서만 바꾼다. 카나리(canary)는 새 버전에 트래픽 일부만 보내 놓고 기다린다. `setWeight`로 비율을, `pause`로 기다릴 시간을 정한다.

```yaml
strategy:
  canary:
    steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - setWeight: 50
      - pause: {}
```

`trafficRouting`을 설정하지 않으면 비율은 파드 수로 맞춘다. 파드 10개에 10%면 새 버전 1개, 이전 버전 9개다. 나눠떨어지지 않으면 가장 가까운 정수로 맞춰서, 41%는 새 버전 4개와 이전 버전 6개가 된다. 요청 단위로 정확히 나누려면 `trafficRouting`에 nginx나 Istio를 지정한다.

`duration` 없는 `pause`는 `kubectl argo rollouts promote`를 받을 때까지 무기한 기다린다. ArgoCD는 멈춘 Rollout을 보고 Application을 Suspended로 표시한다. 아래 데모에서 모드를 바꿔 버그 있는 버전을 배포하고, 에러를 받는 요청 비율이 어디까지 오르는지 견준다.

  <figcaption>버그 있는 버전을 배포했을 때 에러를 받는 요청 비율 (시간은 설명용 대략값)</figcaption>
</figure>

롤링 업데이트는 파드가 바뀌는 만큼 에러 비율이 올라 배포 2분 뒤 모든 요청이 에러를 받는다. 카나리는 파드 10개 중 새 버전이 1개라, 문제를 찾아 중단할 때까지 요청 10건 중 1건만 에러를 받는다.

중단을 사람이 하지 않으려면 분석(AnalysisTemplate)을 붙인다. 분석은 Prometheus 같은 곳에서 에러율을 재고, `failureLimit`의 기본값은 0이라 측정 한 번만 실패해도 분석 전체가 실패한다. 실패하면 Rollout은 중단(abort)되고 카나리 비율을 0으로 돌려 이전 안정 버전이 트래픽을 다 받는다.

중단된 Rollout은 Argo Rollouts와 ArgoCD 양쪽에 Degraded로 뜬다. Git에는 버그 있는 태그가 남아 있지만 Rollouts가 안정 버전을 유지하므로 Git을 급히 되돌리지 않아도 된다. 고친 버전을 새 커밋으로 내보내면 다시 카나리 첫 단계부터 시작한다.

블루그린(blue-green)은 새 버전을 통째로 띄워 `previewService`로 확인한 뒤, `activeService`가 가리키는 대상을 바꿔 트래픽을 한 번에 넘긴다. `autoPromotionEnabled` 기본값이 true라 그대로 두면 준비되는 즉시 넘어간다. 이전 버전은 승격 뒤에도 `scaleDownDelaySeconds`(기본 30초) 동안 떠 있어 바로 되돌릴 수 있고, 그동안 자원은 두 배가 든다.

두 버전이 동시에 요청을 받으면 안 되는 앱(세션이 버전에 묶인 앱)은 블루그린으로, 나머지 API는 카나리로 시작한다.
