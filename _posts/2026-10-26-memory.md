## 메모리 기본 구조

메모리(RAM)는 CPU가 지금 실행하는 명령과 다루는 데이터를 올려 두는 곳이다. 바이트마다 번호(주소)가 붙은 긴 칸의 줄이고, CPU는 주소만 알면 어느 칸이든 같은 속도로 읽고 쓴다. 전원이 꺼지면 내용이 사라져서, 남겨야 할 것은 디스크에 따로 적는다.

| 장치 | 크기 (보통) | 전원이 꺼지면 | 왕복 시간 (대략) |
|---|---|---|---|
| CPU 캐시 | 수 MB에서 수십 MB | 사라진다 | 1에서 15ns |
| 메모리 (DRAM) | 수십에서 수백 GB | 사라진다 | 약 100ns |
| SSD | 수 TB | 남는다 | 수십에서 100µs |

시간은 [CPU 이해하기]({{ site.baseurl }}{% post_url 2026-10-25-k8s-cpu-request-limit %})와 같은 대략값이다.

메모리는 SSD보다 천 배쯤 빠른 대신 칸 수가 적다. 그래서 운영에서는 메모리의 속도보다 **칸이 얼마나 남았는지**를 먼저 본다.

CPU와 메모리는 여럿이 나눠 쓰는 방식이 다르다.

- CPU는 시간을 나눈다. 둘이 같이 쓰면 번갈아 도느라 늦어지지만 둘 다 끝난다.
- 메모리는 공간을 나눈다. 한 칸에는 값 하나만 들어가서, 칸이 다 차면 누군가 비워야 새 값이 들어간다.

두 장면에서 쓰려는 양이 넘칠 때 무슨 일이 생기는지 견줘 보자.

<figure class="fig" data-figure="memory-time-space">
  <figcaption>CPU와 메모리를 둘이 나눠 쓸 때</figcaption>
</figure>

CPU는 모자라도 기다리면 차례가 돌아온다. 메모리는 기다려도 자리가 생기지 않아서, 커널이 무언가를 비우거나 프로세스 하나를 끝낸다(OOM, Out Of Memory). 메모리 설정은 느려지는 선이 아니라 **죽는 선**을 정하는 일이라 CPU보다 보수적으로 잡는다.

## 가상 메모리와 페이지

`top`에서 VIRT는 20GB인데 RES는 300MB인 프로세스가 흔하다. 프로세스가 보는 주소와 실제 메모리 칸이 따로 있기 때문이다.

프로세스는 저마다 자기만의 주소 공간(가상 메모리)을 받는다. 커널은 이 주소를 4KB 단위의 페이지(page)로 나누고, 페이지 테이블에 "가상 페이지 몇 번은 물리 프레임 몇 번"을 적어 둔다. CPU가 주소를 읽을 때마다 하드웨어(MMU)가 이 표를 보고 실제 칸을 찾는다.

`malloc`이나 `mmap`으로 메모리를 받으면 커널은 주소 범위만 예약한다. 물리 프레임은 그 페이지에 처음 쓰는 순간 붙는다. CPU가 표에 없는 주소를 만나 커널로 넘어가는 이 순간을 페이지 폴트(page fault)라고 한다.

두 장면에서 RSS가 언제 늘어나는지 지켜보자.

<figure class="fig" data-figure="memory-pages">
  <figcaption>가상 페이지에 물리 프레임이 붙는 순간</figcaption>
</figure>

예약만 한 32KB는 RSS에 잡히지 않고, 처음 쓴 페이지 세 개(12KB)만 잡힌다. 프레임은 물리 메모리의 빈자리 어디든 붙어서, 가상 주소가 이어져 있어도 실제 칸은 흩어져 있다.

- VSZ(VIRT): 예약한 가상 주소의 합. 쓰지 않은 범위도 들어간다.
- RSS(RES): 지금 물리 메모리에 올라와 있는 페이지의 합.

```text
$ ps -o pid,vsz,rss,comm -p 2817
    PID      VSZ    RSS COMMAND
   2817 21474836 312400 node
```

예시이고 단위는 KB다. VSZ가 20GB라도 RSS가 300MB면 실제로 차지한 칸은 300MB다. 프로세스의 메모리 사용량은 VSZ가 아니라 RSS로 읽는다.

## 메모리 사용량 지표

### 페이지 캐시

서버에서 `free`를 보니 free가 1GB밖에 없다. 그래도 서버는 멀쩡하다. 남는 메모리를 커널이 페이지 캐시로 쓰고 있어서다.

커널은 디스크에서 읽은 파일 내용을 빈 메모리에 남겨 둔다(페이지 캐시, page cache). 같은 파일을 다시 읽으면 디스크 대신 메모리에서 바로 준다. 디스크와 내용이 같은 캐시 페이지는 버리기만 하면 되므로, 앱이 메모리를 더 달라고 하면 바로 내준다.

```text
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            16Gi       4.0Gi       1.0Gi       0.1Gi        11Gi        12Gi
```

- used: 프로세스가 쓰는 메모리
- buff/cache: 페이지 캐시와 커널 버퍼
- free: 아무도 쓰지 않는 칸
- available: 스왑 없이 새 프로세스에 내줄 수 있는 양의 추정치. free에 비울 수 있는 캐시를 더한 값이다.

16GB 서버에서 파일을 읽을수록 빈 칸이 캐시로 바뀌고, 앱이 더 요청하는 순간 캐시가 비켜 주는 모습을 보자.

<figure class="fig" data-figure="memory-page-cache">
  <figcaption>빈 메모리를 채우는 페이지 캐시</figcaption>
</figure>

free가 1GB로 줄어도 available은 12GB다. 앱이 4GB를 더 요청하자 커널은 캐시 4GB를 비워 내줬다. 남은 메모리는 free가 아니라 **available**로 읽는다.

### 컨테이너 메모리 지표

Grafana의 컨테이너 메모리 그래프가 limit의 95%인데, 며칠째 OOM 없이 잘 돈다. 그래프가 페이지 캐시까지 더한 값을 그리고 있어서다.

cgroup은 컨테이너가 읽은 파일의 페이지 캐시도 그 컨테이너의 사용량으로 센다. `memory.stat` 파일에 종류별로 나뉘어 있다.

- anon: 힙, 스택처럼 파일과 연결되지 않은 메모리. 스왑이 없으면 비울 수 없다.
- active_file: 최근에 다시 쓰인 파일 캐시
- inactive_file: 한동안 쓰이지 않은 파일 캐시. 가장 먼저 비운다.

지표마다 이 중 어디까지 더하는지가 다르다.

| 지표 (cAdvisor) | 더하는 범위 | 쓰는 곳 |
|---|---|---|
| `container_memory_usage_bytes` | anon과 파일 캐시 전부 (`memory.current`) | 대시보드 기본값인 경우가 많다 |
| `container_memory_working_set_bytes` | usage에서 inactive_file을 뺀 값 | `kubectl top`, kubelet 축출 |
| `container_memory_rss` | anon | OOM 위험 추이 |

limit 2Gi 컨테이너 하나를 세 지표로 읽어 보자.

<figure class="fig" data-figure="memory-working-set">
  <figcaption>같은 컨테이너를 세 지표로 읽은 값 (크기는 예시)</figcaption>
</figure>

같은 순간인데 usage는 95%, working set은 75%, RSS는 55%로 보인다. limit에 다가가면 커널이 파일 캐시부터 비우므로, usage가 limit 근처인 것만으로는 위험하지 않다.

대시보드에는 working set을 기본으로 두고, OOM이 걱정되면 RSS가 오르는 추이를 같이 본다.

## 메모리 회수와 OOM

### 메모리 회수

OOMKilled가 나기 몇 분 전부터 응답 시간이 먼저 길어진다. 커널이 메모리를 비우느라 바쁘기 때문이다.

빈 칸이 모자라면 커널은 페이지를 비운다(회수, reclaim). 비우는 비용은 페이지 종류마다 다르다.

- 깨끗한 파일 캐시: 디스크에 같은 내용이 있어 버리기만 한다. 가장 싸다.
- 수정된 파일 캐시(dirty): 디스크에 먼저 쓰고 버린다.
- anon 페이지: 스왑으로 내보내야 비울 수 있다. 스왑이 없으면 비울 수 없다.

회수는 보통 백그라운드의 kswapd가 미리 한다. 할당이 빨라 따라가지 못하면 메모리를 요청한 프로세스가 직접 회수하며 기다린다(direct reclaim). 컨테이너는 limit에 닿을 때마다 자기 cgroup의 페이지만으로 이 회수를 한다.

limit 2Gi 컨테이너에서 anon이 계속 늘 때, 캐시와 응답 시간이 어떻게 움직이는지 지켜보자.

<figure class="fig" data-figure="memory-reclaim">
  <figcaption>anon이 늘 때 밀려나는 페이지 캐시와 응답 시간 (모양을 보여 주는 대략값)</figcaption>
</figure>

limit에 닿은 뒤에도 한동안은 캐시가 비켜 주며 버틴다. 캐시가 바닥나면 실행 중인 코드와 자주 읽는 파일까지 밀려나, 필요할 때마다 디스크에서 다시 읽는다. 응답은 이때부터 느려지고, 더 비울 것이 없을 때 OOM이 난다.

cgroup v2는 메모리를 기다린 시간의 비율을 `memory.pressure` 파일에 남긴다(PSI).

```text
$ cat /sys/fs/cgroup/memory.pressure
some avg10=12.50 avg60=4.20 avg300=1.05 total=8812391
full avg10=8.30 avg60=2.71 avg300=0.66 total=5120887
```

- some: 프로세스 하나라도 메모리를 기다린 시간의 비율(%)
- full: 실행할 프로세스 전부가 동시에 메모리를 기다린 시간의 비율(%)

예시 값이다. avg10이 12.5면 최근 10초 중 1.25초를 누군가 메모리를 기다렸다는 뜻이다. 메모리 그래프가 limit에 닿기 전에 응답이 늘면 `memory.pressure`의 some부터 본다.

### OOM killer

새벽에 프로세스가 아무 로그 없이 사라졌다. 커널 로그에 `Killed process` 한 줄만 남아 있다.

회수로도 자리를 만들지 못하면 커널은 OOM killer를 부른다. OOM killer는 후보 프로세스마다 점수(oom_score)를 매겨 가장 높은 하나를 SIGKILL로 끝낸다.

- 점수: 쓰는 메모리가 클수록 높다. 전체 메모리에서 차지하는 비율이 기준이다.
- oom_score_adj: -1000에서 1000 사이의 보정값. 점수에 더해지고, -1000이면 후보에서 빠진다.

OOM killer가 후보를 고르는 범위는 둘이다.

- 노드 OOM: 노드 메모리가 바닥나면 노드의 모든 프로세스가 후보다.
- cgroup OOM: 컨테이너가 `memory.max`에 닿으면 그 컨테이너 안의 프로세스만 후보다. 노드에 메모리가 남아 있어도 일어난다.

두 장면에서 후보가 어디까지인지 견줘 보자.

<figure class="fig" data-figure="memory-oom-killer">
  <figcaption>노드 OOM과 cgroup OOM에서 OOM killer가 고르는 범위 (점수는 단순화한 값)</figcaption>
</figure>

노드 OOM은 노드 전체에서 점수가 가장 높은 프로세스를, cgroup OOM은 limit에 닿은 컨테이너 안의 프로세스를 끝낸다. 쿠버네티스의 OOMKilled는 대부분 두 번째다. cgroup v2 노드에서 kubelet은 컨테이너 cgroup에 `memory.oom.group`을 켜서, 안의 프로세스를 하나만 고르지 않고 전부 함께 끝낸다.

SIGKILL은 프로세스가 막을 수 없는 신호라 앱 로그에 아무것도 남지 않는다. 흔적은 커널 로그에 있다.

```text
$ journalctl -k | grep -i "killed process"
Memory cgroup out of memory: Killed process 2817 (node) total-vm:21474836kB, anon-rss:2091520kB, file-rss:0kB
```

프로세스가 로그 없이 사라졌다면 커널 로그에서 `Killed process`부터 찾는다.

## 쿠버네티스의 메모리 단위

쿠버네티스는 메모리를 바이트로 적는다. 접미사가 두 벌이라 헷갈리기 쉽다.

- `Mi`, `Gi`: 2의 거듭제곱. `1Gi`는 1024³, 1,073,741,824바이트다.
- `M`, `G`: 10의 거듭제곱. `1G`는 1,000,000,000바이트로 `1Gi`보다 7% 작다.
- `m`: 1000분의 1. `400m`은 400MB가 아니라 0.4바이트다.

```yaml
resources:
  requests:
    memory: "1Gi"
  limits:
    memory: "2Gi"
```

kubelet은 limit을 컨테이너 cgroup의 `memory.max`로 적는다. request는 cgroup 파일로 가지 않고 스케줄러와 kubelet이 계산에 쓴다. 두 값이 가는 곳을 따라가 보자.

<figure class="fig" data-figure="memory-layers">
  <figcaption>requests(파랑)와 limits(주황)가 쓰이는 곳</figcaption>
</figure>

CPU request는 `cpu.weight`로 커널에 들어가 경합 때 몫을 정한다. 메모리 request는 커널이 모르는 값이라, 노드에 자리가 있는지 셈할 때와 노드가 모자랄 때 누구를 먼저 내보낼지 정할 때만 쓰인다.

| | request | limit |
|---|---|---|
| 하는 일 | 노드 고르기, 축출 순위와 oom_score_adj 계산 | 컨테이너가 쓸 메모리의 상한 |
| 넘으면 | 노드가 모자랄 때 축출 후보가 된다 | 회수로 못 버티면 OOM으로 끝난다 |
| cgroup v2 파일 (1Gi, 2Gi) | 기본은 없다 | `memory.max = 2147483648` |
| cgroup v1 파일 | 없다 | `memory.limit_in_bytes = 2147483648` |

1.37부터 Memory QoS가 베타로 기본 활성화됐지만, kubelet 기본 설정으로는 cgroup에 더 적는 값이 없다. 아래 두 설정을 켜야 동작한다.

- `memoryReservationPolicy: TieredReservation`: request를 Guaranteed 파드는 `memory.min`, Burstable 파드는 `memory.low`에 적어 회수에서 지킨다. 기본값은 `None`이다.
- `memoryThrottlingFactor`: limit보다 낮은 `memory.high`를 적어, OOM 전에 회수를 먼저 일으킨다. 기본값은 비어 있어 적지 않는다.

### limit과 OOMKilled

파드 재시작 횟수가 조용히 올라가는데 앱 로그에는 아무것도 없다. 컨테이너가 limit에 닿아 바깥에서 끝난 것이다.

컨테이너 메모리가 `memory.max`에 닿으면 커널은 그 컨테이너의 페이지부터 회수한다. 그래도 자리가 나지 않으면 cgroup OOM이 나고, 컨테이너는 SIGKILL로 끝난다.

```text
$ kubectl describe pod api-7c9f
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
    Restart Count:  4
```

- `137`: 128 더하기 9. 9번 신호(SIGKILL)로 끝났다는 뜻이다.
- kubelet은 `restartPolicy`에 따라 컨테이너를 다시 띄운다. 반복되면 재시작 간격이 늘어나 CrashLoopBackOff가 된다.

CPU limit과 메모리 limit은 넘을 때의 모습이 다르다. 아래 데모에서 모드를 바꿔 가며 부하를 올리고, 사용량 선이 limit에 닿는 순간 무슨 일이 생기는지 지켜본다.

<figure class="fig" data-figure="memory-limit">
  <figcaption>같은 부하가 CPU limit과 메모리 limit에 닿을 때 (응답 시간은 모양을 보여 주는 대략값)</figcaption>
</figure>

CPU limit에서는 사용량 선이 limit에서 평평해지고, 원하는 양과의 차이만큼 응답이 늦어진다. 메모리 limit에서는 선이 limit에 닿는 순간 끊기고, 재시작한 프로세스가 처음부터 다시 쌓는다. 바뀐 것은 자원 종류 하나인데 결과는 **느려짐과 재시작**으로 갈린다.

재시작 직후에는 캐시도 커넥션 풀도 비어 있어서, OOMKilled 한 번은 그 뒤 몇 분의 느린 응답으로 이어진다. Restart Count가 오르면 Last State의 Reason부터 본다.

### request와 축출

노드 메모리가 모자라자, limit을 넘지도 않은 파드가 Evicted 상태로 쫓겨났다. kubelet이 노드를 살리려고 파드를 고른 것이다.

kubelet은 노드의 남은 메모리(`memory.available`)를 계속 잰다. 리눅스 노드의 기본값은 100Mi 아래로 떨어지면 파드를 내보내는 것이다(축출, eviction). 커널 OOM보다 먼저 움직여 노드 전체가 멈추는 것을 막는다. 고르는 순서는 이렇다.

1. 사용량이 request를 넘은 파드가 먼저 후보다.
2. 그중 우선순위(PriorityClass)가 낮은 파드를 고른다.
3. 우선순위가 같으면 request를 많이 넘은 파드를 고른다.

request 아래로 쓰는 파드는 맨 마지막 후보다. 3Gi 노드에서 API 파드와 batch 파드의 메모리가 늘어난다. 모드를 바꿔 API 파드의 request만 다르게 두고, 노드가 모자랄 때 누가 쫓겨나는지 본다.

<figure class="fig" data-figure="memory-eviction">
  <figcaption>노드 메모리가 모자랄 때 kubelet이 고르는 파드</figcaption>
</figure>

request 256Mi일 때 API 파드는 request를 0.75Gi 넘어 가장 먼저 축출된다. request를 limit과 같게 두면 사용량이 request 아래라 후보에서 빠지고, request 없이 돌던 batch 파드가 대신 나간다. 바뀐 것은 API 파드의 request 하나다.

kubelet보다 커널 OOM이 먼저 오면, kubelet이 QoS 클래스별로 정해 둔 oom_score_adj가 순서를 정한다.

| QoS 클래스 | 조건 | oom_score_adj |
|---|---|---|
| Guaranteed | 모든 컨테이너가 CPU와 메모리 모두 request와 limit이 같다 | -997 |
| Burstable | Guaranteed가 아니고 request나 limit이 하나라도 있다 | 2에서 999. request가 클수록 낮다 |
| BestEffort | request와 limit이 하나도 없다 | 1000 |

메모리는 넘치면 끝나므로, request는 실제 사용량의 최고치에 맞추고 limit과 같게 둔다. Guaranteed는 CPU도 request와 limit이 같아야 해서, CPU limit을 빼면 Burstable이 된다. 그래도 메모리 사용량이 request 아래면 축출 순위에서는 맨 뒤다.

## Node.js의 메모리

### 프로세스 메모리 구성

힙 사용량 그래프는 500MB 근처에서 평평한데 컨테이너 메모리는 1.7GB까지 오른다. Node.js 프로세스의 메모리는 힙 하나가 아니다.

| 영역 | 들어가는 것 | 커지는 때 |
|---|---|---|
| 힙 | JS로 만든 객체, 배열, 문자열, JIT으로 번역한 코드 | 요청 하나가 객체를 많이 만들 때, 캐시를 지우지 않을 때 |
| 스택 | 함수 호출마다 쌓이는 값과 돌아갈 자리 | 호출이 깊을 때, 스레드가 늘 때 |
| 버퍼 | 파일과 네트워크로 오가는 바이트 (`Buffer`, `ArrayBuffer`) | 큰 파일 업로드, 큰 응답, 압축 |
| 네이티브 | Node 자체와 C++ 애드온 | 이미지 처리, 암호 계산, 일부 DB 드라이버 |

`process.memoryUsage()`가 이 영역을 나눠 보여 준다.

- `rss`: 프로세스가 차지한 물리 메모리 전체
- `heapTotal`, `heapUsed`: V8 힙이 잡은 크기와 그중 쓰는 양
- `external`: JS 객체에 묶인 C++ 객체의 메모리
- `arrayBuffers`: `Buffer`를 포함한 ArrayBuffer 메모리. `external`에 포함된다.

GC가 치우는 곳은 힙뿐이다. 버퍼는 그 버퍼를 가리키는 JS 객체가 치워질 때 같이 풀리지만, 크기는 힙 상한과 상관없이 커진다. 파일 업로드가 몰리는 장면에서 어느 영역이 늘어나는지 보자.

<figure class="fig" data-figure="memory-node-rss">
  <figcaption>Node.js 프로세스의 rss를 이루는 영역 (크기는 대략값)</figcaption>
</figure>

업로드가 몰리면 힙은 그대로이고 버퍼만 0.15Gi에서 1Gi로 는다. 컨테이너는 힙이 아니라 프로세스 전체와 파일 캐시를 더해 limit을 재므로, 힙 그래프만 보면 이 증가를 놓친다. Node 서버 대시보드에는 `heapUsed` 옆에 `rss`와 `external`을 같이 둔다.

### V8 힙 구조

API 서버에서 GC 로그를 켜면 Scavenge가 1초에도 몇 번씩 찍힌다. 그래도 대개 문제가 아니다. V8은 힙을 두 세대로 나눠, 금방 버려지는 객체를 싸게 치운다.

- New space: 새 객체가 놓이는 작은 공간. 두 칸(semi-space)으로 나뉜다. 한쪽이 차면 살아 있는 객체만 반대쪽으로 옮기고 나머지를 통째로 버린다(Scavenge). 대부분 버려진 객체라 짧게 끝난다.
- Old space: Scavenge를 두 번 살아남은 객체가 옮겨 가는 큰 공간. 덜 자주 치우지만, 한 번 치울 때(Mark-Compact) 공간 전체를 훑어 오래 걸린다.

Scavenge 두 번 동안 객체가 어디로 가는지 따라가 보자.

<figure class="fig" data-figure="memory-node-gc">
  <figcaption>New space에서 Old space로 옮겨 가는 객체</figcaption>
</figure>

새 객체 8개 중 6개는 첫 Scavenge에서 바로 사라지고, 두 번 살아남은 하나만 Old space로 간다. 요청 하나가 만드는 객체는 대부분 응답을 보내고 나면 버려지므로 New space에서 끝난다.

Old space에는 오래 살아야 하는 것이 남는다. 커넥션 풀, 라우팅 표, 모듈 바깥에 만든 캐시가 여기 있다. 지우는 규칙 없이 캐시에 키만 넣으면 Old space가 계속 자란다. GC 동작은 `--trace-gc`로 켜서 Mark-Compact가 얼마나 자주 도는지부터 본다.

### 힙 상한

컨테이너 limit을 8Gi로 올렸는데 힙은 2GB 근처에서 OOM이 난다. V8의 힙 상한은 limit을 그대로 따르지 않고, 프로세스가 시작할 때 따로 정해진다.

`--max-old-space-size`를 주지 않으면 Node는 자기가 인식한 메모리로 Old space 상한을 계산한다.

- 인식한 메모리: 호스트 메모리와 cgroup limit 중 작은 값
- 64비트 리눅스의 Node 20에서 26: 인식한 메모리의 절반. 최대 2GB이고, 인식한 메모리가 15GB 이상이면 4GB
- limit 2Gi면 약 1GiB, 4Gi와 8Gi는 둘 다 2GB에서 멈춘다

인식이 틀리는 경우도 있다. Node가 cgroup v2의 limit을 읽기 시작한 것은 libuv 1.45가 들어간 20.3부터다. 그보다 오래된 Node를 cgroup v2 노드에 올리면 호스트 메모리 전체로 계산해서, 힙 상한이 limit보다 커진다.

두 장면에서 Node가 어디서 메모리 크기를 읽는지 보자.

<figure class="fig" data-figure="memory-node-heap-limit">
  <figcaption>Node가 힙 상한을 정할 때 읽는 메모리 (호스트 64GB, limit 2Gi)</figcaption>
</figure>

20.3 이상은 limit 2Gi를 읽어 상한을 1GiB로 잡는다. 오래된 Node는 호스트 64GB를 읽어 4GB로 잡고, 힙이 다 차기 전에 컨테이너가 먼저 OOMKilled된다.

지금 상한은 이렇게 확인한다. MiB 단위이고 New space 몫이 조금 더해져 나온다.

```bash
node -e 'console.log(require("v8").getHeapStatistics().heap_size_limit / 2 ** 20)'
```

상한은 직접 정해 두는 편이 낫다.

```yaml
env:
  - name: NODE_OPTIONS
    value: "--max-old-space-size=1536"
```

- `--max-old-space-size`: Old space 상한(MiB). 위 값은 limit 2Gi의 75%다.
- `--max-old-space-size-percentage`: 인식한 메모리에 대한 비율. 22.21과 24.6부터 쓸 수 있고, limit을 바꿔도 비율이 따라간다.

힙 상한을 limit과 같게 두면 힙 밖의 버퍼와 네이티브 몫이 남지 않아, 힙이 차기 전에 OOMKilled가 난다. limit의 70에서 75%에서 시작해, 실제 rss와 heapUsed의 차이를 재서 맞춘다.

### 힙 OOM과 OOMKilled

같은 Node 서버가 어떤 날은 FATAL ERROR를 남기고 끝나고, 어떤 날은 아무 로그 없이 재시작된다. Node 프로세스에는 천장이 둘 있어서다.

- 힙 상한: heapUsed가 닿으면 V8이 GC를 거듭하다가 프로세스를 스스로 끝낸다.
- 컨테이너 limit: 프로세스 전체가 닿으면 커널이 SIGKILL로 끝낸다.

힙이 먼저 찬 쪽은 앱 로그에 이유가 남는다.

```text
<--- Last few GCs --->
[1:0x...] 270724131 ms: Mark-Compact 251.0 (258.6) -> 250.2 (258.8) MB, pooled: 0 MB
[1:0x...] 270724729 ms: Mark-Compact 251.2 (258.8) -> 250.4 (259.1) MB, pooled: 0 MB

FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
```

가장 무거운 Mark-Compact를 0.6초 간격으로 돌려도 251.0MB가 250.2MB로, 0.8MB밖에 줄지 않았다. 객체가 아직 어딘가에서 참조되고 있다는 뜻이라, 느린 GC가 아니라 객체를 놓지 않는 코드를 찾는다. 이 구간에서 응답은 이미 느려져 있다.

limit 2Gi에 힙 상한 1.5G로 둔 서버다. 모드를 바꿔 트래픽을 보내고, 어느 선이 어느 천장에 먼저 닿는지 본다.

<figure class="fig" data-figure="memory-node-oom">
  <figcaption>힙 상한과 limit, 천장 둘 중 먼저 닿는 쪽 (크기는 대략값)</figcaption>
</figure>

캐시가 새면 heapUsed가 힙 상한에 먼저 닿는다. Node는 FATAL ERROR를 찍고 `abort()`로 끝나서, 종료 코드는 128 더하기 SIGABRT(6)인 134다. 큰 버퍼가 몰리면 힙은 멀쩡한데 rss가 limit에 먼저 닿아, 로그 없이 137로 끝난다.

| | 힙 OOM | OOMKilled |
|---|---|---|
| 닿는 천장 | 힙 상한 | 컨테이너 limit |
| 끝내는 쪽 | V8 (프로세스 스스로) | 커널 OOM killer |
| 앱 로그 | FATAL ERROR와 직전 GC 기록 | 없다 |
| 파드의 Reason | Error | OOMKilled |
| 종료 코드 | 134 | 137 |
| 흔한 원인 | 지우지 않는 캐시, 한 요청이 만드는 객체 과다 | 큰 버퍼, 네이티브 모듈, 힙 상한을 limit과 같게 둔 설정 |

종료 코드는 둘 다 128을 넘어서 둘 다 바깥에서 끝난 것처럼 보인다. 누가 끝냈는지는 파드의 Reason과 앱 로그로 가른다.

## in-place resize

트래픽이 늘어 메모리 limit을 올리고 싶은데, 파드를 다시 만들면 캐시가 비고 연결이 끊긴다. in-place resize는 파드를 그대로 둔 채 컨테이너의 CPU와 메모리 값을 바꾼다.

1.27에 알파로 들어와 1.33에서 베타로 기본 활성화됐고, 1.35에서 정식(GA)이 됐다. `resize` 하위 리소스로 값을 바꾼다.

```bash
kubectl patch pod api-7c9f --subresource resize --patch \
  '{"spec":{"containers":[{"name":"api","resources":{"requests":{"memory":"4Gi"},"limits":{"memory":"4Gi"}}}]}}'
```

kubelet은 바뀐 값을 컨테이너 런타임에 넘기고, 런타임이 cgroup 파일(`memory.max` 등)을 고쳐 쓴다. 커널은 원래 실행 중에도 cgroup 값을 바꿀 수 있었다. 그전까지는 쿠버네티스가 값이 바뀌면 파드를 새로 만들었을 뿐이다.

리소스마다 재시작 여부를 `resizePolicy`로 정한다.

```yaml
resizePolicy:
  - resourceName: cpu
    restartPolicy: NotRequired
  - resourceName: memory
    restartPolicy: RestartContainer
```

- `NotRequired`: 기본값. 컨테이너를 그대로 두고 값만 바꾼다.
- `RestartContainer`: 컨테이너를 재시작해 새 값을 적용한다. 파드는 그대로다.

메모리를 줄일 때 NotRequired면, kubelet은 지금 사용량이 새 limit보다 크면 resize를 미루고 기다린다. 확인한 직후 사용량이 튈 수 있어 OOM을 완전히 막지는 못한다. QoS 클래스는 resize로 바뀌지 않으므로 Guaranteed 파드는 request와 limit을 함께 바꾼다.

Node 서버의 memory limit을 2Gi에서 4Gi로 올리는 두 장면을 견줘 보자.

<figure class="fig" data-figure="memory-resize">
  <figcaption>memory limit을 올릴 때 resizePolicy에 따라 달라지는 힙 상한</figcaption>
</figure>

NotRequired면 `memory.max`는 4Gi로 바뀌지만, 힙 상한은 시작할 때 정해져 1GiB 그대로다. 늘어난 메모리를 힙이 쓰지 못한다. RestartContainer면 컨테이너가 다시 시작하며 Node가 4Gi를 읽고 상한을 2GiB로 잡는다.

Node.js처럼 시작할 때 메모리 크기를 정하는 런타임은 memory의 resizePolicy를 RestartContainer로 둔다. CPU는 NotRequired로 두어 재시작 없이 바꾼다.

## 정리

| | 하는 일 | 기억할 점 |
|---|---|---|
| 페이지와 RSS | 처음 쓴 페이지에만 물리 프레임이 붙는다 | 사용량은 VSZ가 아니라 RSS로 읽는다 |
| 페이지 캐시 | 빈 메모리를 파일 캐시로 쓴다 | 남은 양은 free가 아니라 available로 읽는다 |
| working set | usage에서 inactive_file을 뺀 값 | `kubectl top`과 축출의 기준. OOM 위험은 RSS로 |
| 메모리 회수 | 파일 캐시부터 비운다 | 캐시가 바닥나면 OOM 전에 응답이 먼저 느려진다 |
| OOM killer | 점수가 가장 높은 프로세스를 SIGKILL로 끝낸다 | 노드 OOM과 cgroup OOM은 후보 범위가 다르다 |
| memory limit | cgroup `memory.max` | 넘으면 OOMKilled, 종료 코드 137 |
| memory request | 노드 고르기, 축출 순위, oom_score_adj | 최고 사용량에 맞추고 limit과 같게 둔다 |
| Node.js 힙 상한 | 인식한 메모리의 절반, 최대 2GB 또는 4GB | limit의 70에서 75%로 직접 정한다 |
| 힙 OOM과 OOMKilled | 힙 상한과 limit, 천장이 둘 | Reason과 앱 로그로 가른다 |
| in-place resize | 파드를 그대로 두고 값을 바꾼다 (1.35 GA) | Node는 memory를 RestartContainer로 |
