## 요약

- Redis는 명령을 메인 스레드 하나에서 차례로 실행한다. 쓰기는 메모리에 반영되고 클라이언트가 응답을 받은 뒤에야 레플리카에 닿는다.
- 끊겼던 레플리카는 자기 offset을 들고 와서 복제 백로그에 남은 부분만 받는다. 백로그(기본 1MB)를 벗어날 만큼 밀렸으면 RDB 스냅숏부터 다시 받는다.
- 복제가 비동기라서 프라이머리가 죽으면 성공 응답까지 받은 쓰기가 사라질 수 있다. `WAIT`과 `min-replicas-to-write`는 그 창을 좁힐 뿐 없애지 못한다.
- Sentinel은 쿼럼으로 장애를 판정하고 과반 투표로 페일오버를 시작한다. 클라이언트는 Sentinel에 다시 물어 새 프라이머리를 찾는다.
- 명령 하나가 길면 뒤의 모든 요청이 대기한다. 10ms짜리 Lua 스크립트 25개가 줄을 서면 그 뒤의 가벼운 GET은 250ms 가까이 기다린다.
- 만료된 키는 읽힐 때와 초당 10번의 표본 검사로 지워진다. 만료 시각을 흩어 두고, fork 동안 늘어나는 메모리를 남겨 둔다.
- 막히면 안 되는 쓰기는 다른 부하와 인스턴스를 나눠, 한 용도의 긴 명령이 다른 용도를 세우지 못하게 한다.

## 쓰기 경로

Redis 서버는 클라이언트 연결 수천 개를 메인 스레드 하나로 받는다. 이벤트 루프가 epoll(여러 소켓 중 읽을 준비가 된 것만 알려 주는 리눅스 시스템 콜)로 소켓을 고르고, 들어온 명령을 하나씩 꺼내 실행한다. 두 명령이 동시에 실행되는 일이 없어서 `INCR`도 잠금 없이 원자적이다.

fsync, 큰 키의 메모리 해제 같은 일부 작업만 백그라운드 스레드로 넘긴다. 소켓 읽기와 쓰기를 나눠 맡는 I/O 스레드(`io-threads`)를 켜도 명령 실행은 여전히 한 스레드다. Valkey도 같은 명령과 설정 이름으로 이렇게 동작한다.

`SET order:42 paid` 하나는 아래 그림처럼 여섯 단계를 지난다.

1. 명령이 서버 소켓의 수신 버퍼에 쌓인다.
2. 차례가 오면 메인 스레드가 명령을 파싱해 실행한다.
3. 메모리의 키 공간(해시 테이블)에 값을 쓴다.
4. 같은 명령을 복제 스트림에 덧붙인다. AOF를 켰으면 AOF 버퍼에도 덧붙인다.
5. 클라이언트에 `+OK`를 보낸다.
6. 복제 스트림이 레플리카로 흘러가고, 레플리카가 같은 명령을 실행한다.

**프라이머리는 레플리카가 받았는지 확인하지 않고 응답한다.** 레플리카는 처리한 offset을 1초마다 알려 줄 뿐이다. 덕분에 응답은 네트워크 왕복 한 번으로 끝나지만, 성공 응답을 받은 쓰기가 프라이머리 메모리에만 있는 구간이 생긴다.

복제 스트림에는 세 가지 이름이 붙는다.

- offset: 스트림의 바이트 위치다. 복제 ID(데이터 이력마다 붙는 무작위 문자열)와 offset 한 쌍이 데이터의 한 시점을 가리킨다.
- 복제 버퍼: 레플리카마다 아직 보내지 못한 스트림이다. 기본 한도는 `client-output-buffer-limit replica 256mb 64mb 60`으로, 256MB를 넘거나 64MB 이상이 60초 이어지면 그 레플리카 연결을 끊는다.
- 복제 백로그: 레플리카와 상관없이 최근 스트림을 원형 버퍼로 남겨 둔다. 기본값은 `repl-backlog-size 1mb`다.

메모리에 쓴 값을 디스크에 남기는 방식은 두 가지다.

- RDB: 정해진 간격으로 fork한 자식 프로세스가 메모리 전체를 스냅숏 파일로 쓴다. 파일이 작고 재시작이 빠르지만, 마지막 스냅숏 뒤의 쓰기는 장애 때 잃는다. 보통 수 분 분량이다.
- AOF: 쓰기 명령을 파일 끝에 덧붙인다. 기본값 `appendfsync everysec`는 1초마다 fsync해서 최대 1초 분량을 잃는다. `always`는 응답 전에 fsync해 매우 느리고, `no`는 커널에 맡겨 리눅스에서 보통 30초 주기로 내려간다.

영속성은 프로세스 재시작에, 복제는 서버 장애에 대비한다. 서로를 대신하지 못한다. 프라이머리의 영속성을 끄고 자동 재시작만 켜 두면, 빈 채로 다시 뜬 프라이머리를 레플리카가 그대로 따라 해 데이터가 모두 지워진다. 공식 문서가 이 조합을 따로 경고한다.

## 부분 재동기화와 전체 동기화

레플리카 연결은 네트워크 문제나 `repl-timeout`(기본 60초)으로 끊긴다. 다시 붙을 때 레플리카는 `PSYNC <복제 ID> <offset>`을 보내 어디까지 받았는지 알린다.

- 부분 재동기화: 그 offset 다음부터가 백로그에 남아 있으면 프라이머리는 `+CONTINUE`로 답하고 빠진 바이트만 보낸다.
- 전체 동기화: 백로그가 이미 덮어써졌거나 복제 ID가 다르면 `+FULLRESYNC`로 답한다. 프라이머리가 fork해 RDB를 만들고, 그동안 들어온 쓰기는 복제 버퍼에 쌓는다. 레플리카는 기존 데이터를 버리고 RDB를 메모리에 올린 뒤 쌓인 쓰기를 이어 받는다.

아래 그림의 두 장면은 끊긴 동안 쌓인 쓰기의 양만 다르다.

<figure class="fig" data-figure="redis-resync">
  <figcaption>끊겼던 레플리카가 다시 붙을 때</figcaption>
</figure>

백로그 크기는 끊겨도 버틸 시간에 초당 쓰기 바이트를 곱해 잡는다. 기본 1MB는 쓰기가 많은 서비스에서 1초도 버티지 못한다.

```text
초당 복제 스트림 2MB, 30초 끊김까지 부분 재동기화 → 백로그 60MB 이상
기본 1MB → 같은 부하에서 0.5초만 끊겨도 전체 동기화
```

(초당 2MB는 계산을 보이기 위한 예시 값이다. 실제 값은 `INFO replication`의 `master_repl_offset`이 1초에 늘어나는 양으로 잰다.)

전체 동기화는 양쪽에 비싸다. 프라이머리는 fork와 RDB 생성에 CPU와 메모리를 쓰고, 레플리카는 새 데이터를 메인 스레드에서 적재하는 동안 요청을 받지 못한다. 데이터가 수 GB면 수 초가 걸린다. 쓰기가 많으면 RDB를 보내는 사이에 쌓인 복제 버퍼가 256MB 한도를 넘겨 연결이 끊기고, 다시 전체 동기화를 시작하는 반복에 빠질 수 있다.

페일오버로 승격된 레플리카는 옛 복제 ID를 보조 ID로 기억한다. 그래서 다른 레플리카는 새 프라이머리에 전체 동기화 없이 부분 재동기화로 붙는다.

## 페일오버와 쓰기 유실

Sentinel은 프라이머리와 레플리카를 감시하다 프라이머리가 응답하지 않으면 레플리카 하나를 승격하는 별도 프로세스다. 함께 죽지 않을 서로 다른 서버에 3대 이상 둔다. 페일오버는 이 순서로 진행된다.

1. 주관적 다운(SDOWN): Sentinel 하나가 `down-after-milliseconds`(sentinel.conf 예시값 30000ms) 동안 PING에 유효한 답을 받지 못한다.
2. 객관적 다운(ODOWN): 쿼럼에 적은 수(3대 중 2대 등)의 Sentinel이 다운에 동의한다.
3. 리더 선출: 페일오버를 실행할 Sentinel을 전체 Sentinel의 과반 투표로 뽑는다. 쿼럼을 1로 줘도 과반과 연락되지 않으면 페일오버하지 않는다.
4. 승격: 오래 끊겨 있던 레플리카를 빼고, `replica-priority`가 낮은 쪽, 같으면 offset이 큰 쪽을 고른다. 고른 레플리카는 `REPLICAOF NO ONE`으로 프라이머리가 된다.
5. 재구성: 나머지 레플리카가 새 프라이머리를 따르게 하고 `+switch-master` 이벤트를 알린다.

비동기 복제의 대가는 여기서 드러난다. 프라이머리가 offset 1000까지 응답했는데 가장 앞선 레플리카가 960까지만 받았다면, 961~1000의 쓰기는 클라이언트가 성공으로 알고 있는데 새 프라이머리에는 없다. 아래 그림처럼 장애, 판정, 승격 세 장면을 지나면 그 구간이 사라진다.

</figure>

옛 프라이머리가 돌아오면 Sentinel이 그것을 새 프라이머리의 레플리카로 돌리고, 데이터는 새 프라이머리 것으로 덮인다. 네트워크가 갈라져 옛 프라이머리가 고립된 채 쓰기를 계속 받은 경우에도 그 쓰기는 같은 식으로 버려진다. 이 창을 좁히는 설정은 두 가지다.

- `WAIT 1 100`: 이 연결에서 앞서 보낸 쓰기를 레플리카 1대가 확인할 때까지 최대 100ms 기다린다. 확인한 레플리카 수를 돌려줄 뿐 쓰기를 되돌리지 않고, 확인한 레플리카가 승격된다는 보장도 없다.
- `min-replicas-to-write 1`, `min-replicas-max-lag 10`: 10초 안에 확인을 보낸 레플리카가 1대 미만이면 프라이머리가 쓰기를 거절한다. 고립된 프라이머리가 쓰기를 받는 시간을 10초 안으로 묶는다. 대신 레플리카가 모두 죽으면 쓰기도 멈춘다.

공식 문서도 Sentinel과 Redis 조합은 확인된 쓰기가 장애 뒤에 남는다고 보장하지 않는다고 적는다. 한 게임 서비스의 웹 이벤트 API에서도 Redis 페일오버 중 API가 실패하면 쓰기가 사라지지 않느냐는 걱정이 나왔다. 실패로 응답한 요청은 다시 보내면 되지만, **성공으로 응답한 뒤 사라지는 쓰기**는 클라이언트가 알 방법이 없다. 결제 기록이나 재화 지급처럼 잃으면 안 되는 쓰기는 원본을 관계형 DB 같은 저장소에 두고, 요청마다 멱등 키(같은 요청을 두 번 처리해도 결과가 같게 하는 식별자)를 붙여 재시도로 메운다.

클라이언트는 프라이머리 주소를 고정하지 않고 Sentinel 목록과 서비스 이름을 받는다. 연결할 때마다 아래 순서로 주소를 찾는다.

```text
SENTINEL get-master-addr-by-name mymaster   # Sentinel에 현재 프라이머리 주소를 묻는다
ROLE                                         # 붙은 인스턴스가 정말 master인지 확인한다
```

Sentinel은 역할을 바꾼 인스턴스에 `CLIENT KILL type normal`을 보내 연결을 모두 끊는다. 끊긴 클라이언트는 다시 Sentinel에 물어 새 주소로 붙는다. 감지에 30초가 걸리고 선출과 승격이 더해지므로, 예시 설정 그대로면 쓰기는 30초 넘게 실패한다.

Sentinel은 원래 서버로 되돌리는 페일백(failback)을 하지 않는다. 돌아온 옛 프라이머리는 레플리카로 남는다. 특정 서버를 프라이머리로 두고 싶으면 그 서버가 다 따라잡은 뒤 `replica-priority`로 후보를 정하고 `SENTINEL FAILOVER mymaster`를 실행한다. 이 작업도 쓰기가 잠깐 끊기므로 한산한 시간에 한다.

## 단일 스레드 병목

메인 스레드가 하나라서 명령 하나가 오래 걸리면 뒤에 선 모든 요청이 대기한다. 초당 처리량은 멀쩡해 보여도 짧은 명령의 응답 시간이 길어진다. 오래 걸리는 명령은 대개 원소 수에 비례하는 것들이다.

- `KEYS pattern`: 키 전체를 훑는다. 운영에서는 `SCAN`으로 조금씩 나눠 훑는다.
- `HGETALL`, `SMEMBERS`, `LRANGE 0 -1`: 원소 수만큼 걸리고 응답도 크다.
- `DEL`: 원소가 많은 키는 메모리 해제를 메인 스레드에서 한다. `UNLINK`는 키 공간에서 떼어 내기만 하고 해제는 백그라운드 스레드로 넘긴다.
- `EVAL`: Lua 스크립트는 원자적으로 실행되고, 실행하는 동안 서버의 다른 일이 모두 멈춘다.

한 게임 서비스의 웹 이벤트 API가 마지막 경우였다. 사용자 상태를 고치는 API를 사용자 한 명이 1분에 60~80번 불렀고, 호출마다 Redis 명령 70~100개를 묶은 Lua 스크립트 하나를 `EVAL`로 실행했다. 원자성을 위해 묶은 것이고 스크립트 하나가 7~10ms 걸렸다. 부하가 몰리자 이 스크립트가 25개쯤 줄을 섰다.

```text
대기 = 앞에 선 스크립트 수 × 스크립트 하나 실행 시간
     = 25 × 7~10ms ≈ 175~250ms
```

(사례의 수치는 둥근 대략값이다.)

같은 Redis를 쓰던 결제와 재화 서비스의 가벼운 명령이 이 줄 뒤에서 대기했고, 클라이언트 타임아웃을 넘겨 실패했다. 아래 데모에서 같은 요청 묶음을 한 인스턴스에 넣는 경우와 용도별 인스턴스로 나눠 넣는 경우를 골라 보낸다.

</figure>

두 모드에서 처리한 일의 양과 스크립트가 다 끝나는 시각은 250ms로 같다. 공유 인스턴스에서는 GET이 스크립트 줄 끝에 서서 240ms를 대기하고, 분리하면 스크립트끼리만 기다리고 GET은 바로 처리된다. 이 서비스는 세 단계로 대응했다.

1. 결제와 재화 서비스가 쓰는 Redis를 별도 인스턴스로 분리했다. 이벤트 API의 스크립트가 길어져도 결제 쪽은 기다리지 않는다.
2. 클라이언트 타임아웃을 늘렸다. 대기 자체는 줄지 않고 실패가 늦게 날 뿐이라 임시 조치다.
3. 로직을 다시 설계했다. 스크립트 하나에 묶는 명령 수를 줄여 원자성이 꼭 필요한 범위만 남기는 쪽이 근본 대응이다.

긴 명령은 기본 설정으로는 잘 드러나지 않는다.

- SLOWLOG: `slowlog-log-slower-than 10000`(기본 10ms)을 넘은 명령을 최근 128개 남긴다. 실행 시간만 재고 대기 시간은 빠져서, 7ms 스크립트는 기본값으로 한 건도 남지 않는다. 기준을 1~2ms로 낮춰 둔다.
- 지연 모니터: `CONFIG SET latency-monitor-threshold 100`을 걸면 명령, fork, 만료 주기 같은 사건별 최대 지연을 `LATENCY LATEST`와 `LATENCY DOCTOR`로 볼 수 있다. 기본값 0은 꺼짐이다.
- `busy-reply-threshold 5000`(별칭 `lua-time-limit`): 스크립트가 5초를 넘으면 다른 클라이언트에 BUSY 오류를 돌려주기 시작한다. 스크립트를 멈추지는 않는다. 아직 쓰기를 하지 않은 스크립트만 `SCRIPT KILL`로 멈출 수 있고, 이미 쓴 스크립트는 `SHUTDOWN NOSAVE` 말고 멈출 방법이 없다.

## 만료와 메모리

TTL이 지난 키는 그 순간 지워지지 않는다. 두 경로로 지워진다.

- 지연 만료(lazy expiration): 명령이 키에 접근했을 때 만료됐으면 그때 지우고 없는 키로 답한다.
- 능동 만료(active expiration): 초당 10번 만료가 걸린 키 중 20개를 무작위로 뽑아 지난 것을 지운다. 뽑은 것 중 25% 넘게 만료돼 있으면 바로 다시 뽑는다.

아래 그림처럼 아무도 읽지 않는 만료 키는 표본으로 뽑힐 때까지 메모리를 차지한다.

<figure class="fig" data-figure="redis-expire">
  <figcaption>만료된 키가 지워지는 두 경로</figcaption>
</figure>

기본 설정(`active-expire-effort 1`)은 만료됐지만 남은 키를 전체 키의 10% 안쪽으로 묶으려고 한다. 그만큼 `used_memory`는 살아 있는 데이터보다 크게 잡힌다.

같은 순간에 만료되는 키가 많으면 능동 만료가 25%를 넘는 동안 표본 검사를 거듭하며 메인 스레드를 붙잡는다. 배치 하나가 키 수십만 개에 같은 `EXPIRE 3600`을 걸면 한 시간 뒤 이 일이 생기고, 캐시라면 한꺼번에 비어 원본 DB로 요청이 몰린다. TTL에 무작위 흩어짐(jitter)을 더해 만료 시각을 퍼뜨린다.

```python
ttl = 3600 + random.randint(0, 360)  # 기준값의 10% 안에서 흩는다
```

`maxmemory`를 넘으면 쓰기가 들어올 때마다 `maxmemory-policy`에 따라 키를 내보낸다(eviction).

- `noeviction`(기본값): 아무것도 지우지 않고, 메모리를 늘리는 쓰기에 OOM 오류를 돌려준다. 읽기와 `DEL`은 된다.
- `allkeys-lru`: 모든 키 중 오래 쓰지 않은 것을 내보낸다. 캐시 전용 인스턴스의 기본 선택이다.
- `volatile-ttl`: TTL이 걸린 키 중 남은 시간이 짧은 것부터 내보낸다. TTL 걸린 키가 없으면 `noeviction`처럼 쓰기를 거절한다.

LRU는 근사다. 키 `maxmemory-samples`(기본 5)개를 뽑아 그중 가장 오래된 것을 고른다. 캐시와 지워지면 안 되는 데이터를 한 인스턴스에 두면 정책 하나로 둘을 모두 만족시킬 수 없어서, 문서도 이 경우 인스턴스를 나누라고 권한다.

`maxmemory`에는 fork 여유를 남겨 둔다. RDB 저장, AOF 재작성, 전체 동기화는 모두 fork를 쓰고, 아래 그림처럼 자식이 일하는 동안 부모가 고친 페이지만큼 메모리가 늘어난다.

<figure class="fig" data-figure="redis-fork">
  <figcaption>fork 뒤 부모가 고친 페이지만 복사되는 copy-on-write</figcaption>
</figure>

모든 페이지가 고쳐지면 부모만큼 더 쓴다. fork 자체도 페이지 테이블을 복사하는 동안 메인 스레드를 멈춘다. 24GB 인스턴스의 페이지 테이블은 48MB이고, 공식 문서의 측정에서 fork는 GB당 9~13ms(Xen 가상 머신에서는 수백 ms) 걸렸다. 투명 거대 페이지(THP)가 켜져 있으면 페이지 하나가 2MB라 작은 쓰기에도 큰 복사가 일어나서, 문서는 THP를 끄라고 권한다. 복제와 AOF 버퍼도 `maxmemory` 계산에 들어가지 않으므로 그만큼 더 남긴다.

## 운영 기준

인스턴스는 용도별로 나눈다. Redis 하나의 메인 스레드와 메모리 정책은 그 위의 모든 용도가 함께 쓴다.

- 결제, 재화처럼 막히거나 잃으면 안 되는 쓰기: `noeviction`, AOF, `min-replicas-to-write`를 건다.
- 세션, 캐시처럼 지워져도 원본에서 다시 채우는 데이터: `allkeys-lru`, 영속성은 가볍게 둔다.
- 랭킹, 이벤트 집계처럼 긴 스크립트나 큰 컬렉션을 다루는 부하: 다른 용도와 떼어, 느려져도 그 용도만 느려지게 한다.

같은 서버의 다른 프로세스로 나눠도 메인 스레드는 따로 돈다. CPU 코어와 fork 때의 메모리는 함께 쓰므로, 저장 시각을 겹치지 않게 두거나 서버를 나눈다.

클라이언트 쪽은 타임아웃과 연결 풀을 같이 정한다.

- 타임아웃: 평소 p99 응답 시간보다 넉넉하되, 페일오버 중 요청이 무한정 걸려 있지 않게 둔다. 타임아웃이 난 쓰기는 서버에서 이미 실행됐을 수 있으므로, 자동 재시도는 멱등한 명령에만 건다.
- 연결 풀: 서버는 한 번에 명령 하나만 실행하므로 풀을 키워도 처리량은 늘지 않고 서버 쪽 대기 줄만 길어진다. 풀에서 연결을 얻는 대기 시간에도 상한을 둔다.
- 연결 재사용: 요청마다 연결을 맺지 않는다. 페일오버로 연결이 끊기면 풀 전체를 닫고 Sentinel에 주소를 다시 묻는다.

레플리카로 읽기를 나누면 프라이머리 부하는 줄지만 복제 지연만큼 낡은 값을 읽는다. 방금 쓴 값을 바로 다시 읽는 흐름은 프라이머리에서 읽는다. 레플리카는 키를 직접 만료시키지 않고 프라이머리의 `DEL`을 기다리지만, 읽기에는 자기 시계로 만료된 키를 없는 것으로 답한다. 전체 동기화 중인 레플리카는 `replica-serve-stale-data yes`(기본값)라 옛 데이터로 답한다.

지연은 프라이머리와 레플리카의 offset 차이로 잰다. 바이트 차이가 초당 복제 스트림의 몇 배인지가 곧 몇 초 뒤처졌는지다.

```text
INFO replication   master_repl_offset, slave0:...,offset=...   복제 지연(바이트)
INFO persistence   latest_fork_usec                             마지막 fork 시간
INFO stats         expired_keys, evicted_keys                   만료와 축출 수
SLOWLOG GET 10                                                  최근 느린 명령
```
